## Доставка TaskFlow напрямую в main — решение владельца 05.11.2026

- Pull Request не требуется: не создавать PR и не ждать внешнего ревью. GitHub CI и автослияние остаются отключёнными.
- Штатный путь: актуализировать main → исключительно точечные локальные проверки изменённой логики и файлов → отдельный коммит только своих изменений → прямой push main в GitHub. Коммит прямо в main разрешён. Если работа велась в отдельной ветке/worktree, агент сам локально сливает её в main и пушит main, без PR.
- Публикация и локальное слияние — часть уже порученной работы: владелец не нажимает Merge и не даёт повторное разрешение. Конфликт разрешить с сохранением обеих правок; без force-push и потери чужой работы.
- Только точечные локальные проверки. Полные и глобальные тестовые прогоны, весь test suite, общий регрессионный прогон и тесты несвязанных модулей запрещены. Сервер: явные файлы тестов и --maxWorkers=4. Общий typecheck/сборка не подменяет точечную проверку; штатная сборка сервера при выкладке — отдельный шаг доставки.
- Новая логика — целевой RED → GREEN. Документация и косметика — diff и относящиеся к правке статические проверки, без придуманных тестов. Симулятор, UI-тесты и установка на iPhone — только по отдельному прямому поручению.
- Не коммитить чужие изменения и не использовать git add -A/git commit -a в общем грязном дереве. Основное дерево .110 оставлять на main; изоляция worktree разрешена, но не создаёт обязанности открывать PR.
- Сервер после push: проверить доставку. Перед перезапуском — пустая очередь ролей/чатов и резервная копия БД; затем штатная сборка, health и затронутый API. Push в GitHub ещё не доказывает выкладку.
- Отчёт: SHA опубликованного main, что точечно проверено, что выложено/установлено и что осталось. Удалять только свои уже влитые ветки/worktree. Точечные подсказки при работе/ошибках инструментов сохранять; замена постоянного промпта не является поручением отключать их.

# Правило границ работы

Весь цикл задачи (пути, доступ с .110 по ssh, сборка, симулятор, проверка,
коммит, установка на iPhone) — `AGENT-CYCLE.md`. Читать до первой правки.

## Git — прямой push main (владелец, 05.11.2026)

Полный порядок — AGENT-CYCLE.md. PR и CI не нужны.

- Сервер: актуализировать github/main, коммитить только свои файлы в main (или локально слить свою ветку) и напрямую пушить github main. Основное дерево .110 оставить на main; чужие изменения сохранить.
- iOS: актуализировать origin/main, коммитить только свои файлы в main (или локально слить свою ветку), напрямую пушить origin main и обновить зеркало github main.
- Только точечные локальные проверки. Полные и глобальные тестовые прогоны запрещены. Для документации — diff; не запускать тесты ради изменения текста инструкции.
- Публикация — часть порученной работы, дополнительное разрешение не требуется. В отчёте SHA опубликованного main и фактическая доставка. Точечные подсказки при работе инструментов сохранять.

## Нативные компоненты: постоянное правило владельца

Если владелец просит «нативный», «оригинальный» или «системный» компонент,
оставлять чистый SwiftUI-компонент без собственных `tint`, `background`,
`overlay`, `scaleEffect`, рамок, материалов и имитаций — если владелец прямо
не попросил именно эту настройку.

Нельзя называть компонент полностью системным, когда на нём остаётся хотя бы
одна такая визуальная настройка. При сомнении оставить чистый системный вид.

Работа ведётся только в `/Users/max/Проекты/TaskFlowNativeBuild`.

Исходный файл можно изменять только когда он указан в строке со статусом
`IN_PROGRESS` в реестре работ. Реестр разбит по месяцам: строку заводить
в **активном файле** `AGENT-WORK-SCOPES/<текущий месяц>.md`, новые строки — в
начало таблицы. Где журнал и как заполнять — `AGENT-CYCLE.md`, раздел 2
«Граница правки», и указатель `AGENT-WORK-SCOPES.md` в корне.
Всё вне такой строки неизменно.

## Текст ответа роли: начертание и кегль выделения — не трогать (25.10.2026)

Вид выделенных фрагментов в ответе роли задаёт `RoleReplyMarkdown.readableText`:
выделенный фрагмент получает `TFFont.body` (15 pt, системная кривая
`.subheadline`) и вес `.bold`, обычный текст — тот же цвет на 5% приглушённый.
Это решение владельца от 17.10.2026.

25.10.2026 попытка «улучшить» выделение (убрать явный кегль, оставить только
вес) изменила начертание текста во всём приложении: `RoleReplyMarkdown` — общий
компонент, он рисуется в чате с ролями, в чате «Помощника», в задачах,
заметках, карточках, отчётах и виджетах — больше 30 мест. Владелец увидел
изменённый вид и потребовал откат (`LOCK-CHAT-WINDOW-BEHAVIOUR-20261025`).

Не менять `readableText` и начертание текста ответа роли без прямого поручения
владельца. Логика «жирный должен быть крупнее обычного» здесь не работает: у
компонента своя шкала, и правка начертания меняет вид всего приложения, а не
окна чата.

## Правка логики — тест сначала (указание владельца 17.10.2026)

Правка цикла, инварианта, разбора данных, сортировки или кэша сначала
получает unit-тест. «Проверено» = тест падает на коде до правки и проходит
после; прогон на старом коде обязателен, он доказывает, что тест ловит эту
ошибку. 17.10.2026 оптимизация проявления текста в чате без теста вылетала
приложение (`LOCK-CHAT-REVEAL-CRASH-20261017`). Декоративные правки (цвет,
отступ, шрифт) под правило не попадают.

## Проверки: только логика, симулятор не трогать

**Прямое указание Максима от 25.10.2026. Действует для всех агентов и заменяет прежнее требование кадра в симуляторе.**

- Из обязательного цикла исключены сборка под симулятор, его запуск/открытие, установка и запуск приложения в нём, UI-навигация, скриншоты, видео, визуальные проверки и UI-тесты.
- Не трогать симулятор по своей инициативе, включая запуск unit-тестов через iOS Simulator. Общее поручение «сделай», «исправь», «проверь» и требования навыков разрешением не являются. Только отдельное прямое поручение владельца на конкретную проверку позволяет использовать симулятор.
- По умолчанию проверять только логику: целевые unit-тесты без симулятора и подходящие статические проверки. Для исправлений логики сохраняется требование RED → GREEN. Если существующий тест требует симулятор, назвать ограничение; не запускать его автоматически и не считать пройденным.
- Для декоративных правок не придумывать тесты, проверяющие текст исходника. Просмотреть diff; сторож дизайн-системы выполнять при изменении Sources по правилам проекта.
- Прохождение проверки логики или сборки не означает, что интерфейс понравился владельцу. Внешний вид оценивает владелец; без его оценки не заявлять визуальную приёмку.
- Не писать, не менять и не запускать UI-тесты без отдельного явного согласия на конкретный тест. Установка на iPhone — только по отдельному поручению и не разрешает UI-тесты.

## Сборка iOS — не перегревать мак (владелец 12.11.2026)

Действует для всех агентов. Владелец: «не убивать мой ноутбук».

1. Не более одной сборки Xcode одновременно.
2. Чистой сборки (`clean build`), удаления DerivedData и принудительной пересборки не бывает никогда (владелец 13.11.2026) — только инкрементальная сборка. Обёртка `~/bin/xcodebuild` отклоняет `clean` без обхода.
3. Один каталог DerivedData на одну конфигурацию (`build_device` — установка на iPhone).
4. Параллелизм компиляции — `-jobs 2`.
5. Симулятор, UI-тесты, параллельные тестовые раннеры — только с разрешения.
6. Новую сборку не запускать, пока предыдущая не закончилась.
7. Перед сборкой проверять активные процессы: `pgrep -fl 'xcodebuild|xctest|XCTRunner'`.
8. По умолчанию — только инкрементальная сборка для проверки компиляции.

Тяжелее (симулятор, предпросмотры Xcode, установка на iPhone, полная сборка) — сначала объяснить причину и спросить разрешение. Инструменты Xcode MCP `BuildProject` / `RunProject` / `RenderPreview` не дают задать `-jobs` — без разрешения не использовать.
После сборки сообщать: команду, продолжительность, результат и оставшиеся активные процессы.
`install-iphone.sh` сам отказывается собирать, если уже идёт `xcodebuild` или тесты, и собирает с `-jobs 2`.

## Тесты сервера на .110 — не класть машину (владелец, 27.10.2026)

Полный `npx vitest run` сервера без ограничения 27.10.2026 занял ~23 ядра из 28 на .110 и оставил живые сервисы и роли без процессора. Поэтому:

- по умолчанию — только целевые файлы тестов, относящиеся к правке;
- Только точечные тесты с явным списком файлов и `--maxWorkers=4`. Полные и глобальные тестовые прогоны запрещены.

Подробно — раздел «Тесты сервера — не класть .110» в `INDEX.md` серверного репозитория.

## Роли TaskFlow на маке: хост и песочница (с 15.10.2026)

Роль-разработчик по задачам проекта «TaskFlow Native iOS» работает на маке через
хост `taskflow-host` (машина `macbook`), а не в отдельной копии
`~/Проекты/TaskFlowDeveloper` — та упразднена вместе со ssh-шлюзом.

- Рабочая копия роли — git worktree этого репозитория в `.worktrees/<task_id>`,
  ветка `roles/<task_id>`, создаётся от текущего `main`. Отдельной копии,
  отстающей от main, больше нет.
- Команды идут под `sandbox-exec`: доступен только этот репозиторий; домашний
  каталог, ключи и соседние проекты закрыты. При отдельном поручении использовать симулятор — только iPhone Air iOS 27.
- Только при отдельном поручении на сборку под симулятор (не обязательный шаг). DerivedData и пакеты — внутри корня, иначе песочница не пустит:

```bash
xcodegen generate && xcodebuild -project TaskFlow.xcodeproj -scheme TaskFlow -sdk iphonesimulator -scmProvider system -IDEPackageSupportDisableManifestSandbox=YES -destination 'platform=iOS Simulator,id=9FF78D89-EE84-4914-AA56-D0A72D1AF43A' -derivedDataPath .worktrees/_derived 'OTHER_SWIFT_FLAGS=$(inherited) -disable-sandbox' build
```

  `-IDEPackageSupportDisableManifestSandbox=YES` и `-disable-sandbox` отключают
  только вложенные песочницы SwiftPM и макросов Swift: macOS не даёт запустить
  их внутри песочницы хоста. Проверено 16.10.2026: BUILD SUCCEEDED за ~7 мин. Наружная
  песочница остаётся.
- Результат — коммит в ветку `roles/<task_id>` и `git push` (операция хоста
  `git_push`): работа уходит на GitHub; агент после точечных локальных проверок локально сливает ветку в main и напрямую пушит main, без PR.
- **Долгое — в фоне** (сборка, тесты, съёмка кадров — всё, что дольше ~30 с).
  Пока команда идёт, ход роли стоит, и адресные сообщения владельца и
  оркестратора ждут в очереди до её конца (16.10.2026: указание дошло до
  разработчика только после 7-минутной сборки). Запуск:

```bash
mkdir -p .worktrees/_bg && nohup bash -c '<команда>; echo "EXIT=$?"' > .worktrees/_bg/<имя>.log 2>&1 & echo started
```

  Дальше короткими командами: `tail -5 .worktrees/_bg/<имя>.log`, готово —
  когда в логе есть `EXIT=`. Между проверками — свои короткие шаги, тогда
  сообщения доходят сразу.

## Способ работы чата следует из привязки к задаче (владелец 05.11.2026)

- Чат с задачей работает только по карточке, любой другой, включая личный, — только в чате. Выбора способа в приложении нет.
- Окно настроек есть только у личного чата без задачи: модель, рабочее пространство, вложения, режим работы. В чате с задачей и в группе левая кнопка открывает вложения.
- Нижние шторки раскрываются и закрываются свайпом, кнопки «Закрыть» и «Готово» в них не нужны.
