# Триаж UI-бага в TaskFlow iOS: репродукция → граф → код

Владелец 30.09.2026, после нескольких сессий подряд, где агент либо гадал по
скриншотам с ручным пересчётом координат, либо сразу лез в код без
воспроизведения: «зафиксируй последовательность действий... чтобы впредь ты
следовал именно ей». Порядок жёсткий, шаги не переставлять и не пропускать.

## Шаг 0 — прочитать жалобу буквально

Владелец описывает словами: какой экран, что видит, где именно (не додумывать
и не обобщать — см. правило дословности в корневом `AGENTS.md`, §6.1). Если
описание допускает два прочтения экрана/элемента — сначала одна уточняющая
строка, а не бег по всем похожим экранам.

## Шаг 1 — открыть нужный экран и снять скриншот без UI-теста

По прямому указанию Максима от 24.10.2026 **ни один агент, включая Codex, не пишет и не запускает UI-тесты автоматически**. Старое требование этого навыка использовать временный XCUITest отменено.

1. Собрать приложение один раз по `AGENT-CYCLE.md`.
2. Открыть нужный экран через `TASKFLOW_DEBUG_ROUTE` или обычную навигацию по accessibility. В домашней сети используется штатный LAN-вход; отсутствующий `TASKFLOW_AGENT_TOKEN` не искать.
3. Снять скриншот через XcodeBuildMCP `screenshot` либо `simctl io <UDID> screenshot`, посмотреть именно заявленный элемент.
4. Сообщить, что удалось воспроизвести, сохранить нужный кадр. Не обходить соседние экраны и не делать повторные сборки без причины.
5. Если экран недоступен, назвать причину владельцу. Только в крайнем случае предложить конкретный UI-тест и дождаться явного согласия. Сложность бага и требование «проверить» таким согласием не являются.

Не писать тест ради навигации, скриншота или потому что так было в старой инструкции. Даже существующий UI-тест нельзя запустить без согласия владельца. Unit-тесты логики — отдельная проверка.

## Шаг 2 — идти в граф, не грепать вслепую

Правило корневого `AGENTS.md` («Есть граф — идёшь в граф») применяется и
здесь буквально. Спросить граф словами симптома, а не именем файла:

```
mcp__graft-ios__graft_find_code "где рисуется <элемент/экран>, <что видно/что не так>"
```

Например: «шеврон сворачивания секции карточки задачи», «шапка формы
создания задачи кнопка Готово», «панель быстрого создания задачи». Граф
отдаёт ранжированные `file:line` — это и есть точка входа для шага 3, а не
повод сразу открывать первый попавшийся файл руками.

Граф может отставать от кода (правило корневого `AGENTS.md`) — использовать
находку как указатель, не как факт, и свериться с реальным исходником.

### Это правило и для субагентов, которых запускаешь сам

Прецедент 30.09.2026: делегировал исследование агенту Explore и в задании
прямым текстом написал «используй Read/Grep/Glob», ни разу не упомянув
граф — отчёт получился точным, но путём, запрещённым правилом выше. Граф
доступен только ЭТОЙ сессии как MCP-инструмент (`mcp__graft-ios__*`) —
агент, запущенный через `Agent`/Plan-agent, его САМ не подключит и не
вспомнит о нём, если не сказать явно. Поэтому в промпте любому Explore/Plan
агенту для этого репозитория — отдельной строкой: «сначала спроси граф
(`mcp__graft-ios__graft_find_code`/`graft_find_all`) по симптому, потом
Read/Grep только по тому, что граф не покрыл». Забыть эту строку — то же
самое, что не сходить в граф самому.

## Шаг 3 — точечно перейти и изучить

Открыть ровно то `file:line`, что дал граф (плюс соседний контекст,
достаточный для понимания — не весь файл целиком без нужды). Понять
механизм ДО того, как предлагать правку: что рисует конкретно этот
элемент, откуда берётся его цвет/фон/видимость, какой коммит/LOCK его ввёл
(`git blame`/комментарии рядом — часто там уже написано, почему сделано
именно так).

Только после этого — гипотеза, план правки, и (если правки не тривиальны)
согласование с владельцем перед тем, как открывать `IN_PROGRESS` в
`AGENT-WORK-SCOPES.md` и трогать код.

## Итог последовательности одной строкой

Жалоба словами → открыть нужный экран без UI-теста → скриншот → `graft` по
симптому → точное `file:line` → изучить → только потом правка.
