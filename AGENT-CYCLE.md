## Цикл

### 1. Поручение владельца

Этот цикл относится к внешнему агенту, который напрямую меняет нативный
клиент. Для такой работы не создавать учётные карточки и командные планы
в TaskFlow, не выполнять `taskflow_claim` и `taskflow_heartbeat`. Учёт
работы — в `AGENT-WORK-SCOPES.md`, результат — в `docs/`. Карточки
TaskFlow предназначены для выполнения внутренними ролями. Создавать
или запускать их только по отдельному поручению владельца. Инструкции
и жизненный цикл внутренних ролей этим файлом не регулируются.

Если владелец поручил поставить задачу внутренней команде TaskFlow,
в постановке работы с кодом обязательно проверить структурированное
поле «Ответственный за интеграцию». Автоматический выбор из команды:
оркестратор → архитектор → единственный исполнитель; если исполнителей
несколько — назвать конкретного участника. Для задач без правок репозитория
явно «Не требуется». Наличие рабочей ветки не означает перенос в main:
названный участник доводит принятые изменения до основной ветки. Сервер
проверяет назначение при запуске команды для всех источников создания,
не при сдаче разработчика или ревью. Не придумывать дополнительные барьеры.

Пояснения неочевидных полей прятать за небольшим неброским знаком «?»
рядом с названием. Постоянный текст подсказок в форме не показывать;
ошибку незаполненного обязательного поля показывать при попытке запуска.


### 2. Граница правки

Открой `AGENT-WORK-SCOPES.md` и заведи строку `IN_PROGRESS`: Lock ID, что
чиним, точный список разрешённых файлов, как проверим. Менять можно только
файлы из этой строки; смежную проблему — назвать владельцу и ждать ответа.
Готово, когда строка записана и в ней перечислен каждый файл, который
собираешься трогать.

Сначала граф, потом поиск руками:

```bash
ssh max@MacBook-Pro-Maksim.local "zsh -lc 'cd ~/Проекты/TaskFlowNativeBuild && ~/.local/graft/node_modules/.bin/graft ask \"task detail screen\"'"
```

Спрашивать английскими словами и именами типов: русский запрос «экран

может отстать. Готово, когда открыт настоящий файл экрана, а не заглушка.

### 4. Правка

- С мака — обычными инструментами редактора.
- С .110 — точечно по ssh: прочитать `ssh max@… 'cat ~/Проекты/TaskFlowNativeBuild/<файл>'`,
  записать через heredoc или скрипт замены на маке. Удобнее редактировать
  локально — можно вытащить ОДИН файл в `/tmp` на .110, поправить, вернуть
  `scp` на то же место и сразу удалить временный файл. Каталогами (`rsync`,
  `scp -r`) в репозиторий ничего не заливать.
- Добавил или удалил файл — обязательно `xcodegen generate`, иначе он не
  попадёт в проект. Ассеты прописываются в `sources` в `project.yml`.

Готово, когда изменены только файлы из строки реестра (`git status -s`).

### 5. Сборка

Через XcodeBuildMCP: в начале сессии `session_show_defaults`; если пусто —
`session_set_defaults` с `projectPath:
/Users/max/Проекты/TaskFlowNativeBuild/TaskFlow.xcodeproj`, `scheme:
TaskFlow`, симулятор. XcodeBuildMCP сам `xcodegen` не запускает — после
добавления файлов сначала шаг 4.

Или командой (с .110 — внутри `ssh … "zsh -lc '…'"`):

```bash
cd ~/Проекты/TaskFlowNativeBuild && xcodegen generate && xcodebuild -project TaskFlow.xcodeproj -scheme TaskFlow -sdk iphonesimulator -destination 'platform=iOS Simulator,name=iPhone Air,OS=27.0' -derivedDataPath build_sim build 2>&1 | grep -E 'error:|BUILD (SUCCEEDED|FAILED)' | head -30
```

Полный лог не выводить — фильтр и потолок. Готово при `BUILD SUCCEEDED`.

**Сторож дизайн-системы — до сборки.** В этом проекте есть
`Tools/design-system-guard.py` (владелец 16.10.2026): ловит сырые
системные контролы мимо `Sources/DesignSystem/` — голый `Toggle`
вместо `TFToggle`, сырой `Button` вместо `TFButton`, системные цвета
текста, ручной `.font(.system(size:))`. Сторож подключён в `project.yml`
как `preBuildScripts` и в `.claude/settings.json` как хук Claude Code,
но в логе `xcodebuild` его вывод теряется за фильтром. Агент **обязан
прогнать его явно** до сборки, по правке:

```bash
python3 Tools/design-system-guard.py --diff HEAD
```

- Код возврата 1 = есть НОВЫЕ нарушения. **Сборку не запускать, пока
  не починено или не оформлено осознанное исключение.**
- Осознанный отказ — `// design-system-guard: ignore` в самой строке
  нарушения; согласованные исторические нарушения лежат в
  `Tools/design-system-baseline.txt` и сами по себе сборку не роняют.
- Если правка затрагивает только `Tests/`, `UITests/`, `SnapshotTests/`,
  `Tools/`, `docs/` — сторож можно не звать, он сканирует `Sources/`.

После зелёного сторожа запускать сборку. Готово при `BUILD SUCCEEDED`
и пустом отчёте сторожа.

**Заголовки одного уровня сверяются внутри экрана.** Допустимый шрифт сам
по себе не означает соответствие соседним разделам. Для составных экранов
регистрировать группы заголовков в `Tools/screen-heading-scopes.json`:
экран, уровень, файл, тип и функция/свойство контейнера раздела. Первый
`Text`/`SettingsCapsLabel` контейнера считается его заголовком. Включать
вложенные компоненты другого файла в ту же группу. При добавлении раздела
дополнять группу; если нужный шаблон сторож не распознаёт — расширить его
с регрессионным тестом, не объявлять проверку выполненной. Группы разных
экранов не сравниваются. Режим `--fragment` без файла не проверяет это
правило; использовать `--new-file`, `--paths`, `--diff` или сборку.

### 6. Запуск в симуляторе

Вход без экрана логина — токен не нужен: в домашней сети приложение входит
само (`POST /auth/lan` при старте без токена, дальше токен лежит в Keychain):

```bash
SIMCTL_CHILD_TASKFLOW_DEBUG_ROUTE=today xcrun simctl launch <UDID> com.maksim.taskflow.native
```

Ключа `TASKFLOW_AGENT_TOKEN` в vault нет — снят намеренно; не искать и не
подменять другим токеном.
`TASKFLOW_DEBUG_ROUTE` открывает экран сразу: `overview`, `settings`,
`notes`, `projects`, `notifications`, `chat`, `today`, `upcoming`,
`noteeditor:<id>`, `task:<id>`, `expand`, `quickadd`. Booted-симуляторов
несколько — UDID указывать явно (`list_sims`). Готово, когда нужный экран
открыт с данными.

### 7. Проверка

#### Выбор режима: лёгкий или полный

До проверок выбрать режим по риску изменения. По умолчанию для обычной
локальной правки действует **лёгкий режим**; полный цикл включается для
критичных изменений или по отдельному поручению владельца.

- **Лёгкий режим** — декоративные и локальные правки, которые не меняют
  логику, сохранение данных, сетевой контракт, права доступа, порядок
  операций или взаимодействие компонентов. Выполнить одну подходящую
  автоматическую проверку: ближайший существующий юнит-тест или, если правка
  видна на экране, кадр симулятора. UI-тесты запускает только Codex (см.
  AGENTS.md), остальные агенты кадр снимают и смотрят.
  Если менялся Swift-код приложения, собрать нужный тестовый продукт и
  запустить эту проверку один раз. Не добавлять временный тест, если уже есть
  подходящий; не запускать полный набор, физический iPhone, ручной обход
  экранов и метрики производительности. После успешного результата остановиться.
- **Полный режим** — изменения, где ошибка может повредить или потерять данные,
  нарушить безопасность/доступ, сломать основной сценарий приложения,
  контракт API/событий, синхронизацию, очереди, сохранение либо работу между
  компонентами/ролями; также любые изменения, для которых владелец отдельно
  запросил полный цикл. Подготовить целевые регрессионные проверки по риску и
  пройти применимые шаги этого раздела, включая симулятор и физический iPhone
  для поведения интерфейса. Метрики собирать только для изменений
  производительности.
- Если граница риска неясна и влияет на выбор режима, сначала уточнить её у
  владельца. Не повышать декоративную правку до полного цикла «на всякий случай».

Для обоих режимов действуют правила экономии ниже: проверять конкретное
требование, сохранять результат и не повторять успешную проверку без новой
правки. Ошибка теста в инфраструктуре или самом тесте не является поводом
многократно чинить тест и запускать его заново; зафиксировать блокер и сообщить
владельцу.

#### Правка логики — сначала тест, который её ловит (указание владельца 17.10.2026)

Любая правка логики — цикл, инвариант, разбор данных, сортировка, кэш,
перестроение ленты — сначала получает unit-тест. «Проверено» означает: тест
**падает** на коде до правки и **проходит** после. Один прогон на старом коде
обязателен: он доказывает, что тест ловит именно эту ошибку, а не что-нибудь
соседнее.

Причина: 17.10.2026 оптимизация проявления текста в чате отдана без теста и
падала в `Range requires lowerBound <= upperBound` — приложение вылетало
(`LOCK-CHAT-REVEAL-CRASH-20261017`). Декоративные правки (цвет, отступ, шрифт,
заголовок) под это правило не попадают — их проверяет кадр симулятора.

**Все тесты запускать в фоне.** Сборка тестовых продуктов, unit/UI-тесты и
долгие сканирования не должны удерживать рабочий ход в ожидании: запустить их
асинхронным MCP-вызовом или отдельным фоновым процессом, затем продолжать
независимую работу в разрешённой области. Результат проверять короткими
опросами состояния/лога; к ожиданию возвращаться только когда для продолжения
нужен результат или перед сдачей. Для shell-команд использовать лог и маркер
завершения, например:

```bash
mkdir -p .worktrees/_bg
nohup bash -c '<команда теста>; echo "EXIT=$?"' \
  > .worktrees/_bg/<имя-теста>.log 2>&1 </dev/null &
```

Не запускать тот же тест повторно, пока первый процесс ещё работает. После
завершения прочитать код `EXIT` и итог теста, а не считать запуск доказательством.

**Постоянное указание владельца, 10.10.2026: рабочий образец и экономный цикл.**

- Если владелец указал рабочее окно/компонент в приложении, сначала открыть его реализацию и перенести существующее поведение. Не подбирать новые настройки вместо названного образца. Менять только порученный элемент; список и соседние экраны не затрагивать.
- До запуска подготовить один точный XCUITest (это шаг Codex, не остальных агентов): выбрать элемент именно внутри нужного окна по идентификатору/label, учесть возврат прокрутки к началу перед сворачиванием. Не использовать первый попавшийся ScrollView — это может быть экран позади sheet.
- Один раз собрать актуальные исходники и тесты, сохранить возвращённый MCP путь `.xctestproducts` либо `.xctestrun`. Повтор того же теста на той же сборке запускать через MCP `test_sim(testProductsPath: ...)` / `test_sim(xctestrunPath: ...)`: это `test-without-building`. Не повторять полный build/test ради неизменной проверки.
- После изменения исходника приложения или Swift-файла теста нужна новая сборка соответствующих продуктов; старый пакет не содержит правку. Это обоснованная пересборка, а не исключение для повторных запусков без изменений. Не делать clean/rebuild без конкретного сбоя сборки. Если после правки приложения DerivedData «вдруг» холодный (новый путь или первый запуск) — это нормально, не лечить `clean`; следующая инкрементальная сборка вернёт DerivedData в тёплое состояние.
- Если нужная проверка прошла и новых правок нет, не расширять и не повторять её: сохранить результат и завершить работу. Не ставить фиксированные задержки, когда можно ждать нужный элемент или состояние.


#### Юнит-тесты — отдельный режим

Юнит-тесты в `Tests/` (XCTest + Swift Testing) не требуют UI-сценариев и
тащат только test-раннер, без переустановки `.app` в симулятор. Их тоже
прогонять через `test-without-building` поверх уже собранных продуктов
(`TaskFlowTests.xctestproducts`), но лимит «не больше двух за задачу» к ним
не относится: один unit-тест идёт секунды, и можно гонять нужный тест по
`-only-testing` столько раз, сколько требует правка. Два прогона лимит — на
полный набор и на UI-тесты, а не на каждый `-only-testing`-запуск.

| Вид теста | Где | Команда | Лимит прогонов |
| --- | --- | --- | --- |
| Один unit-тест | `Tests/` | `xcodebuild … -only-testing:TaskFlowTests/…/<test> test-without-building` | Нет жёсткого лимита |
| Полный набор unit | `Tests/` | `xcodebuild … test-without-building` | 1–2 раза перед сдачей |
| Целевой UI | `UITests/` | `xcodebuild … -only-testing:TaskFlowUITests/… test-without-building` | Не больше 2 за задачу |
| Полный UI | `UITests/` | Не запускать без отдельного указания владельца | — |

#### Предел автотестов — постоянное указание владельца, 13.10.2026

Уточняет пределы проверок и для лёгкого, и для полного режима.

- **Картинки, иконки, аватарки, цвета, тексты и мелкие правки вида** — лёгкий
  режим: одна подходящая автоматическая проверка (тест, скан или сборка).
  Скриншот, физическое устройство и полный обход экранов не обязательны;
  добавлять их по отдельному запросу владельца или если тест выявил проблему.
- **Остальное** — не больше двух прогонов UI-теста за задачу. Не прошёл со
  второго раза — остановиться и написать владельцу: что проверял, на каком
  шаге упало, снимок экрана. Не крутить «поправил тест → пересобрал → снова».
- Повторный прогон — только через готовую сборку (`test-without-building`),
  без полной пересборки.
- **Прямое указание владельца 17.10.2026: в тестах сборки приложения быть не
  должно, прогонов — не больше двух.** Раздел «Тесты — БЕЗ сборки приложения»
  ниже.

#### Тесты — БЕЗ сборки приложения. Не больше двух прогонов — указание владельца 17.10.2026

Владелец, дословно: «Зачем в тесты включать сборку? Зачем каждый раз собирать одно и
то же? Тесты гонять два раза максимум». Это жёсткое правило, оно сильнее любых
соображений экономии ниже и не обсуждается.

1. **В команду запуска тестов сборку приложения не включать.** Ни
   `xcodebuild … test`, ни `build-for-testing` «на всякий случай». Сборка — это
   отдельный шаг цикла (шаг 4), и в тестовом прогоне её быть не должно.
   Запуск: `xcodebuild … test-without-building` по уже собранным продуктам
   (`.xctestproducts` / `.xctestrun`).
2. **Где взять готовые продукты.** Собранные артефакты тестов в этом проекте
   лежат в `build_sim/Build/Products/Debug-iphonesimulator/`. Нужны
   `TaskFlowTests.xctestproducts` (юнит-таргет) и/или
   `TaskFlowUITests.xctestproducts` (UI-таргет) и парный `*.xctestrun` рядом.
   Перед каждым прогоном проверить, что файл существует и его `mtime` свежее
   текущей правки: если продукт старше правки — собрать заново один раз
   (шаг 5), это смена входных данных, а не «пересборка ради пересборки».
   Если продуктов в репозитории нет вообще (новая сессия, чистый
   DerivedData) — собрать их один раз командами из шага 5, и только один раз;
   дальше все прогоны идут по этим продуктам.
3. **Собрать один раз — и дальше не пересобирать то же самое.** Пересборка
   допустима только когда действительно менялся исходник приложения или
   Swift-файл теста. Проверка, для которой код не менялся, идёт по той же
   готовой сборке.
4. **Два прогона за задачу, максимум.** Это счётчик на всю задачу, а не на
   каждый отдельный симптом: восемь прогонов «по одному на каждое падение» —
   нарушение. Нашёл второе падение в том же прогоне — это одно падение, а не
   повод запускать ещё раз. Первый прогон не прошёл — второй и последний.
   Не прошёл и второй — стоп: зафиксировать, что проверял, на каком шаге
   упало, приложить снимок экрана и доложить владельцу. Никаких
   «поправил тест → пересобрал → снова».
5. **Считать прогоны заранее.** Прежде чем запустить тест, ответить себе: это
   первый прогон или второй? Третьего не бывает. Если задача требует больше
   двух проверок — это неверно выбранный способ проверки, а не повод крутить
   дальше.

Прецедент 17.10.2026: правка чата — девять прогонов `xcodebuild test` с
пересборкой в каждом, больше часа; правильная схема — одна сборка, дальше
`test-without-building`.

Прецедент 13.10.2026: аватарка секретаря — семь прогонов одного временного
теста, полчаса без результата.

#### Оформление и визуал — указание владельца, 17.10.2026

Владелец, дословно: «Главное, чтобы оно не крашилось. И всё. И работала
логика. Потому что на вас по-другому всё равно нихуя не делается с этими
проверками». Агент не различает мелкие наплывы и правильный вид; кадры,
снимаемые агентом, не заменяют твою оценку. Визуальную приёмку делает
владелец на iPhone, а не агент.

**Что проверяет агент:**

1. **Не крашится и работает логика.** Smoke-маршрут через приложение
   (открыть → создать → закрыть → переоткрыть → на месте) или ближайший
   существующий регрессионный тест из `UITests/` (структурный, не визуальный).
   Это и есть приёмка. Зелёного теста на «не падает» достаточно для большинства
   правок.
2. **Сторож дизайн-системы.** `Tools/design-system-guard.py` — основной
   гейт, ловит сырые системные контролы (Toggle, Button, цвета, кегль)
   мимо `Sources/DesignSystem/`. Звонится по правке в шаге 5 до сборки
   (`--diff HEAD`); при код возврата 1 — чинить или согласовывать
   исключение. Подробности и режимы — в шапке самого скрипта и в
   `docs/2026-10-16-design-system-guard.md`.
3. **`ui-drift-scan.sh` (вспомогательно).** Ловит отступы/фоны/заливки,
   которые `design-system-guard` не покрывает: свой фон у корневого
   списка вместо `.tfScreenBackground()`, `TFButton` без `variant:`
   (красная заливка вместо серой), системный `Button("Повторить")`
   (синий), сплошной `Color.black`. Идёт в коде, секунды. Код возврата 1
   = есть незарегистрированное отклонение; показать владельцу отдельным
   списком и не править молча. `Tests/UIStyleGateTests.swift` — то же
   самое в виде XCTest-ассертов, если удобнее прогнать в наборе тестов.

**Что агент НЕ делает:**

- **Не снимает кадры для визуальной приёмки.** Скриншоты экрана,
  `XCTAttachment(screenshot:)`, `simctl io screenshot` — только когда владелец
  явно попросил показать конкретное состояние, или когда нужно приложить
  доказательство к отчёту по конкретному багу. Не «на всякий случай для
  приёмки» — кадр всё равно не скажет агенту, нормально это или нет.
- **Не обходит экраны визуально.** `UITests/UIStyleGateUITests.swift` как
  «визуальный обход» — отменён; файл остаётся в репозитории как обычный
  структурный гейт, но агенту не запускать его для приёмки декоративных
  правок.
- **Не сравнивает кадры с образцами.** «Зелёный XCUITest, значит вид
  правильный» — ложное правило: тест проверяет существование элемента, а не
  его оттенок. Эту работу делает владелец.
- **Не требует кадры для каждой правки.** Локальная декоративная правка
  (цвет, отступ, шрифт, иконка, текст) — собрать, что не крашится, передать
  владельцу; он сам посмотрит на iPhone за минуту.

**Когда визуальная приёмка агентом оправдана:** создаётся новая страница
с нуля или переписывается целиком существующий экран (новая морда, новый
поток экранов). В этом случае агент снимает кадры **только заявленных
элементов нового экрана**, по `accessibilityIdentifier`, и кладёт в отчёт;
это не «визуальный обход», а приложение доказательств к сдаче нового
экрана. Кадры соседних экранов и проверка мелких наплывов — не задача
агента. Предел: не больше двух заходов в сутки на новый экран, дальше
передать владельцу.

В полном режиме при сдаче критических изменений (потеря данных,
безопасность, основной сценарий, API/события, синхронизация) — физический
iPhone и `docs/ГГГГ-ММ-ДД-<тема>.md` обязательны, как в разделе «Приёмка
на устройстве» ниже.

##### «Отклонений нет» — не результат сам по себе, а условие

Скан выдаёт «Отклонений нет» только если знает все классы расхождений.
На 16.10.2026 закрыты ровно два, и оба открылись как ложные находки:

| Класс пропуска | Что скан не знал | Чем закрыт |
|---|---|---|
| Системный диалог | кнопка внутри `.alert`/`.confirmationDialog` красится СИСТЕМОЙ, синий там законен | `in_system_dialog()` — разбор скобок |
| Тинированный экран | `.tint(Color.tfText)` перекрашивает системные кнопки в серый | список `TINTED_SCREENS` |

Из девяти находок `KNOWN` две оказались ложными именно по этим причинам. То
есть «Отклонений нет» означает «среди известных классов расхождений новых
нет», а не «отклонений не существует».

**Правило для агента.** Найденную находку нельзя пропустить молча, даже если
она выглядит ерундой. Дальше ровно один из двух исходов:

1. **Отклонение настоящее** — починить и убрать из `KNOWN`, либо оставить в
   `KNOWN` с причиной и показать владельцу отдельным списком.
2. **Находка ложная** — починить СКАН, а не код приложения: добавить правило,
   которое отличает этот случай, и записать, какой это класс пропуска.

Молча удалить находку нельзя ни в первом, ни во втором случае. Причина простая
и уже проверена: пока класс пропуска не назван, он вернётся — на другой
странице или после чтения кода по другому поводу, и снова снимет время.

**Когда находка ложная, это находка на скан, а не на экран.** Правка вида
в угоду снять находку — обратный порядок: скан должен знать про экран, а экран
не обязан знать про скан.

Обнаружив новый класс пропуска, сказать владельцу прямо: скан неполон, вот
что он не видит. Молча расширить список исключений — значит через месяц
сказать «отклонений нет» и соврать.

#### Приёмка на устройстве — постоянное указание владельца, 11.10.2026

Этот полный порядок применяется только в **полном режиме**. Для лёгкого режима
достаточно выбранной автоматической проверки; физическая установка, полный
набор UI-сценариев, сбор метрик и восстановление обычного запуска не требуются.

Для изменений поведения интерфейса, чата, анимации, прокрутки, обновления
данных и завершения операций проверка включает **физический iPhone владельца**.
Поручение такой правки включает сборку, установку и целевые тесты на устройстве;
отдельно спрашивать разрешение на каждый запуск не нужно. Правки только
документации не требуют сборки и запуска приложения. Явное указание владельца
не запускать тесты или не устанавливать приложение имеет приоритет.

Порядок — как в проверке чата 11.10.2026:

1. **Воспроизвести конкретный дефект.** До правки зафиксировать исходный сценарий
   и, где применимо, падающую регрессию. Выбирать проверки по цели владельца:
   порядок и привязку ответа, обновление при гонках REST/WebSocket,
   завершение до получения сохранённого результата, исчезновение таймера и
   индикаторов, готовность виджета/HTML и сохранение состояния интерактива.
   Зелёная сборка сама по себе поведение не подтверждает.
2. **Подготовить точный XCUITest.** Искать нужное окно и элементы по
   `accessibilityIdentifier`/`label`, ждать состояние через `waitForExistence`
   или expectation. Проверить промежуточное и конечное состояния, а не только
   наличие экрана. Получать кадр через `XCTAttachment(screenshot:)` с
   `lifetime = .keepAlways` и визуально сверять его с требованием.
3. **Проверить настоящий механизм.** Детерминированная DEBUG-фикстура может
   заменить сетевой ответ, но обязана проходить через тот же компонент и
   механизм обновления/анимации, что работает у пользователя. Если preview
   отключает очередь текста, fade, прокрутку или другой проверяемый механизм,
   включить его явно. Успех фикстуры не объявлять проверкой живого API или
   реальной генерации модели. Для изменений сервера отдельно проверить
   контракт событий и развёрнутый сервис; перед перезапуском убедиться,
   что очереди и выполняющиеся ходы пусты.
4. **Сначала симулятор, затем физический iPhone.** Запустить затронутые
   регрессии и точный UI-сценарий. На устройстве подтвердить установку
   актуальной сборки и пройти нужные целевые проверки через XcodeBuildMCP
   device workflow. Если MCP device tools недоступны, использовать CLI:
   сначала `xcodebuildmcp device test --help`, затем `device test`.
   Проверять ID устройства через `device list`; не подставлять ID симулятора.
   Если телефон недоступен/заблокирован, указать точный блокер и оставить
   физическую приёмку незавершённой; симулятор её не заменяет.
5. **Измерить заявленную плавность и нагрузку.** Когда задача касается
   производительности, выполнить один одинаковый, представительный сценарий
   до и после: например, три свайпа по истории из 300 сообщений и отдельно
   показ длинного ответа через настоящую очередь. Использовать
   `XCTHitchMetric(application:)`, `XCTCPUMetric(application:)`,
   `XCTMemoryMetric(application:)`. Проверить, что xcresult действительно
   содержит метрики. Если симулятор не вернул hitch-метрики, получить их
   на устройстве. Число hitches, их длительность/отношение, CPU и память
   сообщать с платформой и сценарием; не выдавать CPU, 16 мс таймер или
   ноль hitches за измерение FPS. FPS утверждать только при отдельном измерении.
6. **Сохранить доказательства и вернуть обычный запуск.** Записать в отчёт
   команды, версии ОС/устройство, число прошедших и упавших тестов, пути
   `.xcresult` и продуктов, кадры и значения метрик с единицами. Выгрузить
   кадры через `xcresulttool export attachments`, метрики — через
   `xcresulttool get test-results metrics`. Временный UI-тест сохранить
   в папке доказательств при необходимости воспроизведения и удалить из
   `UITests/` после последней проверки, затем выполнить `xcodegen generate`.
   После тестов завершить preview-процесс, если он ещё работает, и запустить
   установленное приложение без тестовых переменных через `device launch`.
   Проверить успешный обычный запуск.

Для каждой платформы сохранить свой `.xctestproducts`/`.xctestrun` и повторять
неизменную проверку без сборки. Продукты симулятора не подходят iPhone.
После правок Swift-кода или теста пересобрать соответствующие продукты.
Не повторять уже успешные проверки без новой правки или обнаруженной проблемы.
Проверка завершена, когда **каждое требование владельца** подтверждено
подходящим результатом; исходники, тесты симулятора, тесты устройства,
живой сервис и подтверждение владельца — разные уровни доказательства.

Пример целевого запуска на iPhone (подставить актуальные ID и имя теста):

```bash
xcodebuildmcp device test \
  --project-path /Users/max/Проекты/TaskFlowNativeBuild/TaskFlow.xcodeproj \
  --scheme TaskFlow --device-id <DEVICE_UDID> \
  --derived-data-path /Users/max/Проекты/TaskFlowNativeBuild/build_device \
  --extra-args '-only-testing:TaskFlowUITests/<Suite>/<Test>' '-allowProvisioningUpdates' \
  --progress false --output json
```

Повтор без изменения кода — `device test --device-id <DEVICE_UDID>
--test-products-path <DEVICE_XCTESTPRODUCTS>` с тем же целевым тестом
(либо `--xctestrun-path`). Не совмещать пути готовых продуктов с
`--project-path`/`--scheme`/`--derived-data-path`.

Рабочий образец: `docs/2026-10-11-chat-correctness.md` и временный тест,
сохранённый в `docs/2026-10-11-chat-correctness/ChatCorrectnessUITests.swift`.


Интерфейс проверяется кадром: Codex снимает его временным XCUITest
(`accessibilityIdentifier`/`label`, `XCTAttachment(screenshot:)`, выгрузка —
`xcrun xcresulttool export attachments`), остальные агенты — кадром симулятора
через `xcrun simctl io <UDID> screenshot`. Ручной тап по
координатам скриншота промахивается (points против пикселей ×3). Баг не
поддаётся со второй попытки — `NSLog` в подозрительное место и
`xcrun simctl spawn <UDID> log show --last 5m --predicate 'process == "TaskFlow"' --style compact`.
Временный тест удалить после всех целевых проверок, включая устройство.
Готово, когда кадр показывает исправленное состояние, затронутые тесты
зелёные и выполнена физическая приёмка, описанная выше.
