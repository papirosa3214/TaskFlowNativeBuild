## Цикл

### 1. Поручение владельца

Этот цикл относится к внешнему агенту, который напрямую меняет нативный
клиент. Для такой работы не создавать учётные карточки и командные планы
в TaskFlow, не выполнять `taskflow_claim` и `taskflow_heartbeat`. Учёт
работы — в `AGENT-WORK-SCOPES.md`, результат — в `docs/`. Карточки
TaskFlow предназначены для выполнения внутренними ролями. Создавать
или запускать их только по отдельному поручению владельца. Инструкции
и жизненный цикл внутренних ролей этим файлом не регулируются.

Если владелец поручил поставить задачу внутренней команде TaskFlow,
в постановке работы с кодом обязательно проверить структурированное
поле «Ответственный за интеграцию». Автоматический выбор из команды:
оркестратор → архитектор → единственный исполнитель; если исполнителей
несколько — назвать конкретного участника. Для задач без правок репозитория
явно «Не требуется». Наличие рабочей ветки не означает перенос в main:
названный участник доводит принятые изменения до основной ветки. Сервер
проверяет назначение при запуске команды для всех источников создания,
не при сдаче разработчика или ревью. Не придумывать дополнительные барьеры.

Пояснения неочевидных полей прятать за небольшим неброским знаком «?»
рядом с названием. Постоянный текст подсказок в форме не показывать;
ошибку незаполненного обязательного поля показывать при попытке запуска.


### 2. Граница правки

Открой `AGENT-WORK-SCOPES.md` и заведи строку `IN_PROGRESS`: Lock ID, что
чиним, точный список разрешённых файлов, как проверим. Менять можно только
файлы из этой строки; смежную проблему — назвать владельцу и ждать ответа.
Готово, когда строка записана и в ней перечислен каждый файл, который
собираешься трогать.

### 3. Найти код

Сначала граф, потом поиск руками:

```bash
ssh max@MacBook-Pro-Maksim.local "zsh -lc 'cd ~/Проекты/TaskFlowNativeBuild && ~/.local/graft/node_modules/.bin/graft ask \"task detail screen\"'"
```

Спрашивать английскими словами и именами типов: русский запрос «экран
карточки задачи» вернул пусто, английский — `TaskFormScreen.swift`. Пусто — `graft grep
"<литерал>"`, `graft callers <символ>`. Найденное сверь по исходнику: граф
может отстать. Готово, когда открыт настоящий файл экрана, а не заглушка.

### 4. Правка

- С мака — обычными инструментами редактора.
- С .110 — точечно по ssh: прочитать `ssh max@… 'cat ~/Проекты/TaskFlowNativeBuild/<файл>'`,
  записать через heredoc или скрипт замены на маке. Удобнее редактировать
  локально — можно вытащить ОДИН файл в `/tmp` на .110, поправить, вернуть
  `scp` на то же место и сразу удалить временный файл. Каталогами (`rsync`,
  `scp -r`) в репозиторий ничего не заливать.
- Добавил или удалил файл — обязательно `xcodegen generate`, иначе он не
  попадёт в проект. Ассеты прописываются в `sources` в `project.yml`.

Готово, когда изменены только файлы из строки реестра (`git status -s`).

### 5. Сборка

Через XcodeBuildMCP: в начале сессии `session_show_defaults`; если пусто —
`session_set_defaults` с `projectPath:
/Users/max/Проекты/TaskFlowNativeBuild/TaskFlow.xcodeproj`, `scheme:
TaskFlow`, симулятор. XcodeBuildMCP сам `xcodegen` не запускает — после
добавления файлов сначала шаг 4.

Или командой (с .110 — внутри `ssh … "zsh -lc '…'"`):

```bash
cd ~/Проекты/TaskFlowNativeBuild && xcodegen generate && xcodebuild -project TaskFlow.xcodeproj -scheme TaskFlow -sdk iphonesimulator -destination 'platform=iOS Simulator,name=iPhone Air,OS=27.0' -derivedDataPath build_sim build 2>&1 | grep -E 'error:|BUILD (SUCCEEDED|FAILED)' | head -30
```

Полный лог не выводить — фильтр и потолок. Готово при `BUILD SUCCEEDED`.

**Сторож дизайн-системы — до сборки.** В этом проекте есть
`Tools/design-system-guard.py` (владелец 16.10.2026): ловит сырые
системные контролы мимо `Sources/DesignSystem/` — голый `Toggle`
вместо `TFToggle`, сырой `Button` вместо `TFButton`, системные цвета
текста, ручной `.font(.system(size:))`. Сторож подключён в `project.yml`
как `preBuildScripts` и в `.claude/settings.json` как хук Claude Code,
но в логе `xcodebuild` его вывод теряется за фильтром. Агент **обязан
прогнать его явно** до сборки, по правке:

```bash
python3 Tools/design-system-guard.py --diff HEAD
```

- Код возврата 1 = есть НОВЫЕ нарушения. **Сборку не запускать, пока
  не починено или не оформлено осознанное исключение.**
- Осознанный отказ — `// design-system-guard: ignore` в самой строке
  нарушения; согласованные исторические нарушения лежат в
  `Tools/design-system-baseline.txt` и сами по себе сборку не роняют.
- Если правка затрагивает только `Tests/`, `UITests/`, `SnapshotTests/`,
  `Tools/`, `docs/` — сторож можно не звать, он сканирует `Sources/`.

После зелёного сторожа запускать сборку. Готово при `BUILD SUCCEEDED`
и пустом отчёте сторожа.

#### XcodeBuildMCP: как подключить с нуля

Нужен, чтобы собирать, запускать симулятор, снимать кадры и тапать по
элементам доступности без UI-тестов. Проверка одной командой:

```bash
which xcodebuildmcp && xcodebuildmcp --version   # сейчас: /opt/homebrew/bin/xcodebuildmcp, 2.7.0
```

Бинарника нет — поставить (`npm i -g xcodebuildmcp@latest`, откуда и появился
симлинк `/opt/homebrew/bin/xcodebuildmcp -> ../lib/node_modules/xcodebuildmcp/build/cli.js`).

Дальше прописать сервер в конфиг оболочки, в которой работаешь. Значения одни и
те же, отличается только файл:

| Оболочка | Файл | Блок |
|---|---|---|
| OpenCode | `~/.config/opencode/opencode.jsonc` | `"xcodebuildmcp": { "type": "local", "command": ["xcodebuildmcp", "mcp"], "enabled": true }` |
| Codex | `~/.Codex/config.toml` | `[mcp_servers.xcodebuildmcp]` + `command = "xcodebuildmcp"`, `args = ["mcp"]` |
| Claude Code | `~/.claude.json` | `"xcodebuildmcp": { "command": "xcodebuildmcp", "args": ["mcp"] }` |

В Codex у владельца уже лежит и вариант через zsh
(`/bin/zsh -lc "xcodebuildmcp mcp"`) — годится, если PATH в неинтерактивной
среде не подхватывается. После правки конфига **перезапустить сессию**: сервер
поднимается при старте, на живую он не появится. Признак успеха — в каталоге
инструментов есть `xcodebuildmcp` (44 инструмента: `build_run_sim`,
`list_sims`, `screenshot`, `snapshot_ui`, `tap`, `wait_for_ui`).

Первое, что сделать в новой сессии, — проверить дефолты:

```text
session_show_defaults
```

Пусто или чужой проект — записать свои значения (иначе MCP соберёт не то):

```text
session_set_defaults {
  projectPath: "/Users/max/Проекты/TaskFlowNativeBuild/TaskFlow.xcodeproj",
  scheme: "TaskFlow",
  simulatorName: "iPhone Air",
  simulatorId: "9FF78D89-EE84-4914-AA56-D0A72D1AF43A",
  derivedDataPath: "/Users/max/Проекты/TaskFlowNativeBuild/build_sim",
  bundleId: "com.maksim.taskflow.native"
}
```

`bundleId` обязателен для `launch_app_sim`, без него запуск падает с
`MISSING_REQUIRED_PARAMETERS`. Дальше рабочий цикл: `build_run_sim` (сборка +
установка + запуск), `wait_for_ui` по тексту (например «Статистика») → `tap`,
`screenshot` — кадр лежит путём из `artifacts.screenshotPath`. Столбики
графиков и другие нарисованные элементы в дерево доступности не попадают:
по ним тап невозможен, такие вещи проверяет владелец пальцем.

**Заголовки одного уровня сверяются внутри экрана.** Допустимый шрифт сам
по себе не означает соответствие соседним разделам. Для составных экранов
регистрировать группы заголовков в `Tools/screen-heading-scopes.json`:
экран, уровень, файл, тип и функция/свойство контейнера раздела. Первый
`Text`/`SettingsCapsLabel` контейнера считается его заголовком. Включать
вложенные компоненты другого файла в ту же группу. При добавлении раздела
дополнять группу; если нужный шаблон сторож не распознаёт — расширить его
с регрессионным тестом, не объявлять проверку выполненной. Группы разных
экранов не сравниваются. Режим `--fragment` без файла не проверяет это
правило; использовать `--new-file`, `--paths`, `--diff` или сборку.

### 6. Запуск в симуляторе

Вход без экрана логина — токен не нужен: в домашней сети приложение входит
само (`POST /auth/lan` при старте без токена, дальше токен лежит в Keychain):

```bash
SIMCTL_CHILD_TASKFLOW_DEBUG_ROUTE=today xcrun simctl launch <UDID> com.maksim.taskflow.native
```

Ключа `TASKFLOW_AGENT_TOKEN` в vault нет — снят намеренно; не искать и не
подменять другим токеном.
`TASKFLOW_DEBUG_ROUTE` открывает экран сразу: `overview`, `settings`,
`notes`, `projects`, `notifications`, `chat`, `today`, `upcoming`,
`noteeditor:<id>`, `task:<id>`, `expand`, `quickadd`. Booted-симуляторов
несколько — UDID указывать явно (`list_sims`). Готово, когда нужный экран
открыт с данными.

### 7. Проверка

## UI-проверки: скриншот по умолчанию, UI-тесты только с согласия владельца

**Прямое указание Максима от 24.10.2026. Действует для всех агентов, включая Codex.**

- По умолчанию собрать приложение, открыть нужный экран, снять скриншот и проверить заявленный элемент. Не запускать обход соседних экранов.
- Самостоятельно не писать, не менять и не запускать UI-тесты, включая временные XCUITest, существующие UI-наборы, тесты на iPhone и навигацию через тест ради скриншота.
- В крайнем случае можно предложить владельцу один конкретный UI-тест и объяснить, что он проверит и почему кадра недостаточно. Выполнять только после явного согласия на этот тест. Молчание и общее поручение «сделай/исправь» согласием не являются.
- Сложность задачи, критичный баг, новая функция, правила навыка и «полный цикл» не отменяют это требование. Старое исключение «Codex может автоматически» отменено.
- Экран открывать через `TASKFLOW_DEBUG_ROUTE` или обычные инструменты навигации по accessibility. Если кадр недоступен, сообщить причину; не подменять его самовольным UI-тестом.
- Это правило касается UI-тестов. Целевые unit-тесты логики остаются отдельной проверкой; нельзя обходить запрет, называя UI-тест unit-тестом, smoke или screenshot-тестом.

#### Обычный цикл проверки интерфейса

1. До сборки выполнить сторож дизайн-системы по правке (шаг 5).
2. Один раз собрать актуальное приложение. Не пересобирать без новой правки или конкретной ошибки сборки.
3. Открыть только нужный экран через `TASKFLOW_DEBUG_ROUTE` либо инструменты accessibility, без написания UI-теста. Указывать конкретный UDID; не выдумывать координаты по retina-кадру.
4. Снять скриншот через XcodeBuildMCP `screenshot` или `xcrun simctl io <UDID> screenshot <файл>`. Проверить, что нужный элемент есть, расположен по поручению и экран не показывает ошибку.
5. Сохранить кадр и короткий итог в `docs/`. Проверку кадром не выдавать за проверку всей логики, API или физического устройства.

Никаких автоматических UI-наборов, физических прогонов, метрик и повторных обходов «на всякий случай». Установка на iPhone — по отдельному поручению; она не означает согласие на UI-тест.

#### Unit-тесты логики и экономия запусков

Правка цикла, инварианта, разбора данных, сортировки или кэша сначала получает целевой unit-тест: он должен падать до правки и проходить после. Декоративные изменения и прямые локальные UI-действия проверяются сборкой и кадром. Полный набор не запускать без необходимости или прямого поручения владельца.

Сборка — отдельный шаг. Тесты запускать по актуальным готовым продуктам (`test-without-building`), без повторной сборки неизменного приложения. Если изменился исходник или тест, один раз обновить соответствующие продукты; не делать clean/rebuild без причины.

Долгие команды выполнять в фоне или асинхронным MCP-вызовом. Между долгими шагами сообщать владельцу, что запущено. Не использовать `sleep N` для ожидания сборки/теста: ждать событие завершения, маркер `EXIT=` или конкретное состояние экрана. Пауза на анимацию допустима до 3–4 секунд.

Ошибка инфраструктуры не является поводом многократно чинить тест и повторять прогон. Зафиксировать блокер и сообщить владельцу.

#### Если владелец явно разрешил конкретный UI-тест

Этот раздел применяется только после явного согласия. Сначала назвать цель теста, платформу и способ проверки. Не расширять одобренный сценарий на соседние экраны или другой набор.

- Искать элементы по `accessibilityIdentifier`/label, не по выдуманным координатам.
- Использовать актуальные готовые тестовые продукты; сборка отдельно, запуск через `test-without-building`.
- Не больше двух прогонов одобренного сценария. Если второй не прошёл — остановиться и сообщить результат, не запускать третий.
- Не передавать `-resultBundlePath` в обычном прогоне: известен случай зависания после `TEST SUCCEEDED`. Если bundle нужен по согласованной проверке, после итоговой строки контролировать завершение процесса.
- Не менять боевые данные ради UI-проверки. Фикстуру не выдавать за проверку живого сервиса.
- Физический iPhone, метрики плавности и дополнительный набор требуют соответствующего явного поручения. Скриншот симулятора не объявлять проверкой устройства.
- Сохранить только согласованные доказательства. Временный тест после проверки удалить, выполнить `xcodegen generate` и вернуть обычный запуск приложения.

Критичные изменения логики/API/синхронизации требуют соответствующих целевых проверок и честного отчёта об ограничениях. Они не дают агенту права самостоятельно добавлять или запускать UI-тесты.

### 9. Установка на телефон и обычный запуск

Для отдельного поручения установить приложение использовать скрипт ниже.
Установка не означает разрешение на UI-тесты: для них всегда нужно отдельное явное согласие владельца. По умолчанию интерфейс проверяется кадром по шагу 7.

```bash
cd ~/Проекты/TaskFlowNativeBuild && ./install-iphone.sh
```

Скрипт сам пересобирает, подписывает (`-allowProvisioningUpdates`) и ставит
на iPhone владельца (UDID зашит в скрипте). Бесплатная подпись
живёт 7 дней. Тот же скрипт запускает кнопка «Задачник» в пульте .110
(служба InfraPanelInstaller на маке).
