# Цикл работы агента с iOS-клиентом TaskFlow

Полный путь прямой работы по нативному клиенту: от поручения до телефона. Читать
целиком перед первой правкой; детали правил — в файлах, на которые здесь
ссылки, а не здесь.

## Откуда ты работаешь

**С мака** (сессия запущена в каталоге репозитория) — команды напрямую.

**С .110** (Claude Code, Гермес, Codex и др.) — всё идёт через ssh на мак.
Инструменты Homebrew видны только в логин-шелле, поэтому команды
оборачиваются в `zsh -lc`:

```bash
ssh max@MacBook-Pro-Maksim.local "zsh -lc 'cd ~/Проекты/TaskFlowNativeBuild && git status -sb'"
```

У Claude Code на .110 есть MCP `XcodeBuildMCP` — он сам ходит на мак по ssh
(`max@MacBook-Pro-Maksim.local`, `xcodebuildmcp mcp`) и даёт сборку,
симулятор, UI-автоматизацию и отладку. Конфиг его возможностей —
`.xcodebuildmcp/config.yaml` в репозитории.

Копия репозитория на .110 или где-либо ещё — источник потерянной работы
(прецеденты 02.09 и 08.09.2026). Код живёт в одном каталоге на маке и
переносится только через git.

## Цикл

### 1. Поручение владельца

Этот цикл относится к внешнему агенту, который напрямую меняет нативный
клиент. Для такой работы не создавать учётные карточки и командные планы
в TaskFlow, не выполнять `taskflow_claim` и `taskflow_heartbeat`. Учёт
работы — в `AGENT-WORK-SCOPES.md`, результат — в `docs/`. Карточки
TaskFlow предназначены для выполнения внутренними ролями. Создавать
или запускать их только по отдельному поручению владельца. Инструкции
и жизненный цикл внутренних ролей этим файлом не регулируются.

Если владелец поручил поставить задачу внутренней команде TaskFlow,
в постановке работы с кодом обязательно проверить структурированное
поле «Ответственный за интеграцию». Автоматический выбор из команды:
оркестратор → архитектор → единственный исполнитель; если исполнителей
несколько — назвать конкретного участника. Для задач без правок репозитория
явно «Не требуется». Наличие рабочей ветки не означает перенос в main:
названный участник доводит принятые изменения до основной ветки. Сервер
проверяет назначение при запуске команды для всех источников создания,
не при сдаче разработчика или ревью. Не придумывать дополнительные барьеры.

Пояснения неочевидных полей прятать за небольшим неброским знаком «?»
рядом с названием. Постоянный текст подсказок в форме не показывать;
ошибку незаполненного обязательного поля показывать при попытке запуска.


### 2. Граница правки

Открой `AGENT-WORK-SCOPES.md` и заведи строку `IN_PROGRESS`: Lock ID, что
чиним, точный список разрешённых файлов, как проверим. Менять можно только
файлы из этой строки; смежную проблему — назвать владельцу и ждать ответа.
Готово, когда строка записана и в ней перечислен каждый файл, который
собираешься трогать.

### 3. Найти код

Сначала граф, потом поиск руками:

```bash
ssh max@MacBook-Pro-Maksim.local "zsh -lc 'cd ~/Проекты/TaskFlowNativeBuild && ~/.local/graft/node_modules/.bin/graft ask \"task detail screen\"'"
```

Спрашивать английскими словами и именами типов: русский запрос «экран
карточки задачи» вернул пусто, английский — `TaskFormScreen.swift`. Пусто — `graft grep
"<литерал>"`, `graft callers <символ>`. Найденное сверь по исходнику: граф
может отстать. Готово, когда открыт настоящий файл экрана, а не заглушка.

### 4. Правка

- С мака — обычными инструментами редактора.
- С .110 — точечно по ssh: прочитать `ssh max@… 'cat ~/Проекты/TaskFlowNativeBuild/<файл>'`,
  записать через heredoc или скрипт замены на маке. Удобнее редактировать
  локально — можно вытащить ОДИН файл в `/tmp` на .110, поправить, вернуть
  `scp` на то же место и сразу удалить временный файл. Каталогами (`rsync`,
  `scp -r`) в репозиторий ничего не заливать.
- Добавил или удалил файл — обязательно `xcodegen generate`, иначе он не
  попадёт в проект. Ассеты прописываются в `sources` в `project.yml`.

Готово, когда изменены только файлы из строки реестра (`git status -s`).

### 5. Проверки логики без симулятора

**Прямое указание Максима от 25.10.2026. Действует для всех агентов и заменяет прежнее требование кадра в симуляторе.**

- Из обязательного цикла исключены сборка под симулятор, его запуск/открытие, установка и запуск приложения в нём, UI-навигация, скриншоты, видео, визуальные проверки и UI-тесты.
- Не трогать симулятор по своей инициативе, включая запуск unit-тестов через iOS Simulator. Общее поручение «сделай», «исправь», «проверь» и требования навыков разрешением не являются. Только отдельное прямое поручение владельца на конкретную проверку позволяет использовать симулятор.
- По умолчанию проверять только логику: целевые unit-тесты без симулятора и подходящие статические проверки. Для исправлений логики сохраняется требование RED → GREEN. Если существующий тест требует симулятор, назвать ограничение; не запускать его автоматически и не считать пройденным.
- Для декоративных правок не придумывать тесты, проверяющие текст исходника. Просмотреть diff; сторож дизайн-системы выполнять при изменении Sources по правилам проекта.
- Прохождение проверки логики или сборки не означает, что интерфейс понравился владельцу. Внешний вид оценивает владелец; без его оценки не заявлять визуальную приёмку.
- Не писать, не менять и не запускать UI-тесты без отдельного явного согласия на конкретный тест. Установка на iPhone — только по отдельному поручению и не разрешает UI-тесты.

Изменение цикла, инварианта, разбора данных, сортировки или кэша сначала получает целевой unit-тест: прогон на коде до правки должен падать, после правки — проходить. Использовать доступный тестовый контур без симулятора. Не объявлять статический поиск по исходнику эквивалентом поведенческого unit-теста. Полный набор не запускать без необходимости.

При изменениях Sources выполнять сторож дизайн-системы:

```bash
python3 Tools/design-system-guard.py --diff HEAD
```

Исправить новые нарушения либо оформить согласованное исключение. Для изменений только документации сторож не нужен. Заголовки одного уровня проверяются внутри экрана через Tools/screen-heading-scopes.json; допустимый шрифт сам по себе не означает соответствие соседним заголовкам.

Сборка и проверки интерфейса не являются обязательным условием сдачи. Если владелец отдельно поручает сборку или конкретную проверку на устройстве/симуляторе, выполнять только это поручение, соблюдать его границы и сообщать фактический результат. Сборку не выдавать за визуальную приёмку. UI-тесты требуют отдельного согласия на конкретный тест.

Долгие целевые проверки логики выполнять в фоне или асинхронным вызовом. Не повторять инфраструктурно сломанные прогоны по кругу; назвать блокер. Не делать clean/rebuild без конкретной причины.

### 6. Отчёт и коммит

- Отчёт `docs/ГГГГ-ММ-ДД-<тема>.md`: что изменено, какие проверки логики выполнены и их ограничения. Кадры не требуются.
- Строку реестра перевести в `REVIEW`, описать сделанное; сделанное сверх
  задачи назвать отдельно.
- Коммит в `main` на маке, отдельный на каждую независимую правку; мусор
  (пустые файлы, `.detach_logs/`, `.superpowers/…`) не добавлять.
- Push — по просьбе владельца. Remotes: `origin` и `github` — GitHub
  `papirosa3214/TaskFlowNativeBuild`, `gitea` — Gitea на .110
  `maksim/taskflow-native-ios` (ssh-алиас `gitea` есть только на маке).

Готово, когда собственные изменения закоммичены, строка в `REVIEW`,
отчёт сохранён в `docs/`. Чужие изменения сохранять.

### 7. Установка на телефон — только по отдельному поручению

Для отдельного поручения установить приложение использовать скрипт ниже.
Установка не означает разрешение на UI-тесты: для них всегда нужно отдельное явное согласие владельца. Визуальная приёмка остаётся за владельцем; симулятор и кадры не входят в обязательный цикл.

```bash
cd ~/Проекты/TaskFlowNativeBuild && ./install-iphone.sh
```

Скрипт сам пересобирает, подписывает (`-allowProvisioningUpdates`) и ставит
на iPhone владельца (UDID зашит в скрипте). Бесплатная подпись
живёт 7 дней. Тот же скрипт запускает кнопка «Задачник» в пульте .110
(служба InfraPanelInstaller на маке).
