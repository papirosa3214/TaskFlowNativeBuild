# Входящие: обращения к владельцу

30.10.2026. Проект поведения для реализации; код ещё не изменён.

## Поручение и принятое решение

Владелец хочет отдельные лаконичные карточки, похожие по сдержанности на «Все задачи» в проектах, но просторнее и с содержанием обращения. На вопрос о составе ответил: «Да, только вопросы, разрешения и решения». Обычные задачи «В работе» из входящих исключаются. Статус задачи сам по себе не является входящим обращением.

## Вид тикета

Одна колонка карточек на фоне экрана; существующие цвета, типографика, отступы и радиусы TaskFlow. Без декоративных перфораций, градиентов и вложенных карточек. Доступный размер текста, перенос длинного вопроса, понятные подписи действий для VoiceOver.

Содержимое по порядку:

1. Агент и тип обращения: «Вопрос», «Согласование», «Решение».
2. Конкретный вопрос или решение, которое требуется от владельца; это основной текст карточки.
3. Связанная задача/проект или чат и время ожидания.
4. Действие с понятной подписью: «Ответить», «Рассмотреть изменение», «Открыть задачу». Действие соответствует существующему механизму, а не просто меняет локальный флажок.

Пример структуры, демонстрационные данные:

> Лайф-тестировщик · Решение
>
> Достигнут лимит доработок. Продолжить исправления или остановить работу?
>
> Чат инфра-панели · TaskFlow
>
> Открыть задачу →

Открытие тикета не означает согласия. Разрешение или запуск происходят только после явного действия в соответствующем контексте.

## Что проверено в текущем коде

- `Sources/Features/Attention/AttentionScreen.swift` рисует обычные строки задач из групп blocked/in_progress/review.
- `Sources/Core/Models/AttentionFeed.swift` моделирует эти группы, а не отдельные обращения.
- `.110: server/src/routes/attention.ts` выбирает задачи по статусу самой задачи или незакрытого шага. Вопрос без такого статуса не попадает в ответ.
- `.110: server/src/lib/chatQuestions.ts` и миграция 180: вопросы чатов имеют устойчивый ID и статусы open/answered/expired/cancelled.
- `.110: server/src/runtime/planMutations.ts`: предложения изменений плана имеют собственное состояние; уведомление plan_approval_request — только сообщение, не источник истины о незакрытом обращении.
- `.110: server/src/runtime/planReviewLifecycle.ts`: исчерпание доработок выставляет blocked с явной причиной о решении владельца.
- `.110: server/src/runtime/coordinationResolver.ts`: различает waiting_owner, permission_or_owner и ожидание других исполнителей. Не всякая блокировка требует владельца.
- iOS уже имеет `RoleQuestionCard` и API ответа на вопрос чата; не нужно создавать второй канал ответа.

## Источники и жизненный цикл

| Источник | Условие показа | Действие | Когда убрать |
| --- | --- | --- | --- |
| Вопрос чата | Открыт, не просрочен, чат доступен владельцу | Ответить через существующий API | answered/expired/cancelled |
| Уточнение подготовки задачи | Требуется уточнение, есть актуальный вопрос | Открыть задачу и существующую форму ответа | Уточнение снято |
| Предложение изменения плана | Ожидает решения, относится к действующему плану | Рассмотреть в контексте плана | Принято/отклонено/устарело |
| Ожидание решения владельца | Незавершённая задача/шаг, актуальная явная причина ожидания владельца | Открыть задачу с причиной | Ожидание снято |
| Черновик плана | Требуется утверждение владельца перед запуском | Рассмотреть план | Утверждён/заменён/отклонён |

Не добавлять обычную работу, ожидание предшественника, старые уведомления, закрытые/архивные задачи и любые фразы из истории, уже утратившие актуальность. Не выдавать текстовую догадку за структурированное разрешение. Если агент просто написал «на усмотрение владельца» и продолжил работу, надёжно определить незакрытое обращение по этой фразе нельзя: для гарантии потребуется явная регистрация обращения в инструментах агента.

Каждое обращение имеет устойчивую идентичность источника, например question:<id> или plan-op:<id>. Два вопроса в одной задаче — разные тикеты. Одно обращение, пришедшее из нескольких каналов, не должно дублироваться. Текст показывается из текущего источника, а не генерируется моделью при каждом обновлении.

Точная сортировка — новые обращения сверху; время относится к созданию обращения, не к любому обновлению задачи. Пустое состояние: «Нет обращений — агенты не ждут вашего ответа или решения». Ошибка загрузки не подменяется пустым состоянием. После возврата с ответа список обновляется.

## Подходы

1. Только оформление текущих трёх статусов: быстро, но не устраняет пропуски запросов. Не соответствует выбранному владельцем составу.
2. Серверная проекция открытых обращений плюс нативные карточки и существующие формы действий. Рекомендованный подход; выбранный состав подтверждён владельцем.
3. Новая универсальная система сообщений и разрешений с миграцией всех агентов: шире первого изменения; не нужна для отображения уже структурированных источников.

## Границы реализации

iOS и общий сервер API на .110. Замороженный веб-клиент не менять. Сохранить совместимость клиента с прежним сервером: отсутствие новой проекции не должно выдавать все старые статусы за актуальные обращения. Новые поля необязательные; при старом сервере явно сообщать об отсутствии поддержки.

Права чтения каждого чата и задачи проверяет сервер. Просмотр входящих не изменяет состояния задач, разрешения, планы и сообщения. Обработка кнопок использует существующую авторизацию и повторно проверяет актуальность запроса.

Добавить подсказку про тикеты и место ответа. Не менять общую типографику RoleReplyMarkdown. Не затрагивать текущие чужие правки рутин и формы задачи.

## Проверки и приёмка

- Серверные целевые unit/integration тесты: открытый вопрос виден без blocked; закрытый исчезает; два запроса не схлопываются по task_id; ожидание другой роли не появляется; устаревшее предложение исключается; недоступные чаты и задачи не раскрываются.
- Новый тест должен падать на старом коде и проходить после правки. Серверные тесты только с --maxWorkers=4; без полного набора.
- iOS: host XCTest для разбора контракта и маршрута действия; проверка сценария подсказки; Swift parse и design-system guard.
- Без симулятора, браузера, UI-тестов и установки на iPhone. Вид принимает владелец.
- Приёмка владельцем: агент задаёт вопрос → появляется тикет → владелец отвечает → ответ получает агент → тикет исчезает. Разрешение аналогично, без автоматического согласия от открытия карточки.
