# Согласование живого ответа и истории сессий

14.11.2026. Поручение владельца по исследованию Pi; затем отдельное
поручение проверить в симуляторе с соблюдением ограничений сборки.

## Изменения

- Каждая готовая реплика хранит свои текст, серверные блоки и идентичность
  (entryId, иначе курсор). Один слот lastEventReply удалён.
- История берёт блоки из SessionReply. Живой рендер сессии требует область
  хода; без неё не читает общий реестр по совпавшему тексту. Комнаты ролей
  и общий рендерер не менялись.
- Снимок декодирует session.live. Начальный мост используется только для
  текущего стримящегося ответа; уже показанный текст не заменяется снимком.
  На reset мост не ставится поверх очереди событий, пришедшей в полёте,
  и событий смены сообщения.
- message_end без блоков больше не теряет финальный хвост: обычный текст
  показывается существующим fallback, без локального разбора.
- Напечатанный ход сохраняется после settle и не дублируется историей.
  Безусловный сброс сохранённого хода без live из исследовательского плана
  не применён: он противоречит закреплённым правкам владельца 14.11 о
  сохранении показанного ответа при потере головы. Дыра остаётся явно
  известной и закрывается авторитетным финалом/снимком.
- На сервере отдельно опубликован d0ff7a28: одновременные повторы одного
  requestId разделяют один Promise. Память не переживает рестарт и
  вытеснение ключа; строгой долговременной идемпотентности не заявляем.

### Результат ручной проверки

Создана отдельная сессия 01a1db1f-dbbb-7550-badc-30adb03d5a0b.
Первый запрос: три разных абзаца и таблица. Второй: SECOND RESPONSE COMPLETE.
Во время первого хода выполнен выход к списку и повторное открытие.
После завершения и перезапуска приложения оба ответа сохранены отдельно.

Первый проход выявил настоящую ошибку: таблица была видна, три текстовых
блока — заглушками. Исправление сервера c2d4230f добавляет text_blocks
внутрь JSON-конверта через существующий jsonWithTextBlocks копии сессий.
После выкладки и повторного входа все три абзаца видны без заглушек.
Маркер исходного ввода частично искажал драйвер AXe (US keyboard only,
залипший Shift); это не дефект доставки TaskFlow. Второе сообщение введено
без искажений и отрисовано отдельно.

По замечанию владельца JSON-таблицы сессий подключены к ChatTableView:
согласованная тёмно-красная шапка и красные разделители вместо серой
таблицы документа. Параметр включён только у SessionReplyMarkdown;
по умолчанию общие виды сохраняют поведение комнаты роли.
RoleReplyMarkdown.readableText и типографика ответа не менялись.
Это отображение готовых данных, без переноса разбора Markdown на телефон.

Сборки: одна за раз, один DerivedData Xcode, -jobs 2, без clean:
1. Основное исправление: 20:26:12–20:29:37, 3 мин 25 с, BUILD SUCCEEDED.
2. Согласованная таблица: 20:40:15–20:42:08, 1 мин 53 с, BUILD SUCCEEDED.

Команда обеих:
xcodebuild -project TaskFlow.xcodeproj -scheme TaskFlow -configuration Debug
-destination id=9FF78D89-EE84-4914-AA56-D0A72D1AF43A -jobs 2 build

Свежая сборка установлена именно на этот UDID; в финальном кадре видны
три абзаца, красная таблица и отдельный второй ответ. Ручной визуальный
проход не является доказательством всех сценариев длительного обрыва,
вытеснения буфера или переключения эпохи сервера.

### Первичные наблюдения по очередям ролей (только чтение)

По отдельному поручению владельца 14.11:
chat_queue_defer_enabled=false (изменено владельцем в 16:54:12 UTC),
chat_delivery_journal_enabled=true. Отложенных chat_queued_messages=0.
В chat_message_queue на момент чтения только терминальные done, failed,
superseded; фактического ожидающего backlog нет.

Очередь отложенных сообщений и журнал надёжной доставки — разные механизмы.
Первый откладывает новый ввод до конца хода и уже выключен.
Второй защищает передачу от потери при рестарте и повторов, но его настройка
сцепляет надёжность и показ плашек в ленте. Чтобы убрать технический шум,
не следует выключать защиту доставки: видимость штатных статусов нужно
отделить от работы журнала. Настройки и код ролей в этой работе не менялись.
