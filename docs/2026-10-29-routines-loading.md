## Путь загрузки и причина лишнего ожидания

`OverviewScreen` отдельно читает `/schedules` для счётчика активных рутин.
При открытии `RoutinesScreen` создаётся собственная модель и `.task` вызывает
`load()`; pull-to-refresh также вызывает `load()`. Первое открытие раньше
последовательно ожидало `api.roles()`, затем `api.schedules()`.
Каталог ролей нужен только для имени исполнителя, модель уже умеет показывать
ключ роли до получения имени. Теперь сначала запрашиваются рутины, публикуются
список или ошибка и снимается `isLoading`, затем загружаются подписи ролей.
Ожидание каталога больше не блокирует содержимое. Общая длительность `load()`
всё ещё включает каталог (в том числе завершение жеста refresh).

`APIClient.roles()` использует общий RolesCache: TTL 30 секунд и склейку
одновременных запросов. Если кэш свежий, устранённое ожидание было малым.
`APIClient.request` сохраняет GET в ResponseCache, но модель рутин не читает его;
поэтому повторное открытие снова ждёт свежий `/schedules`. Это отдельный выбор
политики свежести: предлагается при необходимости показывать прошлый ответ
с последующим обновлением; в этой работе кэширование не менялось.
В обычном `send` нет собственного цикла повторов: один URLSession.data(for:).

Сервер изучен напрямую через SSH .110: `/api/schedules` после авторизации
выполняет `listSchedules().map(present)`; store — один SQLite SELECT по
`task_schedules`, без запросов к внешней модели/сервисам. Сервер не изменён.
В журнале сервиса за 06:35–06:45 нет длительностей нужных запросов. Фактическую
server latency и вклад сети телефона установить по этим данным нельзя.
В APIClient уже есть debug-лог длительности HTTP; следующий шаг для точного
замера — сопоставить `/api/roles` и `/api/schedules` в логе реального открытия.
Ускорение на телефоне не измерялось и не заявляется.
