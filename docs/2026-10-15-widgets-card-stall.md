## Выявленные недочёты

### 1. Задание ссылалось на место, куда роль не может попасть
Готовая работа лежала **только** на маке, в отдельной копии `~/Проекты/TaskFlowDeveloper`
(ветка `codex/developer-mac`, не запушена в main). Роли запускает сервер на .110 — путь
`~/Проекты/...` на маке для них не существует. Ни аналитик, ни оркестратор, ни решение
владельца этого не учли: всем троим путь казался доступным.

**Не хватило:** доступа роли к файловой системе мака (или правила «код передаётся только через git»).

### 2. Вторая копия клиента на маке живёт отдельно от main
`TaskFlowDeveloper` — клон зеркала со своей веткой; ночной коммит с виджетами (03:21)
так и не попал в main, а в той копии ещё и висят несохранённые правки тех же файлов.
Это ровно та ситуация, которую `CLAUDE.md` запрещает для .110 («код переносится только через git»),
но для второй копии на маке такого правила нет.

### 3. Исчерпанные попытки не переводят шаг в blocked
После «2 из 2» шаг остался `in_progress` с протухшим heartbeat. Снаружи — «агент пропал».
`taskflow-stall-check` раз в 10 минут видел шаг без пульса, но только шлёт сводку — сам ничего не делает.

**Не хватило:** автоматического перехода в `blocked` с причиной «попытки исчерпаны» и адресного сигнала владельцу/оркестратору.

### 4. Зависший запуск навсегда держит блокировку слота (дефект сервера)
`inProcessRun.ts:1201–1204`: блокировка `acquireSlotSession` отпускается только по
`result.completion`. Когда поток модели «остановился», `completion` так и не разрешился —
запуск убран из `activeRuns`, но блокировка в памяти осталась. Поэтому:
- `/api/subtasks/:id/reset` — проходит (чистит БД), но блокировку не трогает;
- `/api/subtasks/:id/restart` — ждёт 15 с и отвечает «Сессия слота занята»;
- `/api/subtasks/:id/cancel` — не поможет: живого run в `activeRuns` уже нет.

Снять можно только перезапуском процесса сервера.

**Не хватило:** таймаута/принудительного release у блокировки и ручки «освободить слот» для владельца/оркестратора.

### 4а. Живой сервер работал в обход systemd (главная находка)
На :3001 сидел процесс `node dist/index.js`, запущенный в 21:34 через `nohup` из ssh-сессии,
а не сервис `taskflow-server`. Сервис systemd при этом числился `active`, но порт занять не мог.
Поэтому `systemctl --user restart taskflow-server` ничего не лечил: перезапускался не тот процесс,
блокировка жила дальше. Помогло только остановить посторонний процесс и перезапустить сервис —
после этого `/restart` шага delivery прошёл с первого раза (`inproc_e81b2691…`, 22:35 МСК).

**Не хватало:** сторожа «порт :3001 принадлежит MainPID сервиса», запрета на ручной `nohup` сервера.

### 5. Оркестратор (роль) не мог ничего сделать сам
`role_code_orchestrator` правильно диагностировал «брошен», но у него нет ни доступа к маку,
ни инструмента перезапуска слота, который работал бы при висящей блокировке. Он только писал комментарии в пустоту.

### 6. Внешний отладчик был запрещён собственной инструкцией
Глобальный `CLAUDE.md` §5.1 запрещал Claude Code даже читать трекер без прямого слова владельца —
хотя учётка оркестратора для этого и создавалась. Исправлено сегодня: чтение — всегда, запись — по слову владельца.
Автоматический фильтр разрешений Claude Code отдельно блокировал запись в API до явного «разрешаю» в чате.

### 7. Дубли шагов в карточке
Помощник владельца завёл три ручных шага («Разведка», «Разработчик», «Критик») без исполнителей,
а план совместной работы создал свои три слота. Ручные шаги висят открытыми и путают картину.

### 8. Мусор в рабочем репозитории
В `TaskFlowNativeBuild` брошены несохранённые «Удалённые машины» (без строки в реестре) и папка `</`
(ошибочный путь `</Users/max/Library/...`). Чей — не установлено.
