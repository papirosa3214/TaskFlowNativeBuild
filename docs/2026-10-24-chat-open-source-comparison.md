# Как готовые системы решают чат с работающим агентом

24.10.2026. Сравнение документации и исходников, без установки новых систем и запуска моделей. Рекомендации — инженерный вывод, не подтверждение совместимости с TaskFlow без интеграционных тестов. Ссылки main отражают состояние на дату исследования и могут изменяться.

## Что сравнивается

Два сценария владельца: обычный чат, где уточнение должно менять дальнейшую работу, и карточка, где отдельное обсуждение завершается передачей согласованного итога работающему исполнителю. Дополнительно: порядок сообщений/действий, остановка, ветки, восстановление, сжатие контекста. Нативный SwiftUI-интерфейс остаётся самостоятельным клиентом.

## 1. Pi — ближайшая база, уже установленная в TaskFlow

На .110 проверена установленная версия `@earendil-works/pi-coding-agent`: **0.84.4**. В её declarations есть `steer`, `followUp`, `abort`, `compact`, `navigateTree`; у navigateTree есть summarize/customInstructions/replaceInstructions. Это подтверждено локальным пакетом, не только свежей документацией main.

Pi различает уточнение перед следующим запросом модели и сообщение после окончания текущей работы. `steer` в установленной версии ждёт окончания текущего assistant-turn с вызовами инструментов; это не немедленная отмена работающей команды. В актуальном SDK отдельно описаны abort и ожидание idle. [SDK](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/sdk.md).

Сессия — дерево. Навигация по дереву и создание отдельной fork-сессии различаются. При переходе с ветки можно сформировать её сводку для выбранного продолжения; compaction сжимает старую историю с сохранением недавней части. Для установленной версии доступна [документация v0.84.4](https://github.com/earendil-works/pi/blob/v0.84.4/packages/coding-agent/docs/compaction.md); актуальный пользовательский сценарий описан в [Sessions and Context](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/sessions.md).

**Для TaskFlow:** сначала использовать эти примитивы через один согласованный адаптер, вместо нескольких несвязанных способов доставки. Формат «что было / цель / что выполнить» можно задать политикой суммаризации. Перенос между двумя одновременно существующими сессиями остаётся явной операцией приложения: навигация внутри дерева сама по себе не равна доставке в отдельно работающий слот.

**Цена:** наименьшее изменение технологической основы. Однако управление рабочими процессами, квитанциями и журналом приложения не возникает автоматически от наличия SDK.

## 2. OpenHands — наиболее наглядный образец агента с событиями

В состоянии Conversation находятся EventLog, статус выполнения и лимит итераций; сообщения, действия и результаты представлены событиями. Это образец единого источника состояния вместо независимых history/live-массивов. [ConversationState](https://github.com/OpenHands/software-agent-sdk/blob/main/openhands-sdk/openhands/sdk/conversation/state.py).

В реализации явно различаются pause между шагами и interrupt асинхронного выполнения, в том числе текущего LLM-вызова. До отмены выставляется cancellation token, чтобы не стартовали ожидающие инструменты; синхронный путь может переходить к pause. Fork копирует разговор под новым ID и оставляет исходную историю отдельно. Эти возможности не означают автоматическую отмену любого внешнего эффекта или автоматическое слияние результатов двух разговоров. [LocalConversation](https://github.com/OpenHands/software-agent-sdk/blob/main/openhands-sdk/openhands/sdk/conversation/impl/local_conversation.py).

Отдельный condenser строит сокращённое представление событий для модели с сохранением защищённого начала и недавней части; границы сжатия учитывают структуру событий. [Condenser](https://github.com/OpenHands/software-agent-sdk/blob/main/openhands-sdk/openhands/sdk/context/condenser/llm_summarizing_condenser.py).

**Для TaskFlow:** брать за образец разделение журнала событий, состояния исполнения и контекста модели. Полный архив и краткий prompt — разные сущности. Заимствовать семантику состояний/отмены, не произвольные численные defaults. Перенос на Python-runtime потребовал бы существенно больше работы, поэтому замена Pi на OpenHands пока не обоснована.

## 3. LangGraph — явное состояние рабочего процесса

Работа представлена графом шагов. Checkpointer сохраняет состояние thread; interrupt останавливает выполнение в предусмотренной точке, а Command(resume) передаёт внешний ввод для продолжения. Это не команда принудительного убийства произвольного процесса. [Interrupts](https://docs.langchain.com/oss/javascript/langgraph/interrupts).

Можно создать ответвление от checkpoint с изменённым состоянием. При продолжении часть узлов выполняется повторно; внешние эффекты требуют защиты от дублей. Fork не является автоматически отдельной копией файлов и не сливает обсуждение с другой работающей задачей. [Time travel](https://docs.langchain.com/oss/javascript/langgraph/use-time-travel).

**Для TaskFlow:** полезный образец для карточного режима: хранить задачу, этап, договорённости и ожидаемое решение явно, а не извлекать всё из стенограммы. Закрытие обсуждения может записывать результат в состояние рабочего процесса, но этот конкретный переход проектирует приложение. Внедрять LangGraph целиком рядом с имеющимся графом карточек — риск получить два конкурирующих оркестратора. Сначала сравнить существующие сущности.

## 4. Vercel AI SDK — готовая механика чатовой ленты

UIMessage имеет ID и parts; пользовательское сообщение добавляется в массив сообщений, поток обновляет ответ по ID. В текущем chat.ts stop отменяет активный запрос, сохраняет полученный текст и ждёт завершения очереди обновлений; stopGeneration не даёт отложенным автоматическим запросам оживить остановленную работу. [Исходник chat.ts](https://github.com/vercel/ai/blob/main/packages/ai/src/ui/chat.ts).

Это решает сборку потокового сообщения и жизненный цикл клиентского запроса. Оно само по себе не определяет, где разрезать многошаговый ответ при новом сообщении, не отменяет удалённую сборку и не создаёт карточный процесс. Подходящий для обычного диалога контракт — остановить предыдущую генерацию, сохранить частичный ответ, добавить новое сообщение, начать новый ответ. Это предлагаемая политика TaskFlow, а не утверждение, что любая отправка в SDK автоматически так делает.

Возобновление потоков требует собственного хранения; документация отдельно предупреждает о несовместимости описанного resume-пути с abort. Поэтому обещать оба свойства без проверки конкретного транспорта нельзя. [Resume streams](https://ai-sdk.dev/docs/ai-sdk-ui/chatbot-resume-streams).

**Для TaskFlow:** использовать message/parts/ID и обработку поздних обновлений как образец. React-hook не переносится непосредственно в SwiftUI. Это источник проверенного подхода, а не основание добавлять веб-стек в iOS.

## Сопоставление

| Вопрос | Pi | OpenHands | LangGraph | Vercel AI SDK |
|---|---|---|---|---|
| Главная единица | Сессия и её дерево | Conversation, события и состояние | Thread и checkpoint графа | UIMessage и поток parts |
| Уточнение | Steer либо follow-up; отмена отдельно | Ввод + pause/interrupt | Ввод/изменение state + resume | Отправка/stop; политика прерывания задаётся приложением |
| Ветка | Дерево/fork; сводка при переходе | Fork разговора | Fork состояния checkpoint | Нужна логика приложения |
| Сжатие | Compaction и branch summary | Condenser | Организуется в приложении/графе | Нужен серверный контекстный слой |
| Основная польза нам | Уже имеющаяся база SDK | Устройство журнала и исполнения | Управляемые этапы карточки | Контракт потокового UI |

Таблица — обобщение проверенных выше механизмов, не список взаимозаменяемых продуктов.

## Что готовое, а что действительно остаётся нашим

**Готовые механизмы:** потоковые части, идентичность сообщений, события инструментов, жизненный цикл запроса, сессии, ветвление, краткий контекст, сохранение состояния.

**Правила TaskFlow:** какое сообщение останавливает обычный чат; кого адресует ветка карточки; продолжает ли исполнитель работу во время обсуждения; кто утверждает итог; когда итог считается доставленным; что делать, если исполнитель уже сменился. В проверенных источниках нет основания обещать готовую кнопку, которая обеспечивает все эти правила именно в вашей комбинации.

Сохранённое событие чата и событие, переданное в контекст модели, — разные факты. Сворачивание 56 действий в UI не должно уничтожать их порядок; сжатие prompt не должно переписывать историю владельца.

## Рекомендация

1. Оставить Pi основой, поскольку необходимые примитивы уже есть в 0.84.4. Проверить их через небольшие replay-сценарии; обновление пакета не является обязательным первым шагом.
2. Для обычного чата взять простой цикл: завершение/отмена прежнего вывода → сохранённый частичный ответ → новое сообщение → новый ответ. При требуемом свежем контексте использовать отдельную политику checkpoint, не объявлять её универсальным правилом всех чатов.
3. Для карточки сохранить отдельную рабочую сессию и отдельное обсуждение по снимку. Закрытие выпускает один явный итог с адресатом и квитанцией; не подмешивать каждую реплику автоматически, если выбран именно этот сценарий.
4. Использовать OpenHands как проверочный образец разделения событий и исполнения, Vercel — для потокового UI. LangGraph оставить альтернативой при доказанной необходимости менять оркестрацию, не подключать всё одновременно.
5. Переписать прежний план вокруг повторного использования SDK, двух явно разных режимов и тестов их границ. До проектирования нового журнала сопоставить возможности имеющихся session logs с требованиями приложения: новый слой может быть нужен, но дублировать уже решённое без проверки не следует.

Практический критерий выбора: один replay с уточнением в чате, второй — обсуждение карточки с передачей только итога. В обоих — восстановление сети, повтор сообщения, завершение/смена исполнителя и отсутствие двойных действий. Совместимость и гладкость интерфейса этим исследованием не измерялись.
