# Разговор с исполнителем задачи: фактический путь

24.10.2026. Аудит текущих исходников; продуктовая логика не изменялась. Состояние работающего сервиса и сценарий с настоящей моделью не проверялись. Предыдущий план единой хронологии НЕ считать готовым к применению к карточному режиму: сначала согласовать различия ниже.

## Схема владельца

Исполнитель работает над карточкой → создаётся отдельная ветка разговора → обсуждение в ветке → владелец закрывает разговор → итог обсуждения доставляется в существующий рабочий ход. Сообщения обсуждения не должны автоматически становиться рабочими указаниями по одному до закрытия.

## Найденные механизмы — это разные пути

| Механизм | Как открывается | Что происходит |
|---|---|---|
| Ручная ветка сообщения | iOS «Ответвление: обсудить в отдельном чате» → POST /api/chats/:id/branch | Новый чат, те же участники, копия исходного сообщения. Отдельная чатовая сессия |
| Автоматическая ветка-срез темы задачи | Сообщение владельца занятой роли в теме задачи, не ответ на сообщение роли и не уже существующая ветка | Создаётся ветка со снимком задачи, но исходное сообщение одновременно поступает в рабочий ход |
| Разговорный ход этапа | Сообщение адресовано этапу, а активный рабочий исполнитель отсутствует | startSlotConversation открывает сохранённую сессию этапа; не отдельную изолированную ветку |

В обычной личной комнате автоматическое создание веток выключено (`AUTO_BRANCH_ENABLED=false`). Это НЕ выключает отдельное условие `shouldFanOutTaskTopic` для темы задачи.

## 2. Создание ветки на сервере

Серверный исходник: `/home/maksim/Проекты/New-Todoist` на .110.

`server/src/routes/chats.ts`, POST `/api/chats/:id/branch`:

- проверяет участника и исходное сообщение;
- создаёт chats с branch_of_chat_id и branch_of_message_id;
- копирует участников и исходный текст;
- не копирует task_id, parent_chat_id, recipient_subtask_id и execution_mode.

Следствие по текущему `chatExecutionMode.ts`: такая ветка без явного выбора режима имеет обычный путь «В чате». Родство с задачей само по себе не направляет её в startSlotConversation и не устанавливает отдельный read-only контракт обсуждения.

`fanOutOwnerMessage` в тех же routes и `server/src/lib/chatOwnerFanout.ts`:

- topicSlice разрешён для владельца, темы задачи, занятой единственной роли, вне существующей ветки и без reply на роль;
- создаётся ветка и копия сообщения;
- первый ответ — snapshot: описание/шаги задачи и пять последних task_events;
- запускается dispatch для скопированного сообщения ветки;
- возвращается `!topicSlice`: для темы задачи false, поэтому dispatch исходного сообщения в основной теме НЕ отменяется.

Это архитектурно «правка в работу + параллельный разговор по срезу», а не «только разговор, затем передать итог».

## 3. Доставка исходного сообщения в карточный рабочий ход

`dispatchRoleReplies` разрешает слот, сохраняет durable delivery и вызывает deliverTopicToWork/deliverChatToWork для карточного режима.

`server/src/runtime/inProcessRun.ts`:

- один подходящий activeRun → текст сразу передаётся в `run.steer(...)` существующего исполнителя;
- ещё запускающийся этап → сообщение сохраняется в slot_topic_inbox;
- несколько подходящих запусков → busy/уточнение адресата;
- новый рабочий исполнитель только ради доставки сообщения не запускается;
- передаётся полный текст исходного сообщения с указанием ответить через taskflow_chat_reply и продолжить свой этап.

Поэтому до закрытия ветки исходная просьба уже может повлиять на работу. Сообщения самой обычной ветки по умолчанию обрабатываются её собственной чатовой сессией; это не тот же путь прямой карточной доставки.

## 4. Если рабочий этап не активен

`server/src/runtime/slotConversation.ts` и `slotSession.ts`:

- startSlotConversation берёт эксклюзивную сессию этапа;
- повторно проверяет, не начал ли работать исполнитель; если начал — пересылает сообщение ему, не создавая параллельного писателя;
- иначе openSlotSession открывает тот же сохранённый файл рабочего этапа;
- роль получает историю этапа, отвечает и сохраняет разговор в этой же сессии;
- инструкции требуют не возобновлять рабочие операции, но каталог инструментов discussion имеет широкие возможности; существующий тест прямо требует same tools as work. Текстовый запрет не следует выдавать за жёсткую техническую изоляцию.
- таймер обсуждения здесь явно `30*60*1000` (30 минут). Это конкретный серверный потолок этого пути; он НЕ доказывает происхождение замеченного владельцем timeout 1800 у иной операции.

Это разделение запуска работы и разговора, но НЕ изоляция контекста через отдельную ветку с финальным handoff.

## 5. Закрытие и формирование итога

POST `/api/chats/:id/close`:

1. Проверяет владельца, участие и тип комнаты; постоянную комнату закрыть нельзя.
2. Устанавливает closed_at.
3. Для ветки читает ТОЛЬКО сообщения `from_user_id LIKE 'role_%'`.
4. `branchSummaryLines` берёт первую содержательную строку каждого ответа, сокращает её до 60 символов, убирает повторы и оставляет последние пять строк.
5. В родительский чат вставляется системное сообщение «Ветка … закрыта. Итог: …» и рассылается chat:new.

Это НЕ смысловая суммаризация договорённостей. Сообщения владельца не входят напрямую в источник итога. Роли с другим форматом ID также не проходят указанный фильтр. В короткие первые строки может не попасть самое существенное решение.

Кроме закрытия есть `mirrorBranchResult`: при публикации сообщения роли через POST в родителя зеркалится первая содержательная строка ответа (до 120 символов). Существует и сводка ответивших веток. Ни одно из этих зеркалирований само по себе не является доставкой итогового контекста в activeRun.

## 6. Получает ли рабочий исполнитель итог закрытой ветки

В обработчике close после вставки системного сообщения НЕТ вызова:

- dispatchRoleReplies;
- deliverTopicToWork / deliverChatToWork;
- run.steer;
- recordDurableDelivery для созданного summaryId.

Следовательно, подтверждённый кодом результат закрытия — **сообщение в родительской ленте**, а не гарантированное немедленное включение итога в контекст текущего рабочего исполнителя. Позже он может прочитать тему или получить её в другом контексте, но это не квитанция доставки по закрытию.

Дополнительные риски самого close:

- повтор closed=true снова создаёт сводку, проверки alreadyClosed перед записью итога нет;
- закрытие и запись сводки не объединены в одну общую транзакцию;
- ошибка сводки ловится и логируется, а закрытый чат возвращается как успешный результат;
- обработчик close не отменяет активный ход ветки и не ждёт его окончательного ответа перед выборкой итога.

Это вывод по пути исходника; воспроизведение этих отказов отдельными новыми тестами в этой работе не выполнялось.

## 7. Уточнение к прежнему объяснению обычного чата

В текущем routes/chats.ts уже есть `interruptChatTurnForOwner`: для сообщения владельца вне темы/задачи вызывается cancelChatRunsFor для отвечающих ролей. Поэтому прежнее утверждение «в обычном чате есть только подмешивание» было неполным. Это ещё не доказывает надёжную остановку дочерних операций, новый checkpoint или требуемый порядок событий. При дальнейшем проектировании сначала учитывать реальную точку прерывания, а не добавлять её дубль.

## 9. Различия с требуемой схемой

| Требование владельца | Текущий результат |
|---|---|
| Отдельная ветка разговора | Есть ручная и автоматическая ветка-срез |
| Рабочий ход продолжает отдельную работу | Для активного этапа сохраняется, но исходное уточнение уже подмешивается до закрытия |
| Ветка знает рабочий контекст | Автоветка получает короткий snapshot; ручная — только исходное сообщение; slotConversation использует общий файл этапа |
| Промежуточная переписка не меняет рабочие указания до закрытия | В целом не обеспечено текущей схемой |
| Итог отражает договорённости | Сейчас обрезанные первые строки ответов ролей |
| Итог автоматически получает именно рабочий исполнитель | В close такого пути доставки нет |
| Повтор закрытия не дублирует handoff | Не обеспечено обработчиком close |
| Подтверждение доставки и безопасный retry | Для summaryId закрытой ветки не найдено |

## Границы и вывод

Механизм не исчез целиком. В коде одновременно живут ветка-срез, обычная ручная ветка, прямое подмешивание в работу и разговор на общей истории этапа. Их нельзя считать одной законченной процедурой «обсудили отдельно → закрыли → передали итог в работу».

Перед изменениями требуется разделить спецификации обычного чата и карточного обсуждения. В карточном пути проектировать отдельный явный handoff с адресатом taskId/subtaskId/run generation, полноценным итогом договорённостей, идемпотентной записью и квитанцией; решение о доставке исходного сообщения ДО закрытия должно быть согласовано явно. Это список предметов проектирования, не выполненные исправления.
