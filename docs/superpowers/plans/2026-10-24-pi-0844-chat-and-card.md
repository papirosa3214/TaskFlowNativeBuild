**Цель:** повторно использовать возможности установленного Pi, исправив связку сообщений, сессий и доставки в TaskFlow. Не менять SDK, провайдеров, движок карточек или SwiftUI-прокрутку без доказанной необходимости.

**Спецификация:** требования владельца из текущего разговора; фактический аудит [карточного пути](../../2026-10-24-task-discussion-current-path.md) и [сравнение готовых решений](../../2026-10-24-chat-open-source-comparison.md).

## Два независимых договора поведения

| Обычный чат | Карточка с работающим исполнителем |
|---|---|
| Новое адресованное сообщение владельца завершает старое направление | Открытие обсуждения не прерывает рабочий этап |
| Не начатые старые действия запрещаются; текущей операции отправляется доступная отмена | Обсуждение получает отдельную сессию и снимок контекста |
| Частичный ответ сохраняется над новым сообщением | Реплики обсуждения не подмешиваются в рабочий ход по одной |
| Продолжение — свежая сессия с выжимкой и новым сообщением | Закрытие выпускает один итог, который доставляется тому же этапу |
| Нет возврата к сырой прежней сессии при ошибке выжимки | Доставка итога не создаёт второго рабочего исполнителя |

Выбор определяет сохранённый режим и тип разговора, а не наличие занятой роли вообще. Ветка карточки получает явный тип discussion и адрес taskId/subtaskId/roleId. Обычное ручное ответвление чата не становится карточным обсуждением только из-за кнопки с похожим названием.

## Что точно есть в установленном пакете

Проверено по .d.ts и .js на .110 в `server/node_modules/@earendil-works/pi-coding-agent/dist/`; версия package.json — **0.84.4**. Это не перенос API из текущего main GitHub.

| API | Реальная семантика | Применение |
|---|---|---|
| `session.prompt(text, options?)` | При активном streaming нужен явно выбранный streamingBehavior | Начать новый чатовый/разговорный ход после готовности |
| `session.steer(text)` | Очередь после текущего assistant-turn и его инструментов, до следующего LLM-вызова; возвращает Promise<void> | Доставить утверждённый итог обсуждения в активную рабочую сессию |
| `session.followUp(text)` | После завершения текущей работы | Не использовать вместо срочного уточнения или квитанции доставки |
| `session.abort()` | abortRetry + agent.abort + ожидание idle | Остановить обычный чат; не считать доказательством завершения всех внешних процессов |
| `session.waitForIdle()` | Ожидание готовности без отмены | Завершение уже запрошенной остановки; не держать на нём POST сообщения |
| `session.compact(customInstructions?)` | Сжатие истории с сохранением недавнего хвоста | Управлять длинной сессией, но не выдавать за полное удаление reasoning |
| `SessionManager.create(cwd, sessionDir, options?)` | Новый менеджер с отдельной историей | Свежий чат после checkpoint и отдельное карточное обсуждение |
| `manager.getLeafId()/getBranch()/getEntries()` | Читать узлы SDK-истории | Снимок завершённой части и ссылки на источник |
| `manager.createBranchedSession(leafId)` | Создаёт файл и переключает ЭТОТ менеджер на новую сессию | Не вызывать на менеджере живого исполнителя |
| `session.navigateTree(targetId, {summarize, customInstructions, replaceInstructions})` | Навигация/branch summary внутри дерева; при streaming бросает ошибку | Не использовать как переключатель работающей карточки на разговор |
| экспорт `generateSummaryWithUsage(...)` | Принимает явный список AgentMessage и параметры модели, возвращает text/usage | Суммаризировать отфильтрованные данные; адаптер инкапсулирует длинную SDK-сигнатуру |
| `session_before_compact` | Может вернуть cancel или свой CompactionResult | Возможность будущей настройки compaction; не обязательный новый механизм этой работы |

Критично: стандартный `serializeConversation` включает блоки `[Assistant thinking]`. Только изменение текста инструкции compact не удаляет их из входа. Для требуемой выжимки передавать в SDK явно отфильтрованный список и проверять фактический prompt тестом. Прямой fork также копирует историю, поэтому не равнозначен короткому очищенному снимку.

## Конкретный сценарий A — обычный чат

1. POST сохраняет сообщение с idempotency key и фиксирует новую inputRevision в существующей долговечной очереди. Возвращает «Принято» после commit, не ожидает модели/abort/суммаризатора.
2. Существующий `interruptChatTurnForOwner` становится входом в единую процедуру остановки, а не дублируется ещё одним контроллером. Для адресата закрывается выдача новых действий старого поколения; старые callbacks не могут объявить актуальный итог.
3. Фоновый обработчик вызывает `session.abort()`. Учитывает отдельно SDK-генерацию и процессы инструмента. Контракт отмены инструментов проверяется на реальных адаптерах. Неотменяемая либо неоднозначная операция остаётся видимой; конфликтующее продолжение не начинается до сверки результата.
4. После завершения/фиксации старого вывода сохраняются его сегменты. Новое сообщение находится после уже отображённых действий. Ни один последующий кусок старого хода не превращается в продолжение нового ответа.
5. Из подтверждённых сообщений/результатов строится checkpoint: **что было; какая цель; что выполнить**. Последние сообщения владельца передаются дословно отдельно. Сохраняются ограничения, пути, неизвестные эффекты, ссылки на артефакты.
6. Адаптер вызывает экспорт Pi `generateSummaryWithUsage` только на отфильтрованном материале, учитывает usage, проверяет структуру и source revision. Не применяет стандартную сериализацию ко всей сырой сессии. Неполные toolCall/toolResult пары превращаются в явно описанные факты/неопределённость, а не в некорректный модельный протокол.
7. Свежий SessionManager.create + createAgentSession получают обычные системные правила, checkpoint и дословные уточнения. Не SessionManager.open старого файла. Старый файл остаётся архивом, в prompt автоматически не возвращается.
8. Перед стартом атомарно проверяется inputRevision. Новое уточнение во время подготовки делает checkpoint устаревшим: обновляется подготовка, не запускаются два исполнителя. Ошибка суммаризации показывает причину и сохраняет очередь; fallback к сырой истории запрещён.

## Конкретный сценарий B — карточное обсуждение

1. Новое обсуждение создаётся с явной привязкой к этапу и независимым discussionId. Исходное сообщение отправляется ТОЛЬКО в обсуждение: текущий topicSlice-dispatch, одновременно передающий его в работу, для этого сценария отключается.
2. Контроллер рабочего этапа публикует снимок уже завершённых SDK-событий и прогресса. Снимок содержит sourceRunId, sourceLeafId, sourceRevision и время; незавершённое действие обозначено как незавершённое. Запрещены переключение leaf живого manager и небезопасное чтение наполовину записанной JSONL-строки.
3. Из снимка строится краткий контекст без сырых thinking-блоков. Создаётся отдельный SessionManager.create и разговорная AgentSession с собственным каталогом разрешений. Использовать createAgentSession/общую роль и модель; не `openSlotSession`, который сегодня открывает рабочую историю этапа.
4. Обсуждение технически ограничено чтением и ответами. Для него не доступны запись проекта, изменение статусов/плана, старт/сдача слотов и скрытый обход через универсальный gateway. Одной инструкции «не работай» недостаточно. Исходный исполнитель продолжает работу; его состояние не меняется из-за открытия ветки.
5. Реплики разговора сохраняются в ветке и обрабатываются её сессией. Они не вызывают deliverTopicToWork/deliverChatToWork. Новая реплика может прервать только старый ответ обсуждения, не рабочий run.
6. Закрытие переводит обсуждение в `closing`, запрещает новые реплики и фиксирует финальную границу. Если ответ ещё идёт, его останавливают/дожидаются по выбранному контракту, затем суммаризируют полный зафиксированный разговор. Это фоновая операция с видимым статусом.
7. Pi generateSummaryWithUsage получает сообщения владельца И ответы роли, а не последние пять первых строк. Выжимка имеет три раздела, явно выделяет согласованные изменения и не повышает обсуждаемый вариант до решения. При неоднозначной договорённости итог требует подтверждения владельцем; не угадывать указание исполнителю.
8. Готовый итог сохраняется вместе с одной durable delivery в общей транзакции. `handoffId` уникален для версии закрытия. Повтор close возвращает тот же результат; сбой не оставляет вид «закрыто и передано», когда передачи нет.
9. Если тот же рабочий этап активен, итог поступает через существующий deliverTopicToWork → deliverChatToWork → session.steer. Получение подтверждается наблюдаемым user-message event/существующим механизмом квитанций, а не успешным возвратом Promise<void> из steer. Рабочие цель/граф/приёмка сами собой не меняются.
10. Если этап готовится, итог остаётся в slot_topic_inbox/существующей durable queue. Если исполнитель/поколение сменились, адрес пересверяется: новому исполнителю того же незавершённого этапа можно доставить с актуальным снимком; закрытому этапу, другой роли или неоднозначному получателю — видимый статус без автоматического запуска. Никакого нового рабочего run только ради передачи.

Итог в родительской ленте — отображение handoff, а не сам механизм доставки. До квитанции показывать «Итог сохранён, ожидает доставки», затем «Получен исполнителем». Обсуждение можно закрыть, пока итог ожидает адресата; данные и статус доставки сохраняются.

Сохранённая рабочая сессия при этом продолжает содержать собственную прежнюю историю. Передача короткого итога не означает, что у работающего агента исчезли все прошлые размышления. Три раздела вместо сырой истории применяются при новом запуске/перезапуске; обсуждение тоже начинается по короткому снимку.

## Что остаётся собственным в TaskFlow

- Связка chatId/taskId/subtaskId/discussionId/run generation и права адресации.
- Идемпотентность сообщений/close/handoff и квитанции доставки.
- Проекция SDK-событий в строки iOS, а не новый агентный цикл.
- Фильтрация и формат трёх разделов; версия checkpoint и защита от устаревания.
- Контроль реальной отмены инструментов и конечных рабочих бюджетов.

Не создавать второй SessionManager, граф выполнения или механизм очередей «на всякий случай». Использовать существующие chat_message_queue, slot_topic_inbox, fencing и журналы; расширять их после проверки схемы. SDK-лог хранит модельную сессию, БД приложения — доставку и владельческие сообщения; они связаны ID, не претендуют быть взаимозаменяемыми.

## Порядок строк и проявление текста

Каждый законченный комментарий/действие и каждое сообщение владельца получают устойчивые ID и порядок фиксации. Сначала сопоставить доступные Pi entryId/parentId и события адаптера с текущими message sequence. Не смешивать rowid сообщений с timestamp начала целого live-turn, как сейчас делает feedItems.

Нужная прикладная таблица соответствия сохраняет `chatId, rowId, turnId, sdkEntryId?, segmentId?, order, revision`. Она не копирует SDK-историю целиком. Число/схема полей уточняются по fixture; если существующая таблица покрывает контракт, расширить её вместо создания новой.

При сообщении владельца закрывается прежний сегмент. Новый вывод — новая строка после сообщения. Уже начатый инструмент, закончившийся позже, имеет ссылку на запуск и отдельный результат после границы. Завершение хода не заменяет всю историю одним пузырём. Свёртка шагов не пересекает владельческие сообщения.

Проявление текста остаётся по segmentId и не определяет порядок. Поздний REST/WS-пакет применяется по ID/revision. После переподключения виден тот же порядок. ScrollPosition/FocusState остаются штатными; скролл по каждому пакету не возвращается.

## Ограничители: единицы измерения и нерешённые числа

Не брать maxTurns из другого SDK и не выдавать его за метод Pi. В проверенном AgentSession нет параметра maxSteps, который автоматически решает требование владельца. Использовать уже имеющийся beforeToolCall/общий dispatch и надёжную проверку поколения; покрытие CLI/host проверить отдельно.

Бюджет считаем по фактически начинаемым рабочим операциям, с отдельным учётом gateway/параллельных вызовов. Нельзя обходить предел одним wrapper-вызовом, который выполняет много действий. Отмена, квитанции и восстановление ранее начатого job не должны блокироваться исчерпанным бюджетом.

**До включения согласовать:** рабочие вызовы на запуск, общий бюджет поручения/автопродолжений, предел блокирующего ожидания и крайний срок по типу job. Числа 6/10/12 из других механизмов сюда не переносить. Тесты используют явные малые настройки и проверяют границу N/N+1. Настройка конечна, модель не увеличивает её сама; sleep вместо ожидания события не используется.

## Практические дополнения из Deep_Research_.md

Материал владельца `/Users/max/Downloads/Deep_Research_.md` использован как дополнительный список проверок. В нём нет расшифровки ссылок [2]–[9], раздел ошибок обрывается; примеры Chat Completions не являются контрактом установленного Pi 0.84.4.

В этапы 1–2 и 6 включить следующие требования:

- Сначала надёжно сохранить входящее сообщение с clientMessageId и серверным порядковым номером, затем запускать обработку. В примере восстановления из материала новое user-сообщение добавляется только в память, а сохраняется лишь assistant: этот пробел не переносить. Сохранять также прерванный ответ и его статус.
- Хронология определяется серверной последовательностью событий, а не только created_at: одинаковые часы и поздняя доставка не должны менять порядок. Связи tool-call/result, turnId, generation и стабильные идентификаторы сегментов обязательны. Полная история остаётся архивом; рабочий контекст новых запусков собирается по описанным выше правилам выжимки.
- Восстановление после сбоя не повторяет автоматически потенциально выполненную операцию. Сначала сверить сохранённый статус и результат; неизвестный исход показать явно. RED/replay: crash после сохранения user до запуска, посреди ответа и после внешнего эффекта до сохранения result.
- Для выжимки определить версионируемую схему трёх разделов и проверять результат на сервере. Просьба «верни JSON» не заменяет проверку структуры. При ошибке не запускать работу с пустой выжимкой или сырой историей; сохранить восстановимое состояние ошибки.
- Журналировать conversation/session/run/generation/event/request IDs, модель и доступную ревизию, причину завершения, задержку, размеры контекста/ответа, retry и причину отмены. Не писать в диагностический журнал сырые рассуждения и секреты. Request ID служит трассировке; дедупликация требует отдельного устойчивого ключа и проверки результата, он сам не гарантирует отсутствие повторного списания.
- max_tokens/аналогичный выходной лимит не заменяет бюджет действий, ограничение ожидания и сжатие контекста. Совместимость параметров и доступность фиксированной ревизии проверять через используемый провайдер и Pi.

Граница транспорта: провайдерный поток обрабатывает Pi, iOS получает события TaskFlow. Не добавлять второй прямой Chat Completions-клиент или SSE-парсер в приложение ради этих примеров. При изменении существующего транспорта проверить оборванные/повторные события, reconnect и восстановление по курсору. Если собственный SSE-парсер действительно понадобится, отдельно проверить UTF-8 по частям, несколько событий за чтение, многострочные data и окончания CRLF/CR/LF; `[DONE]` — соглашение конкретного API, не общее правило SSE. Основание: [HTML Standard](https://html.spec.whatwg.org/multipage/server-sent-events.html#parsing-an-event-stream).

Отмена подписки при уходе с экрана и отмена исполнения — разные операции. Уход из карточного обсуждения не останавливает фоновую работу. Явный stop/новое сообщение обычного чата проходят серверную границу отмены; обрыв соединения сам по себе не доказывает завершение модели, внешнего процесса или прекращение тарификации. Документация [AbortController.abort](https://developer.mozilla.org/en-US/docs/Web/API/AbortController/abort) описывает отмену fetch/чтения/потока, а не такую серверную гарантию. Добавить replay: отключить клиент, продолжить задачу, подключиться и восстановить ленту без повторного запуска.

## Условия приёмки

- Обычный чат: старое направление не запускает новых действий после границы; следующий ответ начинается после нового сообщения и использует свежую выжимку.
- Карточка: исполнитель не получает промежуточные реплики отдельного обсуждения; получает один итог после закрытия с проверяемой квитанцией.
- Старые сообщения и действия не переезжают после final, reconnect или перезапуска сервера.
- Итог не применяется дважды; ошибка/смена адресата видна и не вызывает второго исполнителя.
- Сырые thinking-блоки не входят в суммаризатор и свежий prompt этих новых путей; старые архивы не уничтожаются.
- Реальная отмена внешней операции проверена отдельно от idle Pi; неизвестные эффекты не замалчиваются.

Самопроверка: варианты A/B разделены; установленные API отделены от новых функций TaskFlow; ограничения branch/streaming учтены; каждый новый переход имеет RED/GREEN или сквозной replay. Документ не является результатом выполнения этих тестов.
