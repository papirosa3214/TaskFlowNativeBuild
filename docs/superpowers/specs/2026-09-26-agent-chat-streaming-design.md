# Живая лента шагов роли в чате — Design

## Goal

Пока роль (`researcher/builder/qa/architect/designer/...`) работает над задачей,
владелец в чате видит вместо статичных точек «печатает» живую строку с тем,
что роль делает прямо сейчас (читает файл, правит код, выполняет команду,
ищет) — по мотивам референсного компонента `AgentActivityFeed.swift`.

## Scope

- Только живая лента — без истории. Закрыл чат и открыл заново — прошлые
  шаги не восстанавливаются, видно только то, что происходит сейчас (если
  роль всё ещё работает).
- Только шаги (какой инструмент сейчас используется). Токен-стриминг текста
  ответа роли — отдельная будущая задача, не в этом объёме.
- Только тет-а-тет: владелец и ровно одна роль в одном чате. В групповом
  канале («agents», где одновременно могут быть несколько ролей) лента
  шагов НЕ показывается — там всё остаётся как сейчас, точки «печатает».
  Причина: в группе несколько ролей могут работать параллельно, и поток
  из нескольких одновременных лент — не то, что нужно владельцу.
- Меняется место, где в тет-а-тет чате сейчас рендерится «печатает»
  (`TypingLine`) — для роли-собеседника эта же строка становится строкой
  шага, когда для неё пришло хотя бы одно событие.
- Источник данных — событийный поток текущего рантайма роли (то, что в коде
  сервера сейчас разбирается в `PiRuntimeAdapter.startRun` и почти целиком
  выбрасывается в `recordRunActivity`). Название рантайма нигде в этой фиче
  наружу (в терминологии, в переменных фичи, в UI) не всплывает — это
  деталь реализации одного файла, а не понятие фичи. Понятие фичи — «роль».

## Architecture

**Сервер.** В обработчике событий рантайма роли (`PiRuntimeAdapter.startRun`,
там же, где сейчас вызывается `recordRunActivity`) добавляется relay:
событие начала вызова инструмента (есть имя инструмента и id вызова)
транслируется в существующий WS-канал чата новым сообщением
`agent:step { task_id, user_id, tool }`; на завершении хода/сессии —
`agent:step:done { task_id, user_id }`. Сервер отдаёт голое имя инструмента
строкой, без интерпретации — подпись и иконку выбирает клиент.

**iOS-клиент.** Два новых кейса в `RealtimeEvent` (`.agentStep`,
`.agentStepDone`), разбираются так же защитно, как остальные события канала:
незнакомая форма → `.unknown`, ничего не роняет. Рендерится строка шага
ТОЛЬКО в тет-а-тет чате с ролью — вместо `TypingLine`, если для роли пришло
хотя бы одно событие шага, иначе как сейчас, анимированные точки. В
групповом канале («agents») эти события клиент получать может (сервер их не
фильтрует по каналу), но экран группового канала их игнорирует и рендерит
только обычные точки — различие чисто в презентации, без новой серверной
логики маршрутизации. Таблица
`имя инструмента → подпись/иконка` — маленькая, статическая, на клиенте:
`read`→«Читает», `edit`→«Правит», `bash`→«Выполняет команду»,
`grep`/`glob`→«Ищет», всё незнакомое → «Работает».

## Safety / edge cases

- Реконнект WS посреди хода роли — лента просто пустая до следующего
  события; ожидаемо, раз истории нет по замыслу.
- Неизвестное имя инструмента — общая подпись «Работает», не падаем и не
  показываем сырую строку из рантайма пользователю.
- Ход оборвался без `agent:step:done` (краш, отмена) — подчищается тем же
  таймером, что уже чистит зависшие записи «печатает» в `ChatViewModel`;
  отдельный watchdog не заводится.
- Несколько ролей активны одновременно в групповом канале — сюда не
  относится: лента шагов в группе не рендерится по замыслу (см. Scope), это
  не «краевой случай», а обычное поведение группового канала.

## Testing

- Сервер: юнит-тест на функцию маппинга события рантайма → исходящий
  WS-payload (начало вызова инструмента → `agent:step`; посторонние типы
  событий — no-op, ничего не шлём).
- iOS: разбор двух новых кейсов `RealtimeEvent` (+ битый payload →
  `.unknown`); снэпшот-тест новой строки-шага на паре инструментов
  (конвенция репозитория — `SnapshotTests`).
- Живая проверка перед сдачей — кадром симулятора на реальном прогоне роли
  (`CLAUDE.md` проекта: «проверка правок интерфейса — кадром симулятора, не
  на глаз»).
