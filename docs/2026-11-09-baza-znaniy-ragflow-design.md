# «База знаний» как единый вход в RAGFlow — дизайн

Дата: 09.11.2026. Владелец: Максим. Автор: агент (ThinkRail).

## 1. Зачем

Сейчас в приложении «База знаний» (`Sources/Features/Knowledge/NotesScreen.swift`) — это
дневник заметок с поисковой строкой, которая отдаёт куски из RAGFlow. Сам RAGFlow живёт сбоку:
заметки уезжают туда раз в сутки, датасеты видны только в настройках проекта, загрузить свой
документ из приложения нельзя, спросить базу одним вопросом — нельзя.

Владелец (09.11.2026): «нужно как-то базу знаний нашу... слияние... чтобы напрямую всё это
работало максимально органично, а не вот так вот, как сейчас какие-то синхронные, рассинхроны...
нужно ракфлоу куски соединить с TaskFlow», и уточнил: в разделе «База знаний» он должен видеть
датасеты, окно запросов к базе, и сам загружать туда документы для чанкования.

## 2. Что решил владелец

| Вопрос | Решение |
|---|---|
| Судьба дневника | Экран «База знаний» = список датасетов; датасет заметок открывается дневником (папки, редактор). Отдельного раздела «Дневник» не остаётся. |
| Индексация заметки | Сразу при сохранении: через несколько секунд заметка в поиске, в списке видно «индексируется / в поиске / ошибка». Суточный прогон остаётся страховкой. |
| Окно запроса | Ответ модели + источники-куски со ссылкой на документ. Не только куски, не чат-ассистент. |
| Датасеты | Видеть все. Поиск идёт по всем включённым датасетам; чтобы сузить, владелец проваливается в конкретный датасет и ищет там, внутри — вторая фильтрация по документам/папке. Уточнение владельца 10.11.2026 (п. 9.1) отменяет прежнее «поиск всегда начинается с выбора датасета». |
| Способ сборки | Сервер TaskFlow — единственный шлюз. Приложение про RAGFlow не знает, ключ остаётся на сервере. |

## 3. Цели

1. Один экран «База знаний»: датасеты, документы датасета, загрузка файла, статус разбора,
   окно запроса с ответом и цитатами.
2. Заметка TaskFlow попадает в индекс RAGFlow без суточного ожидания; расхождение
   «в дневнике одно, в поиске другое» исчезает.
3. Поиск по умолчанию идёт по всем включённым датасетам, а внутри датасета — по выбранным
   документам/папке (уточнено владельцем 10.11.2026, п. 9.1).
4. Ничего нового в контуре не появляется: ни ассистентов RAGFlow, ни второго индекса,
   ни ключа RAGFlow на телефоне.

## 4. Не-цели

- Не заменяем RAGFlow своим векторным хранилищем.
- Не переносим в приложение настройки RAGFlow (чанкование, embedding, модели датасета).
- Не трогаем внешние синки (`lessons_ragflow_sync.py`, `memory_ragflow_sync.py`, vault-синк,
  research) — они пишут в свои датасеты и остаются как есть.
- Не делаем стриминг ответа в v1.
- Не меняем поведение KB-MCP у агентов.

## 5. Анти-цели (провал, даже если «работает»)

- Заметка видна в поиске через сутки после правки.
- Удаление чужого датасета/документа из приложения (уроки, память, CRM).
- Датасет, не имеющий отношения к вопросу, попадает в выдачу молча.
- Ключ RAGFlow или его адрес появляются в iOS-коде.
- Новый фон-таймер, который снова надо держать в согласии с датасетами.

## 6. Ограничения

- iOS — тонкий клиент: всё вычисление на сервере `.110` (`~/Проекты/New-Todoist`).
- Ключ RAGFlow (`RAGFLOW_TOKEN`), адрес (`RAGFLOW_API`) и датасет по умолчанию
  (`RAGFLOW_TASKFLOW_DATASET`) — только в `server/.env`; читаем `process.env` внутри функций,
  не на уровне модуля (`server/src/routes/knowledge.ts`, комментарий от 08.09.2026).
- RAGFlow v0.25.5. Retrieval (`/ragflow/api/apps/sdk/doc.py:340`) принимает: `dataset_ids`
  (обязательно), `question`, `document_ids`, `similarity_threshold`, `vector_similarity_weight`,
  `top_k` (по умолчанию 1024), `page`/`page_size` (по умолчанию 30), `highlight`,
  `metadata_condition`.
- Вложения в TaskFlow приходят сырыми байтами, без multipart (`server/src/routes/attachments.ts`),
  лимит 15 МБ. Тот же приём — для загрузки документов.
- Заметки лежат в `user_notes`; папки — `journal_folders`; проект привязан к папке
  (`projects.notes_folder_id`) и к своему датасету (`projects.knowledge_dataset_id`). Поэтому
  заметки разных проектов физически лежат в РАЗНЫХ датасетах RAGFlow.
- Доставка — прямой push в main обоих репозиториев, без PR. Правки только по строкам реестра
  `AGENT-WORK-SCOPES/`. Проверки — точечные юнит-тесты (RED → GREEN), без симулятора.
  Сервер: явные файлы тестов, `--maxWorkers=4`.

## 7. Как устроено сейчас (факты)

- iOS: `AppRoute.knowledge` открывает `NotesScreen`. В нём папки заметок, редактор
  (`NoteEditorScreen.swift`), строка поиска (`knowledgeSearch`) → `GET /api/knowledge/search`.
  Кнопка «В базу знаний» у заметки — `TaskOutcomeSection.swift` → `POST /api/notes/:id/knowledge`.
- Сервер: `server/src/routes/knowledge.ts` — `GET /api/knowledge/datasets`,
  `POST /api/knowledge/datasets`, `GET /api/knowledge/search`, `GET /api/knowledge/documents`,
  `GET /api/knowledge/documents/:ragflowId`, `POST /api/notes/:id/knowledge`.
- Индексация: `server/src/lib/knowledgeSync.ts` — раз в сутки после 06:20
  (`startKnowledgeSyncSchedule`), состояние в `~/.local/state/taskflow-docs-sync/state.json`,
  отметка живости и уведомление владельцу о сбое. Документ — `taskflow-<note_id>.md`
  с YAML-шапкой, хэш смысла `content-v1`.
- Сторож поиска: `server/src/lib/kbSearchWatcher.ts` — настоящий retrieval раз в 6 часов.
- RAGFlow на `.110`, v0.25.5, 12 датасетов (09.11.2026): «TaskFlow — документация» 1444,
  «База знаний — уроки» 1198, «Хранилище — Obsidian» 716, «Память — заметки» 520,
  business_knowledge 302, TaskFlow-документация проектов, «База агента CRM» 42,
  business_operations 117, business_actions 115, «Ресёрч и документация» 87,
  «Инструменты без регистрации» 10, «Документация … iOS и macOS» 14. Ассистентов — 0.

## 8. Подходы

**A. Сервер-шлюз (выбран).** Все вызовы RAGFlow остаются в TaskFlow-сервере; iOS получает
ручки «датасеты», «документы», «загрузить», «разобрать», «спросить». Индексация заметки —
очередь внутри сервера. Ответ на вопрос формирует модель сервера (`callUnifiedAi`) по кускам
RAGFlow.

**B. Ассистенты RAGFlow (отклонён).** Ответ и цитаты целиком на стороне RAGFlow, приложение
показывает диалог. Отклонён: на каждый датасет нужен ассистент, которого надо держать в
согласии с датасетом — это ровно тот синк, от которого уходим; промпт и вид ответа почти не
контролируются.

**C. Прямой доступ iOS к RAGFlow / свой векторный индекс (отклонены).** Первое кладёт ключ в
телефон и ломает правило тонкого клиента; второе выкидывает 12 живых датасетов.

## 9. Решение по частям

### 9.1 Экран «База знаний»

Верхний экран (`NotesScreen` перестраивается, `AppRoute.knowledge` остаётся):

1. Системное поле поиска сверху (`.searchable`) — ищет по всем включённым в TaskFlow датасетам
   сразу. **Решение владельца 10.11.2026** (заменяет прежнее «поиск без выбранного датасета
   запрещён»): «обычное окно ввода поисковое, стандартное… если я хочу не везде искать, я
   проваливаюсь в конкретный датасет, и ищу там». Дневник отдельным экраном не делается: заметки —
   одна из полок, вход значком книги. Окно запроса (п. 9.5) открывается строкой «Спросить базу»
   в результатах поиска — то есть всегда по набранному вопросу.
2. Список датасетов, сгруппированный по разделам (п. 14): имя, число документов, чанков, пометка
   «Заметки TaskFlow» / «Датасет проекта» / «Свои файлы» / «Чужой», у датасета с ошибкой —
   красная метка. Исключённые из TaskFlow датасеты в обычный список не попадают — они под
   переключателем «Показать исключённые». Пометки — украшение на клиенте поверх двух серверных
   состояний `owner`: третьей серверной категории нет.
3. Первым закреплён вход «Заметки TaskFlow» — открывает текущий дневник (папки, заметки,
   редактор). Это вход, а не датасет: заметки проектов лежат в датасетах проектов, а дневник
   показывает их все, потому что источник правды — `user_notes`.
4. Тап по датасету — экран датасета (п. 9.3).

Моё решение (строителю): закреплённый вход «Заметки TaskFlow» — потому что заметки одного
проекта физически лежат в датасете этого проекта; одна строка на датасет разорвала бы дневник
на куски.

### 9.2 Серверные ручки

Все — с `authOrApiToken`, как остальные.

| Ручка | Что делает |
|---|---|
| `GET /api/knowledge/datasets` | все датасеты RAGFlow + `document_count`, `chunk_count`, `is_default`, `owner` (`taskflow`/`other`), `last_sync_at`, `index_error` |

`owner: taskflow` — единственный предикат: `id` датасета входит в множество
`{projects.knowledge_dataset_id} ∪ {RAGFLOW_TASKFLOW_DATASET}`. По имени не определяем: «Память —
заметки» и «База знаний — уроки» названиями похожи на наши, но это чужие синки, и ошибка в
предикате разрешила бы удалить чужое (анти-цель 2).
| `GET /api/knowledge/datasets/:id/documents` | документы датасета: `name`, `title`, `project`, `doc_id`, `ragflow_id`, `chunk_count`, `size`, `indexed`, `archived`, `owned`, `uploaded_at` |
| `POST /api/knowledge/datasets/:id/documents` | загрузка файла сырыми байтами (`?name=`), ≤ 15 МБ; сразу ставит разбор; отвечает `{document_id, name, status}` |
| `GET /api/knowledge/documents/:ragflowId/status` | статус разбора (`UNSTART`/`RUNNING`/`DONE`/`FAIL`, прогресс, текст ошибки) |
| `DELETE /api/knowledge/documents/:ragflowId` | удаление только своего документа (`taskflow-*.md` или запись в `knowledge_uploads`); чужой — 403 с текстом |
| `POST /api/knowledge/datasets/:id/reparse` | переразбор своих документов (кнопка «переиндексировать») |
| `POST /api/knowledge/ask` | `{question, dataset_ids[], document_ids[], folder_id?}` → `{answer, model, chunks[]}` |
| `GET /api/knowledge/search` | `dataset_id`/`dataset_ids` необязательны: без них сервер ищет по всем включённым датасетам (решение 10.11.2026, см. п. 9.1) |
| `GET /api/knowledge/documents/:ragflowId?dataset_id=` | уже существует (§7): отдаёт markdown без шапки. Отдельная ручка содержания не нужна |
| `GET /api/notes/:id/index-state` | не нужна: состояние приходит полем `index_state` в `GET /api/notes` (п. 9.4) |
| `POST /api/notes/:id/knowledge` | без изменений по смыслу (ручная переиндексация «сейчас») |

Семантика пустого фильтра поиска (уже в сервере, не только в дизайне): `searchDatasetIds` в
`server/src/lib/knowledgeRegistry.ts:246` при `requested.length === 0` берёт
`[...allowed].filter(scoped)` — то есть все включённые датасеты, а для вызова от имени роли
только выданные ей. Поэтому пустой `dataset_id` — не ошибка и не «поиск без области»: 403
«нет доступов» остаётся единственным отказом и только когда роли не выдан ни один датасет.
Ограничение RAGFlow «`dataset_ids` обязательно» (п. 6) снимается на сервере: клиент датасет не
обязан называть, сервер сам передаёт в retrieval явный список, расширенный до всей области.

`GET /api/knowledge/datasets` не кэширует список; каждый вызов — один запрос к RAGFlow.

### 9.3 Экран датасета

- Заголовок: имя, число документов, пометка владельца.
- Поле поиска внутри датасета (retrieval с `dataset_ids: [этот]`).
- Фильтр «внутри датасета»: выбор документов (мультивыбор) и, для датасетов TaskFlow, фильтр по
  папке проекта. Выбранные документы уезжают в `document_ids`; папка разрешается сервером в
  список `ragflow_id` по `doc_id` заметок.
- Список документов: имя/заголовок, чанки, размер, «в поиске / индексируется / ошибка»,
  `archived` для закрытых проектов. Тап по документу TaskFlow — редактор заметки; по чужому —
  чтение markdown тем, что уже отдаёт `GET /api/knowledge/documents/:ragflowId?dataset_id=`.
- Кнопка «+» — загрузка файла (document picker), после загрузки строка показывает прогресс
  разбора (опрос статуса раз в 2 с, до 5 минут).

### 9.4 Индексация заметки сразу

- Новая таблица `knowledge_index_jobs` (миграция в `server/src/migrations.ts`):
  `note_id PK`, `queued_at`, `attempts`, `status` (`queued`/`running`/`done`/`error`),
  `error`, `dataset_id`, `ragflow_doc_id`.
- Сохранение заметки (`POST/PATCH /api/notes/:id`) ставит задание (upsert) — не дожидаясь ответа
  RAGFlow.
- Очередь в процессе сервера: тик раз в 5 с, задание берётся, если прошло ≥ 10 с с `queued_at`
  (дебаунс серии правок). Один прогон за раз (как `running` в `knowledgeSync`).
- В таблице ещё `content_hash`: прогон собирает `noteDocument()` и, если хэш совпал с уже
  проиндексированным (`state.json`, тот же `content-v1`), задание закрывается без обращения к
  RAGFlow. Без этого автосохранение с дебаунсом 800 мс (`NoteEditorViewModel.swift:69-102`)
  зальёт заметку десятки раз за сессию правки.
- Порядок прогона — «залить, потом удалить старое» (наоборот дало бы окно, где только что
  написанная заметка отсутствует в поиске всё время разбора): залить новую копию под тем же
  именем, дождаться её `ragflow_doc_id`, удалить прежний `ragflow_doc_id`
  (`rememberUploaded()` хранит его), запустить разбор. Секунды дублирования в выдаче безвредны,
  пропажа документа — нет.
- Перенос заметки между проектами и удаление: строка задания помнит `dataset_id`, а `state.json`
  помнит `dataset_id` прошлой заливки; прогон удаляет прежнюю копию из СТАРОГО датасета, если он
  отличается, а `DELETE /api/notes/:id` ставит задание с `action: delete`. Без этого
  `taskflow-<id>.md` навсегда остаётся в датасете, к которому заметка больше не относится, и
  отвечает на вопросы чужого проекта — тот самый рассинхрон.
- Ошибка — `attempts+1`, до 3 попыток с паузой, затем `error` + уведомление владельцу (как сейчас
  в `runKnowledgeSyncWithHeartbeat`).
- Суточный прогон (`startKnowledgeSyncSchedule`) остаётся: он подбирает то, что очередь
  пропустила (сервер лежал, заметку залили мимо приложения).
- Дневник показывает состояние четырьмя словами: `queued` — «в очереди», `running` —
  «индексируется», `done` — «в поиске», `error` — «ошибка». «В поиске» наступает только при
  `DONE` от RAGFlow: чанки появляются после разбора, документ в `RUNNING` retrieval не отдаёт —
  иначе строка врала бы.
- Состояние на список приходит не по ручке на заметку, а полем `index_state` в ответе
  `GET /api/notes` (одна заметка — один запрос на сотни строк не годится). У заметки без строки
  в `knowledge_index_jobs` поля нет — суточный прогон её уже проиндексировал, и показывать
  «не проиндексировано» на пятистах старых заметках после выкладки нельзя.

### 9.5 Окно запроса («Спросить базу»)

- Выбор датасетов: чипсы, по умолчанию — тот, из которого открыли окно; «все» отсутствует.
- Сервер: retrieval по выбранным `dataset_ids` (и `document_ids`, если заданы) →
  сборка промпта с нумерованными кусками → `callUnifiedAi` → `{answer, model, chunks[]}`.
- Один вызов retrieval на все выбранные датасеты: у всех двенадцати `embedding_model` =
  `bge-m3-embed@Ollama` (проверено 09.11.2026), наборы векторов совместимы. Разные модели в одном
  вызове RAGFlow не смешивает, поэтому при появлении датасета с другой моделью сервер разбивает
  запрос по моделям и сливает выдачу по `score`.
- Ответ без стриминга; куски под ответом: текст, документ, проект, `doc_id`, `dataset_id`,
  `dataset_name`, `score`.
- Модель — из `KB_ASK_MODEL` (по умолчанию — модель, которой сервер отвечает ролям; читаем тем
  же путём, что `callUnifiedAi`). Если модель недоступна — 502 с текстом, куски всё равно
  отдаём (ответ `answer: null`), чтобы поиск не пропадал из-за модели.
- Промпт: отвечать только по кускам, при нехватке — сказать «в выбранных датасетах не нашёл»,
  ссылаться номерами `[1]`, `[2]`.

### 9.6 Фильтрация

- Внешняя: для вопроса (`/api/knowledge/ask`) датасеты обязательны — «по всему сразу» подмешало
  бы чужие тематики. Для поиска (`/api/knowledge/search`) датасеты необязательны: без них область —
  все включённые, внутри датасета — только он (решение 10.11.2026).
  В выборку попадают только датасеты, включённые в TaskFlow (`enabled = 1`), а при вызове от имени
  роли — ещё и выданные этой роли (п. 14.4).
- Внутренняя: документы (мультивыбор) и папка проекта (только для датасетов TaskFlow).
  `metadata_condition` не используем в v1: шапка документа — YAML в тексте, а не метаданные
  RAGFlow.
- Пустой результат поиска при выбранных фильтрах — честный текст «в выбранных датасетах нет»,
  а не «знаний нет».

### 9.7 Права

- Загрузка — только в свои датасеты (`owner: taskflow`) и только включённые. В чужие нельзя:
  `lessons_ragflow_sync.py:139-178`, `memory_ragflow_sync.py:95`, `research_ragflow_sync.py:103`
  удаляют из своих датасетов всё, чего нет в их списке, — загруженный файл исчез бы на следующем
  часовом прогоне молча, а строка в `knowledge_uploads` указывала бы на мёртвый id. Чужие
  датасеты видны и ищутся, кнопки «+» у них нет.
- Удаление и переразбор — только для своих: имя `taskflow-*.md` либо запись в новой таблице
  `knowledge_uploads` (`ragflow_doc_id`, `dataset_id`, `name`, `uploaded_by`, `uploaded_at`).
- Чужие датасеты и документы — только чтение и поиск; попытка удаления — 403 с понятным текстом.

### 9.8 Сторож

Расширяем `kbSearchWatcher` двумя пробами (раз в 6 часов, уведомление владельцу не чаще раза в
сутки): (1) существующая — «поиск отвечает»; (2) новая — «очередь индексации не застряла»:
самое старое задание в `queued` старше 10 минут или `error` за последние сутки → сигнал.

## 10. Что остаётся строителю (мои решения помечены)

1. Точный вид верхнего экрана (список + поиск) — по дизайн-системе, без новых компонентов.
2. Модель для ответа: `KB_ASK_MODEL`; дефолт — из существующей лестницы моделей сервера
   (моё решение: не заводить новый профиль модели).
3. Формат промпта и лимит кусков (моё решение: ≤ 8 кусков, ≤ 12 000 символов суммарно).
4. Опрос статуса разбора: 2 с × 5 мин, потом «проверьте позже» (моё решение).
5. Лимит файла 15 МБ; если RAGFlow откажет — показываем его текст (моё решение).
6. Внешние синки не трогаем.
7. Типы файлов v1 — `.md`, `.txt`, `.pdf`, `.docx`, `.html`. Выбор в document picker
   ограничиваем этими UTI, сервер отказывает остальным понятным текстом (моё решение).
8. Способ разбора файла не выбираем: наследуется от датасета (у всех нынешних — `naive`). Свой
   `chunk_method` на файл в v1 не передаём — иначе пришлось бы на каждый тип подбирать парсер и
   модель OCR (моё решение).

## 11. Проверка

- Сервер, юнит-тесты (целевые файлы, `--maxWorkers=4`), RED → GREEN:
  `knowledgeIndexQueue` (дебаунс, 3 попытки, порядок), `knowledgeDocs` (scope: обязательные
  `dataset_ids`, разрешение папки в `document_ids`), `knowledgeAsk` (промпт, отсутствие модели,
  пустая выдача), `knowledgeOwnership` (своё можно удалять, чужое — 403).
- iOS: тип прод-правок — UI; собираем только при прямом поручении на сборку. Логика, вынесенная
  в отдельный тип (разбор ответа, склейка фильтров), получает юнит-тест без симулятора.
- Точечная живая проверка API на `.110` после выкладки: `GET /api/knowledge/datasets`,
  загрузка одного файла в тестовый датасет, `POST /api/knowledge/ask`.

## 12. Риски

- Разбор на CPU: очередь может упираться в Ollama. Лечится тем же, чем сейчас — один прогон за
  раз, повторы, сторож.
- У RAGFlow лимит на размер файла и на число документов в батче — сервер отдаёт его текст, не
  глотает молча.
- Датасетов много и они меняются вне TaskFlow — список всегда живой, без кэша.
- Ответ модели может «додумать» — промпт ограничивает кусками, куски показываются рядом.

## 14. Управление датасетами из приложения (владелец, 09.11.2026)

Владелец добавил три требования: (а) датасет «Память — заметки» исключить из TaskFlow,
(б) включать и исключать датасеты прямо из приложения, (в) раскладывать датасеты по разделам-
тематикам и (г) выдавать доступ к отдельным датасетам отдельным ролям, чтобы не засорять поиск
тем ролям, которым датасет не нужен.

### 14.1 Три таблицы

| Таблица | Что хранит |
|---|---|
| `knowledge_dataset_sections` | `id`, `title`, `position`, `created_at` — разделы-тематики |
| `knowledge_datasets` | `dataset_id PK`, `enabled`, `section_id`, `title` (переименование в TaskFlow), `created_at` |
| `knowledge_dataset_roles` | `dataset_id` + `role_key`, PK по паре — доступ ролям к датасету |

Список датасетов по-прежнему берётся из RAGFlow (он источник правды о существовании и размерах);
таблицы держат только то, чего в RAGFlow нет: включён/исключён, раздел, имя для приложения,
доступ ролям. Строка реестра заводится лениво при чтении списка, если датасет в нём появился.

«Память — заметки» (`aad90ec0901f11f1be69a9ef96f0a9d6`) в миграции получает `enabled = 0`: это
датасет памяти агентов (Mnemosyne-синк), а не база знаний TaskFlow. Остальные — включены.

### 14.2 Ручки управления

| Ручка | Что делает |
|---|---|
| `GET /api/knowledge/sections` | разделы по порядку с числом включённых датасетов |
| `POST /api/knowledge/sections` | `{title}` — новый раздел в конец |
| `PATCH /api/knowledge/sections/:id` | `{title?, position?}` — переименовать, переставить |
| `DELETE /api/knowledge/sections/:id` | удалить раздел; его датасеты остаются без раздела |
| `PATCH /api/knowledge/datasets/:id` | `{enabled?, section_id?, title?}` — включить/исключить, положить в раздел, переименовать |
| `PUT /api/knowledge/datasets/:id/roles` | `{role_keys: string[]}` — заменить набор ролей; ключи проверяются по таблице `roles` |

Права — `isOwner` (как в `server/src/access.ts`): управление датасетами и доступами только владелец.

`GET /api/knowledge/datasets` отдаёт к каждому датасету `enabled`, `section: {id,title}|null`,
`roles: [{key,title}]`. Без `?include_disabled=1` исключённые не отдаются.

### 14.3 Как это выглядит в приложении

- Список датасетов — секциями по разделам, последняя секция «Без раздела». В шапке «+ Раздел».
- Долгое нажатие по датасету — меню: «Включить в TaskFlow» / «Исключить из TaskFlow»,
  «Переименовать», «В раздел…», «Доступ ролям…». Свайпов не заводим: меню работает и на строке
  с прокруткой.
- Экран датасета — блок «Доступ ролям»: чипсы ролей из `GET /api/roles`, тап переключает.
- Чипсы датасетов в окне «Спросить базу» — только включённые.

### 14.4 Роли: поиск по выданным датасетам

Сегодня роли читают «базу знаний» как FTS по заметкам (`taskflow_kb_search` →
`searchNotes()` в `server/src/runtime/inProcessRun.ts:813`), RAGFlow роли не видят вообще. Добавляем
в группу `taskflow_knowledge` (`server/src/runtime/roleToolCatalog.ts:376`) операцию `rag_search`:

- инструмент `taskflow_rag_search(query, top_k?)` — retrieval по датасетам
  `выданные роли ∩ включённые`; куски возвращаются с `document_name`, `dataset_name`, `score`;
- роли без выдачи инструмент отвечает «доступ ни к одному датасету не выдан» и ничего не ищет —
  чужой датасет не может засорить выдачу по построению;
- `taskflow_kb_search` (FTS по заметкам) не меняется — иначе у всех ролей сразу поменялось бы
  поведение без спроса.
