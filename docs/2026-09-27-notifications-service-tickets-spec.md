## Backend — подтверждённый живой контракт (проверено `curl` 27.09.2026)

Сервис: `notifications-api.service` на `.110`, systemd user unit, Active.

**Base URL:** `http://192.168.1.110:5198` (без авторизации — LAN, проверено
живым запросом).

| Метод | Путь | Возвращает |
|---|---|---|
| GET | `/` | справка `{service, version, endpoints, inbox_root}` |
| GET | `/notifications/inbox?date=YYYY-MM-DD` | `{date, count, items: [NotificationSummary]}` |
| GET | `/notifications/by-source?source=NAME&hours=N` | то же, отфильтровано по источнику |
| GET | `/notifications/triage?date=YYYY-MM-DD` | то же, только `has_triage: true` |
| GET | `/notifications/raw?path=/abs/path.md` | полный markdown, `text/plain` |

**`NotificationSummary` (живой пример, `curl` 27.09.2026):**

```json
{
  "id": "inbox/2026-09-27/015133-autonomy-110",
  "path": "/home/maksim/Проекты/taskflow-уведомления/inbox/2026-09-27/015133-autonomy-110.md",
  "title": "Автономность .110 — сводка за сутки",
  "ts": "2026-09-27T01:51:33",
  "source": "autonomy-110",
  "level": "error",
  "has_triage": true,
  "snippet": "## Сводка (для отображения в приложении)\n```\n...\n```",
  "links": []
}
```

`id` — реальный, отдаёт сервер (относительный путь без расширения). Ранняя
версия этой спеки ошибочно предполагала, что `id` нужно синтезировать на
клиенте — это неверно, сервер его отдаёт всегда.

## Формат markdown-файла (эталон — `format/svodka-template.md` на `.110`,
перечитан 27.09.2026 после правки владельца)

```markdown
# <Заголовок>

- когда: <ISO 8601 без TZ>
- от кого: <source>
- уровень: <level>
- тревога: да|нет
- приёмка: rendezvous.py v1

## Сводка (для отображения в приложении)
​```
Сводка уведомлений от ДД.ММ.ГГ
**Работают в штатном режиме:**
- <пункт>
**Не отработали в штатном режиме:**
- <пункт с меткой тревоги>
По данным проблемным местам создана карточка на диагностику:
<ссылка tf://task/<uuid>> (дата, исполнитель)
​```
```

Сервер TaskFlow (не приложение!) дописывает в тот же файл по мере
прохождения workflow, отдельными секциями:

```markdown
## По результатам диагностики
Выявлено: <problem>
По подтверждённым проблемам создана карточка на устранение: <ссылка tf://task/<uuid>>

## Итог по устранению
- <проблема> — (исправлено)
- <проблема> — (не исправлено: нет доступов у исполнителя)
- <проблема> — (не исправлено, нужно ваше решение по вопросу...:
  1) ...
  2) ...
  3) ...
  4) свой вариант)
```

**Это Phase 4 backend-работы — на 27.09.2026 ещё НЕ реализовано на сервере**
(карточки диагностики уже создаются автоматически через
`inboxTriageWatcher.ts`, но дописывание блока «Итог по устранению» после
закрытия карточки — следующая итерация). Парсер и модалка в этом плане
строятся по формату шаблона заранее, «на опережение», и не проверены на
живом файле с таким блоком — только на сконструированной фикстуре.

## Как это подключено к карточкам TaskFlow (backend, уже сделано, вне
зоны этой сессии)

Тревожный тикет (`has_triage: true`) автоматически получает обычную
задачу-карточку TaskFlow (создаёт `inboxTriageWatcher.ts` через прямой
`INSERT` в таблицу `tasks`, polling 1с) — это ordinary task, не отдельная
сущность. Весь workflow устранения идёт обычным TaskFlow-путём (claim →
работа → review); приложению для этого ничего специально делать не нужно.

## UI карточки-тикета — финальное поведение (Mnemosyne, 27.09.2026 03:34)

**Никаких inline-кнопок.** Активные и неактивные фрагменты текста внутри
блока «Итог по устранению» — это текстовые строки-сноски с двумя
состояниями:

| Текст строки | Визуально | Тап |
|---|---|---|
| `(исправлено)` | серая, неактивная | открыть связанную задачу-устранение в TaskFlow (просмотр) |
| `(не исправлено: ...)` | красная, активная | открыть модальный диалог «Что делаем дальше?» |
| `(не исправлено, нужно ваше решение...)` | красная, активная | то же — модальный диалог |

В модальном диалоге — до 3 предложенных вариантов (если встроены в текст
строки) + пункт 4 «свой вариант» (поле ввода, дефолт = вариант 1, если он
есть). Submit → `POST /tasks/:id/comments` (уже есть в коде,
`APIClient.createComment`, `APIClient+Subtasks.swift:36`) с текстом
выбранного/правленого варианта — обычный комментарий, никакого отдельного
API. Никакой собственной submit-логики мимо этого метода.

Ссылки `tf://task/<uuid>`, встречающиеся в тексте markdown (у пункта
диагностики/устранения, у "(исправлено)"), открывают задачу через
существующую навигацию приложения (`route = .taskDetail(taskID:)`) —
регистрировать `tf://` как системную URL-схему не нужно, ссылка просто
текст внутри markdown, который приложение само разбирает и обрабатывает
как внутренний переход.
