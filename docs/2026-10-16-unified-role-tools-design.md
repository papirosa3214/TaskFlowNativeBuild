# Единый инструмент TaskFlow для ролей

Дата: 16.10.2026. Статус: проект для согласования, реализация не начата.

## Решение

Каждая роль получает один серверный инструмент `taskflow` в обычном чате, работе по задаче и обсуждении этапа. Через него роль находит возможности, получает точную схему параметров и вызывает нужную операцию. Операция имеет одно определение и один обработчик для всех точек входа.

Различия полномочий задаются ролью, режимом хода и контекстом, а не отдельными реализациями инструментов чата и задачи. Одна и та же операция в одинаковом контексте должна давать одинаковый результат независимо от точки входа.

| Путь | Текущая сборка возможностей |
| --- | --- |
| Работа по задаче | `inProcessRun.ts`: `taskflowTools` + Composio + инфрапанель + инструменты хоста |
| Обычный чат | `PiRuntimeAdapter.ts`: `taskflowTools` + `chatTools` + Composio; совпадения разрешаются порядком добавления в Map |
| Обсуждение этапа | `slotConversation.ts`: рабочий набор отфильтрован собственным `DISCUSSION_TOOLS` |
| Планирование/обсуждение обычного чата | Ещё списки в `chatWorkMode.ts` |

Следствия:

- Чат уже использует рабочий набор, но сохраняет второй источник определений.
- Рабочий набор фильтруется через `roleToolAllowed`; добавления из `chatTools` этой функцией не фильтруются. Например, запрещённый секретарю `taskflow_plan_request` определён также в `chatTools`. Это расхождение выдачи возможностей; разрешит ли действие конечный маршрут, нужно проверять отдельно.
- Инфрапанель подключается в рабочем пути, но не в показанной сборке обычного чата. Инфраструктурная роль получает разные возможности.
- `taskflow_chat_attach_file` и `taskflow_slot_restart` добавляются только при наличии контекста сообщения в `chatTools`.
- Три инструмента мессенджера уже имеют общую реализацию в `agentMessaging.ts`, но создаются с разным контекстом.
- Экранный список `inProcessToolNames` отражает рабочий набор и встроенные инструменты, а не полную фактическую сборку каждого хода.

## Контракт единственного инструмента

Предлагаемый интерфейс — три действия одного инструмента:

```json
{"action":"discover","query":"приложить отчёт к ответу"}
```

Возвращает небольшой список операций: стабильное имя, назначение, доступность, причину ограничения. Пустой запрос возвращает разделы каталога с постраничной выдачей. Поиск по точному имени обязателен; поиск по смыслу дополняется обычным текстовым поиском, чтобы отсутствие модели поиска не делало операции недоступными.

```json
{"action":"describe","operation":"chat.attach_file"}
```

Возвращает JSON Schema аргументов, пример, побочные эффекты, необходимые контекст и права, версию контракта. Роль не придумывает параметры по названию операции.

```json
{"action":"invoke","operation":"chat.attach_file","version":1,"arguments":{"file_name":"report.md","format":"md","content":"..."},"request_id":"..."}
```

Внешняя схема `taskflow` проверяет оболочку запроса. Сервер затем обязательно валидирует `arguments` по схеме конкретной операции. Получение описания не выдаёт разрешение: доступ заново проверяется при каждом вызове.

Ответ содержит `ok`, `operation`, `version`, `request_id`, `data` либо структурированную `error`. Для долгой операции возвращаются `job_id` и состояние; её результат читается через операции того же каталога. Тайм-аут не должен провоцировать повторное создание задачи или отправку сообщения.

## Единый реестр

Каждая операция регистрируется один раз:

```text
name, version, title, description, inputSchema,
requiredContext, effects, authorize, execute, timeout, retryPolicy
```

Регистрация повторного имени и версии завершает проверку/запуск ошибкой. Правило «первый обработчик победил» удаляется. Описания для модели, каталог, экран возможностей команды и проверка параметров строятся из этого же реестра. Редактируемые владельцем описания сохраняются через существующий механизм инструкций; права и схема не меняются текстовой инструкцией.

Существующие обработчики сначала оборачиваются в операции без переписывания предметной логики. Маршруты API и их проверки остаются действующими. Composio, инфрапанель и хост подключаются адаптерами к тому же каталогу, с пространствами имён и явным состоянием подключения. Недоступный сервис отображается как недоступный, а не исчезает без объяснения.

## Контекст и полномочия

Сервер создаёт доверенный контекст хода: пользователь роли, роль, run/session, режим, текущие task/subtask/chat/message, машина и рабочий каталог. Модель не может подменить личность, режим или назначенный ей этап аргументами инструмента.

Явный выбор другой задачи/чата допустим только для операций, которые это разрешают, после проверки доступа. Операции текущего слота сохраняют существующие ограничения принадлежности. Просьба владельца, необходимая для перезапуска этапа, подтверждается исходным сообщением и действующим серверным контрактом, а не строкой `owner_requested=true` от модели.

Разделить три основания ограничения:

1. Права роли и доступ к объекту — обязательная серверная авторизация.
2. Режим хода — планирование/обсуждение ограничивают изменения по типам эффектов операций.
3. Рекомендации роли — приоритет поиска и краткое описание часто нужных действий; они не скрывают разрешённую редкую возможность навсегда.

Точные действующие ограничения ролей сохраняются при первом переносе. Пересмотр запретов — отдельное явное решение; единый вход сам по себе никому новых прав не даёт. Каталог не раскрывает закрытые объекты и секреты.

Ошибки: `UNKNOWN_OPERATION`, `INVALID_ARGUMENTS`, `CONTEXT_REQUIRED`, `AMBIGUOUS_TARGET`, `FORBIDDEN`, `MODE_RESTRICTED`, `DEPENDENCY_UNAVAILABLE`, `VERSION_MISMATCH`, `CONFLICT`. Каждая содержит понятное объяснение и допустимый следующий шаг. При нескольких этапах сервер просит точный этап, а не выбирает самостоятельно.

Для изменяющих операций нужна идемпотентность в долговечном хранилище: ключ привязан к личности, операции и содержимому запроса. Повтор с тем же ключом и другими аргументами отклоняется. Для внешних систем без поддержки идемпотентности фиксируется неопределённый результат и проводится сверка; слепой повтор запрещён. Лимиты сообщений и консультаций учитываются сервером в контексте хода и не сбрасываются повторным созданием обёртки.

## Файлы и машины

Первый этап унифицирует серверные возможности TaskFlow и подключаемые сервисы. `read/bash/edit/write` временно остаются инструментами SDK, но создаются общим сборщиком с существующими операциями хоста. В обычном чате нельзя молча запускать команду на .110, когда подразумевается проект на Mac.

Следующий этап может перенести файловые и командные операции в тот же `taskflow` через адаптер хоста. Тогда для модели действительно останется один вход. Песочница, разрешённый каталог, выбор машины и отмена сохраняются. Это отдельная часть миграции с собственными проверками, а не обещание, что серверная обёртка уже решила удалённое исполнение.

## Варианты и выбор

| Вариант | Оценка |
| --- | --- |
| Общий реестр, десятки отдельных инструментов модели | Устраняет дублирование кода, но оставляет большой набор описаний и зависимость от регистрации в сессии |
| Один `taskflow`, discover/describe/invoke | Предлагаемый вариант: новые операции доступны через каталог без пересборки списка инструментов сессии |
| Произвольный HTTP/SQL/код через один инструмент | Слишком слабый предметный контракт; сложнее проверять права, параметры и повторы |

Цена выбранного варианта: дополнительные обращения для обнаружения и описания; вложенные аргументы не проверяются SDK по предметной схеме. Компенсация — серверная валидация, компактные ответы и кеш описаний с версией. Приёмка должна измерить задержку и ошибки выбора, а не считать уменьшение числа имён автоматическим улучшением.

## Переход

1. Зафиксировать фактические наборы всех настроенных ролей в трёх точках входа, включая схемы, обработчики, режимы и адаптеры. Сохранить снимок до изменений.
2. Выделить общий реестр и контекст. Старые имена временно сделать адаптерами тех же операций; исключить двойные обработчики.
3. Добавить `taskflow` и общий сборщик сессий. Каталог и invoke используют одну функцию проверки доступности.
4. Проверить в изоляции на тестовой БД; никакие проверки не запускают настоящие роли и не меняют живые репозитории.
5. Выполнить ограниченную живую проверку после согласования реализации и сценария. Развёртывание — при отсутствии выполняющихся ходов либо с поддержанной совместимостью сессий.
6. Перевести новые ходы на единый вход. Сохранённые истории со старыми именами продолжают работать через адаптеры до завершения/миграции. Новые определения операций не требуют правки чата, работы и обсуждения отдельно.
7. Удалить старые сборщики и ручные списки после проверки совместимости. При необходимости отдельным этапом унифицировать SDK/хостовые операции.

Откат переключает сборщик на совместимые адаптеры того же реестра. Уже выполненные изменения не повторяются. Нельзя откатывать путём восстановления двух независимых реализаций.

## Уточнения после проверки проекта

- До переключения составить явную матрицу доступа: серверные проверки объекта и действия обязательны; `roleToolScope.ts` — исходная декларация выдачи, но обнаруженные расхождения с чатом перечисляются отдельно и согласуются владельцем. Случайный обход фильтра не становится автоматически разрешением. До решения спорные операции не включать в мигрируемую группу, старый путь для неё сохраняется.
- `discover` и `describe` без версии возвращают последнюю стабильную поддерживаемую версию; `invoke` требует явную версию. Версия, использованная незавершённой сохранённой сессией, поддерживается до её завершения либо явной миграции. Изменение прав применяется немедленно ко всем версиям.
- Состояния изменяющего запроса: `pending`, `running`, `succeeded`, `failed`, `unknown_outcome`. Операция `requests.status` читает доступный роли запрос по `request_id`; `requests.reconcile` запускает предусмотренную адаптером сверку без повторения изменения. При невозможности сверки результат остаётся `unknown_outcome` и требует явного решения; автоматический повтор не выполняется.

## Критерии приёмки

- Все настроенные роли получают `taskflow` во всех трёх точках входа.
- Одна новая тестовая операция становится обнаружимой и исполнимой во всех точках без редактирования их списков.
- Одинаковая роль, режим и контекст дают одинаковые схемы и решения авторизации.
- Проверены: чтение задачи; ответ коллеге; файл владельцу; консультация; документ; сдача своего этапа; чтение инфрапанели инфраструктурной ролью; исследовательская операция исследователем.
- Проверены отказы: чужой слот, недостаточные права, планирование с изменением, неоднозначный этап, недоступный хост и устаревшая версия. Сообщение указывает настоящую причину.
- Повтор изменяющего запроса не создаёт второе сообщение, карточку, файл или запуск; после рестарта сервера защита сохраняется.
- Лимиты, отмена и тайм-ауты работают через адаптеры. История старой сессии продолжается без потери результата.
- Журнал хранит имя операции, роль, режим, контекст, длительность и итог; секреты и полные приватные аргументы в него не попадают.
- По живому сценарию видно, что роль сама нашла возможность и получила наблюдаемый результат. Успешный прямой вызов обработчика этого не заменяет.

Решения о трёх действиях интерфейса, версионировании, поэтапном переносе хостовых операций и формате ошибок — предложения автора документа. Они не выдаются за ранее согласованные владельцем детали.
