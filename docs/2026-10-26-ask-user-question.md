# Уточнение у владельца из чата (`ask_user_question`) — 26.10.2026

Задача: роль задаёт владельцу вопрос с вариантами, владелец отвечает из
приложения, роль продолжает работу с места остановки. Плюс отдельная жалоба
владельца: быстрые варианты ответа на айфоне «не отрисовываются как должны».

## Решение владельца (26.10.2026)

| Развилка | Решение |
| --- | --- |
| Кому нужен механизм | **Только Помощнику владельца** (`u-secretary`, личная комната `chat-secretary`). Остальным ролям не внедряем — владелец общается с ними через «Единое окно» |
| Карточка задачи | **Опускаем.** Тот же серверный механизм заработает и в режиме карточки, но без запроса владельца это лишняя работа |
| Пакет `@juicesharp/rpiv-ask-user-question` | Не ставим: это расширение Pi для терминала, в неинтерактивном режиме инструмент вырезается из списка (`docs/hosts.md`). Берём из пакета формат, правила валидации и конверт результата |

## Почему «быстрые» варианты не работали

Сервер был исправен: в живой базе 85 сообщений с разобранными вариантами,
истинных сбоев разбора (строка `БЫСТРО:` последняя, а `quick_replies` пуст) — **0**.
Ломалась отрисовка на iPhone, в трёх местах:

1. `RoleChatsScreen.lastQuickReplies` требовал, чтобы последнее **сырое**
   сообщение совпадало с последним **видимым**. Следом лежала скрытая
   служебная строка (закрытая строка координации, дубль доигранного живого
   хода) — и плашки гасли совсем, хотя вопрос стоял прямо над ними.
2. Плашки рисовались отдельной строкой в конце ленты, а не у сообщения,
   которое их предложило: промежуточный ответ с вариантами терял кнопки, как
   только приходило следующее сообщение.
3. В `ChatScreen` (старый канальный чат `/api/chat`) `quick_replies` не
   читался вообще — модель `ApiChatMessage` без этого поля. Плашки были
   только в комнате роли.

### Сервер (`.110`, репозиторий `New-Todoist`)

Серверная часть выполнена отдельным агентом в своём worktree
(`roles/ask-user-question-20261026`, коммит `378fd27e`), по правилам сервера:
новая таблица — только versioned-миграцией в `server/src/migrations.ts`
(`180_chat_questions`), инструмент доступен только роли `secretary` (карта
`ONLY` в `server/src/lib/roleToolScope.ts`), живой сервис не перезапускался,
`main` не затрагивался.

Проверено по факту 26.10.2026 (не по отчёту агента): 11 файлов в коммите,
`askUserQuestion.test.ts` — 11 тестов, целевые прогоны — 23/23 PASS,
`tsc --noEmit` — PASS. Маршрут ответа возвращает `{message: …}` в формате
`formatChatMessage` — так и ждёт iOS-клиент (`RoleChatMessageEnvelope`).

Ключевое решение: **ожидание неблокирующее**. Инструмент пишет вопрос в БД и
возвращает роль «вопрос задан, заверши ход». Ответ владельца кладётся в чат
обычным сообщением, и штатная машина (`dispatchRoleReplies` → `deliverAgentReply`)
поднимает новый заход роли в той же сессии Pi — работа продолжается с места
остановки. Блокирующий `await` внутри инструмента упёрся бы в потолок хода
30 минут (`CHAT_RUN_CEILING_MS`) и потерялся бы при рестарте сервера.

## Ограничения

- **Симулятор и визуальные проверки не выполнялись** — по прямому указанию
  владельца от 25.10.2026. Внешний вид формы оценивает владелец; сборка
  проходит, но визуальной приёмки не было.
- **Серверная часть не развёрнута.** Коммит `378fd27e` лежит в ветке
  `roles/ask-user-question-20261026` на .110; живой сервис не пересобирался и
  не перезапускался, `main` сервера не тронут. До выката сервера вопрос в
  боевой базе не появится — iOS-клиент ждёт серверный контракт.
- Установка на iPhone — по отдельному поручению владельца.
- UI-тесты не писались и не запускались — то же указание владельца.
- Карточка вопроса рисуется только в плоском ответе роли (`flatReplyRow`), не
  в пузыре (`messageBubbleRow`). Для «только Помощник» это осознанно: ответ
  роли в личной комнате идёт плоским.
- `ChatQuestionOption.id` = `label`: при одинаковых подписях у вариантов
  разных вопросов идентификаторы столкнутся. Для текущего случая (один
  вопрос с вариантами) не мешает; при многошаговом режиме понадобится
  отдельный `id` у варианта.
