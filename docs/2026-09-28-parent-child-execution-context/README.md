# Контекст ветки: родитель и дочерние задачи

Дата: 28 сентября 2026 года
Статус: решение уточнено владельцем, реализация ожидает выделения server scope

## Проблема

Исполнитель дочерней задачи получает только собственную карточку и не может
надёжно собрать итог, если он зависит от результатов соседних задач. История
конкретной агентской сессии не является источником истины: после перезапуска,
смены исполнителя или недоступности комментариев контекст теряется.

Нужен серверный, версионируемый и ограниченный контекст ветки исполнения.
Он должен восстанавливаться по ID любой задачи и не должен зависеть от того,
какой агент раньше вёл чат.

## Решение

Расширить существующий конвейер `TaskContext v1` обязательным
`DependencyContextEnricher`.

Graph-зависимости остаются единственным источником порядка выполнения.
`DependencyContextEnricher` читает их только после допуска задачи и добавляет
в `TaskContext v1` первичный контекст её ветки: цель родителя, принятые
решения, статусы и результаты зависимостей. После него существующие
обогатители базы знаний и Мнемозины добавляют внешний справочный материал.
Так агент получает один пакет, но происхождение каждого раздела остаётся
видимым.

```text
родитель
  цель, решения, context_version
  |
  +-- исследование A -- completed -- summary + artifact
  +-- контракт B ----- completed -- summary + artifact
  `-- интеграция C --- depends_on A,B
       получает snapshot родителя, A и B перед запуском
```

## Контракт launch context

Перед `claim` сервер собирает один `TaskContext v1`. Его новый раздел
`dependency_context` содержит только данные, необходимые для выполнения
текущей задачи:

```json
{
  "task": { "taskId": "integration-c", "contract": "..." },
  "dependency_context": {
    "version": 7,
    "root": {
      "taskId": "parent",
      "goal": "Собрать проверенный итог",
      "decisions": ["Контракт B принят владельцем"]
    },
    "dependencies": [
      {
        "taskId": "research-a",
        "state": "completed",
        "summary": "Проверены источники и ограничения",
        "artifact": { "path": "docs/.../research.md", "verification": "sources checked" }
      }
    ],
    "openQuestions": []
  },
  "knowledge_context": { "sources": [] }
}
```

`dependency_context` не включает полные приватные чаты, токены или результаты задач,
которые не являются предками, прямыми зависимостями либо их необходимыми
предшественниками. Полный текст результата остаётся в артефакте; в snapshot
попадают короткий итог и ссылка.

## Семантика запуска

1. Диспетчер определяет список `depends_on` текущей задачи из существующего
   графа и проверяет его без циклов.
2. Каждое dependency edge имеет политику допуска: `review` для результата,
   готового к сборке, либо `completed` для результата, который обязан быть
   окончательно принят. Для старых edges действует совместимое значение
   `review`.
3. Если хотя бы одна обязательная зависимость не достигла своей политики,
   задача не запускается. Ей присваивается наблюдаемая причина блокировки,
   но не создаётся attempt.
4. Когда последняя зависимость становится допустимой, сервер повышает версию
   контекста корня и допускает задачу к очереди.
5. Непосредственно перед `claim` runtime запускает
   `DependencyContextEnricher`, затем обычные KB/Mnemosyne enrichers, и
   передаёт объединённый `TaskContext v1` отдельными размеченными секциями.
6. Если за время между допуском и `claim` версия изменилась, runtime берёт
   новую версию; attempt сохраняет фактически использованный номер версии
   для аудита.

Родитель-контейнер не становится исполнителем. Для итоговой сборки создаётся
явная дочерняя задача с ролью `synthesizer` или `critic_verifier` и зависимостями
на нужные результаты.

## Данные и API

Минимальная серверная модель:

- `task_dependencies` остаётся единственным источником порядка выполнения;
  новая таблица связей не создаётся.
- Для корневой задачи добавляется монотонный `task_context_version`.
- Для каждого завершённого узла сохраняется структурированный result record:
  `summary`, `artifact_path`, `verification`, `open_questions`.
- `DependencyContextEnricher` собирает `dependency_context` на чтении,
  а не хранит копии полных веток и не обращается к KB/Mnemosyne.
- В attempt сохраняется `task_context_version`; это позволяет
  воспроизвести, по какой версии контекста был запущен агент.

В MVP отдельный публичный endpoint context не добавляется. Runtime использует
внутренний builder, поэтому прежний API карточек не меняется. Внешнему агенту
контекст доступен только в сформированном launch packet.

В первой версии решения владельца и интегратора фиксируются в существующем
описании/результате задачи по утверждённой серверной схеме. Отдельный редактор
решений в iOS не входит в этот этап: он не нужен для корректного запуска.

## План реализации

### Этап 1. Аудит и миграция

В `/home/maksim/Проекты/New-Todoist/server` проверить фактические таблицы,
маршруты и call sites существующих `task_dependencies`, admission и
`TaskContext v1`. Добавить обратимую SQLite-миграцию для version и result
record, без изменения исторических карточек.

Критерий: существующие деревья и одиночные задачи читаются без нового поля;
версия нового корня начинается с `1`.

### Этап 2. `DependencyContextEnricher`

Создать изолированный server-side enricher, который получает task ID,
находит корень, вычисляет транзитивные обязательные зависимости и добавляет
строго типизированный `dependency_context` в `TaskContext v1`. Enricher
отклоняет ссылку вне дерева и цикл; к внешним базам знаний не обращается.

Критерий: unit-тесты подтверждают состав root/dependencies, исключение
несвязанных соседей и стабильную сортировку по dependency order.

### Этап 3. Результат зависимости и policy edges

Добавить единый валидатор структурированного результата при переходе узла в
`review`/`completed` и хранение policy `review | completed` на dependency edge.
Старый строковый result продолжает работать и нормализуется в `summary`, чтобы
не ломать действующих агентов.

Критерий: задача с policy `review` допускается после review предшественника,
с policy `completed` ждёт принятия; зависимость вне дерева и цикл отклоняются.

### Этап 4. Admission и runtime

Встроить dependency gate перед созданием attempt. При незавершённых
зависимостях создать понятный blocked event без запуска агента. Перед
`claim` добавить `DependencyContextEnricher` первым в существующий pipeline,
затем сохранить объединённый `TaskContext v1` в prompt/runtime packet и
зафиксировать использованную версию в attempt.

Критерий: интегратор не запускается раньше A/B, после их завершения получает
их итог и артефакты, а повторный admission не создаёт второй attempt.

### Этап 5. Наблюдаемость и E2E

Добавить audit events: `dependency_context_updated`,
`dependency_context_blocked`, `dependency_context_used`. Провести живой
закрытый сценарий: A и B завершаются, C собирает их артефакты, после чего
родитель допускается существующей логикой `admitParentAfterChildren()`.

Критерий: из attempt и task event видно, почему задача была заблокирована,
какую версию она использовала и где лежат результаты предшественников.

## Вне первого этапа

- Автоматический пересказ полного чата в prompt.
- Общая память всех агентов вне ветки задачи.
- Отдельный публичный API контекста в первом этапе.
- Новый UI для ручного графового редактирования на iOS.
- Изменение ролей, прав или существующего KnowledgeEnricher.

## Проверки

- Одинокая задача: `DependencyContextEnricher` формирует пустой
  `dependency_context` и не вызывает KB/Mnemosyne сам.
- A и B независимы: могут стартовать параллельно.
- C зависит от A/B: до завершения обеих blocked, после получает оба итога.
- Зависимость вне дерева, отсутствующий ID и цикл: admission атомарно
  отклоняется без attempt.
- Повторная доставка события и повторный admission: без дублирования attempt.
- Перезапуск runtime: новый агент восстанавливает тот же snapshot по task ID.
- Артефакт отсутствует: `dependency_context` явно сообщает об этом, а executor не
  выдумывает результат.
