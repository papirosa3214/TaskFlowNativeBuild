## Причина и исправление

POST /run не учитывал роль из assignee_id и отправлял карточку в старый
отдельный manual_run.sh; ответ ok не подтверждал успешную работу процесса.
Нативный запуск сначала отдельно поднимал ready, а затем отправлял второй
запрос /run, создавая ещё одну возможность повторного запуска.

Теперь сервер учитывает назначенную роль и атомарно сохраняет ready и один
manual job в существующей очереди. Повторные запросы отклоняются 409.
Роль без доступного назначения возвращает понятную ошибку 422. Встроенный
worker запускает работу и сохраняет техническую ошибку; новая попытка
разрешена явно после терминального сбоя. Для ручного старта maxAttempts=1.

GET /tasks/:id/execution сообщает очередь, работу, ожидание, ошибку и
разрешённые действия. Источники — очередь, runtime и состояние карточки.
PATCH смены исполнителя владельцем и создание/правка/утверждение плана
защищены на сервере после выбранного одиночного запуска.

На iOS запрос блокируется сразу; после принятия повторный старт погашен,
выбор исполнителя заменён подписью, шаблоны плана скрыты, остальные действия
плана отключены. После ошибки доступен «Повторить запуск исполнителя».
Роль назначения показывается вместо ошибочного «Автоматически».
При недоступности нового endpoint действия блокируются до обновления.
Статус обновляется существующим опросом карточки и после запроса запуска.
