# Нативные инструменты ролей: отдельные операции и загрузка по требованию

25.10.2026. Работа велась в серверном исходнике `/home/maksim/Проекты/New-Todoist` на .110 (`server/`); этот документ — запись о сделанном. Продуктовая логика ролей не менялась: права, контекст, идемпотентность, аудит и порядок ходов прежние.

## Главное

Роли работают на Pi SDK 0.84.4 (`@earendil-works/pi-coding-agent`). Операции TaskFlow были зарегистрированы отдельными инструментами, но модели показывался только общий шлюз `taskflow` с произвольным полем `arguments`. Штатные механизмы Pi были закрыты обёрткой:

- точный JSON Schema операции до модели не доходил — аргументы приходили произвольным словарём, и модель угадывала поля;
- в каждый запрос уходили описания всех операций: 30 КБ на builder, 54 КБ на secretary (57–113 инструментов), тогда как роль регулярно зовёт 11–17 из них.

Теперь операции видны модели отдельными инструментами с точными схемами, а в запрос уходит ядро; остальное подключает сама модель через `taskflow_tools` — штатным механизмом Pi `session.setActiveToolsByName`.

## Диагноз по живому сервису

Подтверждено на работающем API до правок: в сессии роли (`b504958a`, builder) модель звала только `taskflow` — 5 вызовов, ни одного нативного.

Под тем же общим шлюзом роли вставали на неверных вызовах: «ход остановлен: 3 неверных вызова `taskflow_subtask_done` подряд» (07:00) и «5 неверных вызовов `taskflow_host_bash` подряд» (07:45–07:48) — роль повторяла одну и ту же неудачную форму вызова, и её глушил сторож неверных вызовов.

## Что стало

### 1. Отдельные инструменты с точными схемами

`buildRoleToolCatalog` отдаёт модели каждую операцию своим именем с её JSON Schema. Общий шлюз `taskflow` остаётся зарегистрирован, но модели не виден: он нужен истории и голосовому пути (`server/src/lib/secretaryVoiceTools.ts`).

Права, контекст, идемпотентность и учёт не изменились: нативный инструмент — это тот же вызов шлюза (`universal.execute` → `operationRestriction` → аудит).

### 2. Загрузка по требованию

В реестре сессии — все операции, которые роль имеет право вызывать. Активно ядро (19–26 операций) и загрузчик `taskflow_tools`: он показывает индекс доступных операций и подключает нужные по именам или по смыслу запроса. Индекс выдаётся один раз за сессию и дальше живёт в истории — платим за него не каждый запрос.

| роль | операций | схемы в запросе | payload запроса |
|---|---|---|---|
| builder | 57 → 24 | 30.1 → 11.5 КБ | 58.2 → 36.2 КБ |
| researcher | 61 → 23 | 30.9 → 11.1 КБ | — |
| secretary | 113 → 26 | 54.4 → 12.3 КБ | — |
| critic_verifier | 50 → 19 | 27.2 → 9.1 КБ | — |

Ядро отобрано по частоте за 14 дней (`role_tool_audit`) и по обязательности шага: ориентировка, слот, план, комментарий, сдача шага.

### Деталь SDK, на которой всё держится

`tools` в `createAgentSession` — это фильтр **реестра**, а не только активации: инструменты вне списка нельзя активировать позже (`setActiveToolsByName` их игнорирует — «Only tools in the registry can be enabled»). Поэтому allowlist содержит все операции, а активный набор сужается сразу после создания сессии (`installNativeToolCore`). При старом allowlist динамическая загрузка не заработала бы вовсе.

## Где в коде (сервер, .110)

- `server/src/runtime/nativeToolLoader.ts` — новый: загрузчик `taskflow_tools`, подбор по смыслу запроса, индекс операций.
- `server/src/runtime/roleToolCatalog.ts` — ядро операций, сборка каталога, `installNativeToolCore`.
- `server/src/runtime/inProcessRun.ts`, `PiRuntimeAdapter.ts`, `slotConversation.ts` — три места создания сессии: allowlist расширен до всех операций, активный набор сужается после создания сессии.
- `server/test/nativeToolLoading.test.ts`, `nativeToolPayload.test.ts`, `nativeToolSchemas.test.ts` — контракт ядра, загрузчика, схем и payload.
- `server/test/roleToolCatalog.test.ts`, `slotConversation.test.ts`, `chat-session-runtime.test.ts` — контракт активного набора во всех режимах.
- `docs/2026-10-25-native-tool-loading.md` (в серверном репозитории) — разбор решения на стороне сервера.

## Проверка

- 25 тестов в 5 файлах: ядро вместо всего каталога, загрузчик по именам и по смыслу, запрет подключить закрытое ролью, поведение реестра SDK, неизменность системного промпта при сужении.
- Сквозная проверка на реальной сессии Pi со скриптованной моделью: в первый запрос уходит ядро (24 инструмента, 36.2 КБ против 57 и 58.2 КБ у полного каталога), общий шлюз модели не виден; после вызова `taskflow_tools` подключённая операция приходит в следующем запросе и модель зовёт её по имени.
- Полный прогон сервера против базового коммита: новых провалов нет, четыре прежних чинятся. 90 падающих тестов были и до правки — это окружение (расхождение числа профилей ролей, ненастроенный провайдер в тестовой среде), отдельная зависимость.

## Выкладка

Живой API на .110 — `node dist/index.js` под юзер-юнитом systemd `taskflow-server.service`. Перезапуск рвёт идущие ходы ролей, поэтому делался только при пустой очереди: сторож ждал семи минут тишины в файлах сессий и перезапустил сервис в 09:47.

Живое подтверждение в 10:23, ход роли builder на карточке `b504958a`:

1. `taskflow_work_plan` — нативная операция, отработала;
2. `taskflow` → «Tool taskflow not found» — общий шлюз недоступен, отказ чистый;
3. `taskflow_tools` с запросом про host-bash подключила шесть host-операций (`taskflow_host_bash`, `_find`, `_grep`, `_edit`, `_ls`, `_read`);
4. `taskflow_host_bash` отработала и вернула реальный вывод.

Возобновив старую сессию, модель один раз позвала `taskflow` по старой привычке — и получила отказ вместо искажённого вызова.

## Открытые вопросы

- Строгая генерация аргументов на стороне MiniMax — отдельный вопрос. Схема на проводе строгая (корневые ограничения возвращаются в payload), но enforce у провайдера не запрашивается: Pi шлёт `strict` только при `compat.supportsStrictTools`, а он по умолчанию выключен. Нужен один пробный запрос к MiniMax.
- Временная карточка-проверка `56deaa21` осталась свободной: агент не может ни взять, ни закрыть её (ограничение сервера), снять может владелец.
- Разбор применения в TaskFlow: `docs/2026-10-25-native-tool-loading.md` в репозитории `New-Todoist` на .110.
