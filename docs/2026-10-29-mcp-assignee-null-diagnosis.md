## Роли, команда и интерфейс

`server/src/runtime/planSubtaskAdmission.ts:318–345`: followSlotAssignee назначает карточку на roleUserId активного слота; человека не вытесняет, заблокированный слот имеет приоритет. `348–378`: assigneeToBlockedSlot направляет карточку к заблокированному исполнителю. История данной карточки содержит переходы assignee_follows_slot к role_builder, затем role_qa. Синтетическая роль здесь является существующей записью users; отсутствие пользователя не является причиной null.

Полный SELECT в tasks.ts:315–337 предусматривает ответственного по первому незавершённому слоту утверждённого плана (in_progress имеет приоритет), а после завершения всех слотов — команду. Но нынешний helper исключает эти вычисляемые поля из ответа.

Нативный интерфейс не зависит только от assignee_name:
- `/Users/max/Проекты/TaskFlowNativeBuild/Sources/Features/Task/TaskFormViewModel.swift:326` сохраняет task.assigneeId в модель формы.
- `Sources/Features/Task/TaskFormScreen.swift:2226–2237` выделяет ключ роли из role_… и ищет название в профилях roles; приоритет: dispatchedRole → ownerSelectedRole → assignedRole → planRole → machineSelectedRole. Поэтому видимая подпись может показывать логическую роль с более высоким приоритетом, а не буквально tasks.assignee_id.
- `Sources/Core/Models/Task.swift:417–427`: аватар берёт assigneeId → planResponsibleId → planTeam.first. Идентификатор исполнителя сохранён API, поэтому назначение может быть видно даже при потерянном имени.

Конкретный открытый экран владельца визуально не проверялся; подтверждён путь данных по исходникам.

## Диагноз и минимальное исправление

Данные назначения корректны. Первичный дефект — потеря JOIN/вычисляемых полей в SQL-проекции REST. MCP скрывает разницу между отсутствующим именем и отсутствием назначения. Утверждение агента «исполнитель не назначен» ошибочно: null имени не доказывает null assignee_id; история также противоречила такому выводу.

Минимальная основная правка: сохранить динамические физические колонки без composed_prompt_snapshot, затем добавить весь общий набор вычисляемых полей из TASK_COLUMNS (вынести его в общую константу, чтобы не разошёлся). Не возвращать t.* с тяжёлым prompt. Нужны целевые RED→GREEN тесты detail/list/children: существующая роль и проект дают имена, вычисляемые поля плана сохранены, prompt отсутствует.

Дополнительное укрепление MCP: отдавать assignee_id/project_id и состояние назначения отдельно от имени; для плана — ответственного/команду. Одной подстановки role_qa в текст имени недостаточно: она маскирует серверную регрессию и не возвращает остальные поля. Исправления не выполнялись.

## Перепроверка: что видят внутренние роли

Уточнение владельца: ответственный динамический — кто работает либо на ком этап заблокирован. **Утверждение «внутренние роли не видят ответственного» слишком категорично и неверно.** Роль знает собственное назначение и может получить актуальные роли/состояния всех слотов из плана. Но компактное чтение карточки не содержит отдельного надёжного поля динамического ответственного. Эти два факта нельзя смешивать.

Перепроверка выполнена только по SSH: чтение исходников, SQLite mode=ro и сохранённых сессий. TaskFlow MCP, запуск ролей и записи в карточку не использовались.

### Динамическое назначение и маршрутизация

- `server/src/roleRouting.ts:76–82`: roleUserId(qa) → role_qa (особое исключение — secretary).
- `server/src/runtime/planSubtaskAdmission.ts:494–507`: при старте слот получает agent_id роли, in_progress и attempt; затем followSlotAssignee обновляет assignee_id карточки. Вызов runRoleInProcess следует после этого (`516–519`).
- followSlotAssignee (`323–345`) не вытесняет человека и сохраняет исполнителя, если у него уже есть blocked-слот. assigneeToBlockedSlot (`352–378`) выбирает заблокированный слот, сначала needs_input, затем по свежести heartbeat, и назначает его роль карточке.
- Это сохранённый указатель маршрутизации, обновляемый переходами, а не только вычисляемое имя. При нескольких параллельных активных слотах один assignee_id не перечисляет всю бригаду; полный источник — план/слоты.
- `server/src/runtime/taskDiscussion.ts:239–252` определяет адресата этапа непосредственно через subtasks.agent_id и users.role_key, независимо от assignee_name.
- При повторном чтении БД: tasks.assignee_id=role_qa, tasks.agent_state=NULL; qa_6.agent_id=role_qa, agent_state=blocked, done=0; пять builder-слотов завершены. NULL верхнего agent_state не означает отсутствие работы/блока: `routes/tasks.ts:202–214` вычисляет состояние карточки по слотам. Ответственный по фактам — QA, на нём блок.

### Что попадает модели при старте

`runtime/inProcessRun.ts:1017–1030` строит planSubtaskPrompt с roleTitle, taskId, subtaskId и названием своего шага; `1813–1815` выбирает это задание при запуске. `1516–1523` дополнительно передаёт в TaskContext actor={id:roleUserId(role), name:roleTitle(role)}, зависимости, контекст слота и историю.

Важное различие: `taskForLaunchContext` (`955–968`) выбирает id/title/description/project_id/priority/due_date и комментарии, **не assignee_id всей карточки**. Поле assignment.actor в TaskContext — получатель задания, а не универсальный динамический ответственный всей карточки. Собственный слот роль знает явно; автоматически обновляемого глобального указателя в этом блоке нет. История и стартовое задание — снимок на момент формирования, для текущего положения нужен новый read плана.

### Уточнённое исправление, если будет поручено

Возврат вычисляемых REST-полей исправит внешний Python MCP и клиентов, но **сам по себе не добавит ответственного во внутренний taskflow_task**, поскольку его short() эти поля намеренно не включает. Для единообразного ответа на «на ком сейчас карточка» понадобилось бы явно отдавать assignee_id + имя в обоих компактных форматах и при необходимости текущие слоты (role/state), не смешивая их с выбранной специализацией или ответственным за интеграцию. Проверять отдельными RED→GREEN тестами. Механизм назначения, маршрутизация и чтение плана по текущим доказательствам не требуют исправления из-за этого null.
