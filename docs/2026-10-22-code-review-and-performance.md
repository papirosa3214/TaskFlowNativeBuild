## Часть 1. Производительность

### 1.1 «Сегодня» — снимок пересобирался на каждом кадре

`TodaySectionView.computation` — вычисляемое свойство, а `TodayComputation`
собирает около двадцати фильтров и шести сортировок по всему списку задач.
Экран обращался к нему **дважды за проход** (тело + тулбар), то есть на каждый
кадр прокрутки.

Комментарий в `TodayComputation.swift` прямо обещал обратное: «Результаты
цепочки вычисляются один раз при создании снимка экрана» — но снимок был
вычисляемым свойством, и обещание не выполнялось.

**Правка.** Кэш последнего снимка (`Sources/Features/Today/TodayComputationCache.swift`):
ключ — все десять входов (`allTasks`, `currentUser`, `agents`, `filters`,
`showAgentTasks`, `visibleProjectIds`, `today`, `activeHourDate`, `isLoading`,
`isError`); пока хоть один отличается — снимок собирается заново. Сравнение
по значению, а не по идентичности: список задач из стора меняется на месте.

**Почему не сломается.** `TodayComputation` — единственный потребитель этих
данных (`grep`: `TodaySectionView.swift:84`), скрытых входов у него нет:
внутри используются только переданные параметры, никаких `Date()` или
глобального состояния.

**Проверка.** `Tests/Today/TodayComputationCacheTests.swift` — 6 тестов:
одинаковые входы → одна пересборка (на старом коде было две — тест падал);
изменённые задачи, смена фильтра, смена дня → пересборка; содержимое снимка
не отличается от свежей сборки.

### 1.2 «Заметки» — дерево собиралось на каждом кадре

`NotesViewModel.rows` читается прямо в `ForEach` на экране (`NotesScreen.swift:81`).
Дерево собиралось заново на каждом проходе `body`, а внутри для **каждой
папки** заново считались счётчик заметок и «последняя заметка» — с разбором
дат по каждой заметке в каждой папке (O(F·N) разборов дат).

**Правка (две части).**

1. Кэш дерева по ключу (папки, заметки, раскрытые папки, порядок дат) —
   `@ObservationIgnored`, чтобы пересчёт не будил наблюдателей.
2. Внутри одного перестроения агрегаты считаются **один раз**: даты всех
   заметок разбираются по одному разу на заметку, заметки группируются по
   папкам, поддерево каждой папки считается один раз (`RowsContext`).
   Порядок обхода и правило выбора «последней заметки» сохранены дословно
   (при равных датах остаётся первая — как у `max(by:)`).

**Проверка.** `Tests/NotesViewModelCacheTests.swift` — 6 тестов: неизменные
данные → одна сборка (на старом коде две — падало); новая заметка и
сворачивание папки → пересборка; содержимое дерева (порядок строк, глубина,
счётчик заметок, последняя заметка) не изменилось.

### 1.3 Markdown — разбор повторялся на каждый кадр

`MarkdownParser.parse` стоит 0.153 мс на ответ роли (замерено на этом же
исходнике, `/tmp/tfbench`). Его зовут:

- `TaskFormScreen.swift:1847` — из `Binding`-геттера, то есть на **каждый**
  проход экрана, для каждой подзадачи;
- `TaskFormScreen.swift:2861` — то же для черновика подзадачи;
- `RoleReplyMarkdown.swift:110` — при каждой перерисовке сообщения чата.

**Правка.** `Sources/Features/Markdown/MarkdownParseCache.swift` — кэш
разбора по тексту (128 записей / 256 КБ текста, вытеснение по давности
обращения, под замком).

**Что меняется в идентичности блоков.** Раньше два разбора одного текста давали
разные `UUID` блоков, теперь — одинаковые. Проверено, что это безопасно:

- `RoleReplyMarkdown` использует `id: \.offset`, а не `block.id`;
- `BlockDocumentEditor` (`BlockDocumentEditor.swift:468`) использует `ForEach(blocks)`
  по `block.id`, но блоки одного документа приходят из одного разбора —
  внутри разбора UUID разные, как и раньше;
- редактор держит **свой** `NoteBlockControllerStore` на каждый экземпляр
  (`@State private var controllerStore`), поэтому два редактора с одинаковым
  текстом не делят состояние;
- ключ чеклиста в чате считается от индекса сегмента, а не от `block.id`
  (`RoleReplyMarkdown.swift`), состояние чеклистов не смешивается.

Побочный плюс: идентичность блоков в карточке задачи перестала «прыгать» на
каждом кадре — раньше `Binding`-геттер отдавал новые UUID и строки редактора
пересоздавались.

**Проверка.** `Tests/MarkdownParseCacheTests.swift` — 4 теста: повторный
разбор даёт те же блоки; кэш не меняет разбор (совпадают `kind`, `level`,
`runs`); правка на месте не задевает кэш; разные тексты — разные блоки.
Существующие `Tests/MarkdownParserTests.swift` (28 тестов) проходят целиком.

### 1.4 Даты — 36-44 мкс на разбор, а даты везде

Это нашлось при разборе «Заметок» и оказалось общей бедой приложения:
`DateFormats.sqliteUTC` разбирает дату через `DateFormatter` — на этой машине
**36-44 мкс на дату** (замерено на 500 разных строках, `/tmp/datebench2`).
Даты разбираются в каждом списке, в чате, в тепловой карте, в графике
активности, в карточках задач, в уведомлениях — 31 место вызова
`sqliteUTC(`.

**Правка.** `Sources/Core/Common/DateFormats.swift`: канонический вид
«yyyy-MM-dd HH:mm:ss» разбирается вручную — без `DateFormatter`, без
`Calendar` и без локали (дни считаются по пролептическому григорианскому
календарю). Любая неканоничная строка уходит в форматтер, как раньше.

**Важная деталь, которую поймал тест.** `DateFormatter` переносит лишние дни
и часы: «2026-02-30» → 2 марта, «24:00:00» → следующий день. Быстрый путь
такие строки отклоняет → они уходят в форматтер → результат тот же. Тест
сверяет не «nil», а равенство общей точки входа эталонному форматтеру — на
всех таких строках.

**Проверка.** `Tests/DateFormatsFastParseTests.swift` — 5 тестов: результат
совпадает с форматтером на 14 опорных датах (високосный год, границы
месяцев и года, epoch); неканоничные строки уходят в форматтер и дают тот же
результат; ISO-строка сервера (`last_seen_at`) не сломалась; ручной разбор
в разы быстрее форматтера.

### 1.5 Что осталось незакрытым (файлы заняты другими агентами)

| Что | Где | Почему не правил |
| --- | --- | --- |
| Разбор markdown в `Binding`-геттерах карточки задачи | `TaskFormScreen.swift:1847, 2861` | Файл занят активными строками реестра (LOCK-TASK-CREATE-HEADER-20261018, LOCK-FAMILY-EDIT-20261001 и др.) — правка другого агента может затереть мою |

## Часть 2. Кодревью по шкале Apple

Проверены все 370 файлов `Sources/` по осям: анимации и жесты; материалы и
глубина; типографика и Dynamic Type; доступность, отклик, тактильная отдача;
ориентирование на экране. Найдено 34 расхождения. **Ничего не правилось** —
это перечень решений для владельца.

### 2.1 Анимации и жесты

Главное: шкала движения есть и она грамотная — `DesignSystem/Theme/TFMotion.swift`
(пружины, отскок только после жеста с импульсом, замена на затухание при
«Уменьшить движение», значения совпадают с ориентирами скилла). Но применена
она в трёх местах, а **41 сайт** в приложении использует кривые с
фиксированной длительностью, и примерно 90 % экранов не учитывают «Уменьшить
движение».

- **Жест + большая поверхность (приоритет 1).** `TodaySectionView.swift:63-76`
  (свайп вкладок, живое смещение выброшено, `withAnimation(.easeInOut(duration: 0.2))`),
  `TimelineScreen.swift:100` (`.timingCurve(..., duration: 0.6)` — слой-zoom всей ленты),
  `UpcomingListView.swift:94, 133` (переключение месяц↔неделя),
  `RootShellView.swift:205` (шторка меню), `TFTabBar.swift:200, 234`,
  `TFGlassButtonStyle.swift:137`. → `TFMotion.standard` / `TFMotion.sheet`.
- **«Уменьшить движение» не учтено.** `TFTabBar.swift:200, 234` — при том что
  соседний `TFPillTabBar.swift` его учитывает; `RoleLiveTurnView.swift:287` —
  при том что тот же файл учитывает в `:306, :498, :540, :558`. Ещё ~30 мест.
- **Жесты без отдачи скорости.** `UpcomingWeekView.swift:99-107`,
  `TodayHoursView.swift:369-377`, `UpcomingListView.swift:261-269`,
  `TaskChatSheet.swift:24-31`, `TaskFormScreen.swift:3232-3237`,
  `SecretaryVoiceScreen.swift:200-217` (жёсткий клэмп вместо rubber-band),
  `TaskFamilyNavigation.swift:553-582` (жёсткая остановка `min(width, distance)`
  вместо прогрессивного сопротивления, пружина доводки без `initialVelocity`).
- **Нет непрерывной обратной связи 1:1.** `TodaySectionView.swift:65`,
  `TimelineScreen.swift:108-116`, `UpcomingWeekView.swift:99-107`,
  `TodayHoursView.swift:369-377`, `TaskChatSheet.swift:24-31` (плюс
  `.interactiveDismissDisabled()` — шторка не едет за пальцем вообще).
- **Мёртвый код.** `DesignSystem/Theme/Metrics.swift:64` —
  `dragLiftSpring` записан кривой `.timingCurve(0.34, 1.56, 0.64, 1, duration: 0.22)`
  (псевдо-пружина с перелётом) и **нигде не используется**.
- **Решение владельца — не трогать.** `DesignSystem/Components/HorizontalPan.swift:136-138`:
  `settleAnimation(velocity:)` намеренно игнорирует скорость, пружина одна на
  все случаи. Обоснование записано в `:120-135` (16.09.2026). Расхождение с
  принципом «отдача скорости в анимацию» — но менять без вашего решения нельзя.

**Образец, на который надо равняться:** `Features/Chat/ChatEdgeRail.swift` —
1:1 отклик, решение по броску через направление или проекцию инерции
(`decelerationRate 0.998`, `:136-139`), пружина с `initialVelocity` из скорости
пальца (`:104-106`), отскок только после флика, учёт «Уменьшить движение».

### 2.2 Материалы, глубина, иерархия

- **Модальная панель без scrim.** `QuickAddTaskView.swift:74` и
  `ProjectsScreen.swift:525`: фон под стеклянной карточкой не приглушён.
  В legacy-ветке (`QuickAddTaskView.swift:96-99`) затемнение есть, в ветке
  iOS 26 — нет, то есть один экран на двух ОС выглядит по-разному.
- **Материал вместо вуаля.** `QuickAddTaskView.swift:96-98` и
  `ProjectsScreen.swift:543-545`: `Rectangle().fill(.ultraThinMaterial).overlay(Color.black.opacity(0.1))`.
  При «Уменьшить прозрачность» материал перестаёт размывать и приглушение
  исчезает.
- **Светлая полупрозрачная плашка на светлом.** `NoteEditorScreen.swift:194` —
  `.background(.ultraThinMaterial, in: Capsule())` с подписью `Color.tfDim` в
  светлой теме (фон `#f4f4f5`, карточка `#ffffff`).
- **Стеклянные пилюли без учёта прозрачности.** `TFKeyboardPill.swift:15, 20` —
  используются в 10 местах, ни границы, ни тени.
- **Плоский серый вместо вибрации.** `Color+Palette.swift:29, 31` — `tfSub`,
  `tfDim` заданы фиксированным hex и стоят на материалах; в палитре есть

### 2.3 Типографика и Dynamic Type

Шкала `TFTextStyle` сделана правильно — каждая ступень через `@ScaledMetric`,
трекинг по размеру (крупный — отрицательный, мелкий — положительный). Не
переделывать. Расхождения:

- **Обрезка текста при крупном Dynamic Type.** `TFTaskRow.swift:160, 166, 173` —
  `.lineLimit(1)` на заголовке, описании и метке задачи; также `AgentRow.swift:130-163`,
  `UpcomingTaskChip.swift:36, 89`, `ReasonStrip.swift:39, 43`.
- **Статический кегль.** `TFTabBar.swift:96` (число дня),
  `TimelineScreen.swift:82` (подпись кнопки). `Font.system(size:)` не масштабируется.
- **Статический шрифт в данных.** `ActivityChart.swift:593, 618, 634`,
  `RoleReplyMarkdown.swift:244` — сам проект это фиксирует в
  `Typography.swift:194-197`.
- `.dynamicTypeSize(.fixed)` в приложении нет ни разу — это правильно.

### 2.4 Доступность, отклик, тактильная отдача

- **«Уменьшить прозрачность» не поддерживается вообще** — ноль обращений к
  `accessibilityReduceTransparency` во всём репозитории.
- **«Увеличение контраста» не поддерживается вообще** — ноль обращений к
  `accessibilityContrast` / `legibilityWeight`; палитра (`Color+Palette.swift:12-66`)
  различает только тему.
- **Нет тактильной отдачи на коммите и на ошибке.** `TaskConfirm.swift:45-49`,
  `TaskFormScreen.swift:2967-2970`. `UINotificationFeedbackGenerator().notificationOccurred(.error)`
  в приложении не встречается ни разу.
- **Кнопка без подписи.** `TFPillTabBar.swift:113-119` — «+» с
  `accessibilityIdentifier`, но без `accessibilityLabel`: VoiceOver читает имя
  символа.
- **Нет отклика на нажатие.** `TFPillTabBar.swift:118` и
  `ChatRoomsPanel.swift:26, 38` — `.buttonStyle(.plain)` при наличии
  `TFTapScaleStyle`.
- **Состояние только цветом.** `ChatRoomsPanel.swift:63-66` — зелёная точка
  «роль работает» дублируется текстом только в VoiceOver-подписи.

### 2.5 Ориентирование на экране

- **Подпись вкладки расходится с тестами.** `RootShellView.swift:42` — «План»,
  `TFPillTabBar.swift:68` рисует `accessibilityLabel`, UI-тесты ищут
  «Планирование» (`UITests/AccessibilityTests.swift:61-62`,
  `UITests/UIStyleGateUITests.swift:146`), в превью второго таббара —
  «Планирование» (`TFTabBar.swift:334`). Три разных слова на один таб.
- **Экран без навигационного контекста.** `TimelineScreen.swift:55` —
  `.toolbar(.hidden, for: .navigationBar)`, выход «Назад (демо)» (`:80`),
  при этом экран открывается из прода (`RouteDestinationView.swift:49`).
- **Заголовок не отвечает на «где я».** `UpcomingScreen.swift:113-139` — в
  заголовке дата или месяц, а не имя раздела.
- **Поиск без заголовка.** `SearchScreen.swift:47-49` — только `.searchable`,
  без `.navigationTitle`.

### 2.6 Что уже сделано правильно — не переделывать

`.tfNativeHeader` (только `navigationTitle` + `toolbarTitleDisplayMode`, без
самодельных шапок), `.tfSoftTopScrollEdge()` / `TFHeaderBackdrop` (мягкий
край вместо линии-разделителя), шкала `TFMotion`, шкала `TFTextStyle`,
`TFButton` с `minHeight` через `@ScaledMetric`, стили отклика
`TFTapScaleStyle` / `TFTapRowStyle` / `TFTapFadeStyle` (отклик на нажатии, а
не по отпусканию), параллельные панели без scrim (`ChatRoomsPanel`,
`ChatEdgeRail`, `TaskFamilyNavigation`), `HorizontalPan` с порогом направления
10 px и коэффициентом преобладания 2.0.

## Границы

- Функционал не вырезан, логика не менялась: кэши отдают ровно то же, что
  считалось заново; наборы задач, дерево заметок, разбор markdown и разбор
  дат дают те же результаты, что и до правки (проверено тестами сверки).
- Правки не выходят за строку `LOCK-OPT-PERF-20261022` в `AGENT-WORK-SCOPES.md`.
- Дизайн-находки (часть 2) **не правились** — это перечень решений для
  владельца, там нужны отдельные строки реестра.
