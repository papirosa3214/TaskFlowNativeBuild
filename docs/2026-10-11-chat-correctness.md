# TaskFlow: исправление чата, 11 октября 2026

## Причины

SQLite передавал время как `YYYY-MM-DD HH:MM:SS`, а клиент распознавал только ISO8601. Это ломало порядок и сопоставление готового ответа с живым ходом. История дополнительно сортировалась по времени после серверной сортировки. Искусственная очередь текста начиналась с задержки 0,8 с, отставала на несколько секунд и дочитывала завершённый ответ ещё 2 с. Незакрытый блок HTML/widget оставался «формируется» даже после завершения. REST-снимок мог перезаписать сообщения из WebSocket. Пустой финальный ответ модели мог закончить ход без видимого результата.

## Изменения

- Сервер передаёт `sequence` и `trigger_message_id`; клиент сохраняет последовательность истории и показывает «В ответ на…» у живых и готовых ответов.
- Поддержаны SQLite/ISO даты и разная точность секунд. REST объединяется с более новыми событиями сокета, устаревший снимок не оживляет завершённый ход.
- Стартовый буфер убран; скорость текста 120–1200 символов/с, целевое отставание 0,15 с. При готовом ответе остаток сразу показывается. Rich-блоки обходят очередь текста.
- Финальный rich-блок без закрывающей строки больше не остаётся в ожидании. Повторная доставка не перезагружает уже работающий HTML.
- Завершение снимает индикатор и таймер; сервер очищает live/typing в finally, включая ошибку сохранения. Пустой ответ получает явное сообщение, связанное с вопросом.
- История отображается через LazyVStack.

## Проверки и измерения

Сервер: 44 целевых теста, TypeScript build успешно. Клиент: 54 целевых теста успешно; дополнительный XCUITest проверяет оба контекста ответа после завершения, исчезновение pending/работает/stop, порядок ответов, готовый widget и сохранение нажатого HTML при повторной доставке.

Физический iPhone Air, iOS27.0.1: сценарий трёх свайпов по 300 сообщениям прошёл, XCTHitchMetric зарегистрировал 0 hitches, CPU 1,96 с, пик памяти 61458 kB. Это измерение конкретного сценария, не гарантия для любого текста/HTML.
